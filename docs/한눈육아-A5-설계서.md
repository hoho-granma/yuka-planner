# 한눈육아 A5 설계서 — 엔진 확장 메커니즘 (`basis`·새 트리거·`requiredValues`·`timeline`)

작성: 2026-10-01 · 상태: **설계안 — 승인 대기(구현 시작 안 함)** · 기준 커밋: `f0d7c5b`(v1.12.18) / 문서 커밋 `eedd70a`
근거: `한눈육아-확장설계-2단계-상세.md` §13-5·§13-7·§13-8·§13-9, §14 **Q-G(승인됨, 기존 결과 불변이 절대 조건)**, `한눈육아-이슈기록.md` I-3, 실제 코드(`js/todo-engine.js`, `js/schedule.js`, `js/child-timeline.js`, `js/date-calc.js`)

## 1. 목표와 비목표

**목표** Q-G로 승인된 5가지 *메커니즘*을 엔진에 추가한다. 추가만 하고, 아무 데이터도 이 메커니즘을 쓰지 않으므로 **지금의 모든 화면 결과가 그대로**여야 한다.

| # | 추가 | 요지 |
|---|---|---|
| 1 | `basis` 필드 | `LEGACY_30D`(기본, 지금 동작) / `CALENDAR`(달력 기반). 미지정 = `LEGACY_30D` |
| 2 | `AGE_CALENDAR_WINDOW` 트리거 | `{years, months}`로 쓰는 달력 기반 연령 창 |
| 3 | `SCHOOL_TERM_WINDOW` 트리거 | 입학 학년도 기준 달력 기간 창 |
| 4 | `requiredValues` | `eligibilityCondition`의 "A 또는 B" 비교 |
| 5 | `timeline` 입력 | 엔진이 `ChildTimeline` 결과를 입력으로 받음 |

**비목표(A5에서 하지 않음)**
- 기존 Todo의 `basis`를 `CALENDAR`로 바꾸는 것 — **항목별 승인 + 전후 날짜 차이표 + 골든 스냅샷**이 필요한 별도 작업(Q-G 조건).
- 새 Todo 콘텐츠·정책 데이터 작성(A6, 정책값은 공식 확인 선행), 36개월 상한 해제, 화면 문구/UI 변경, 온보딩의 `profile.care` 입력.
- `app.js`·`index.html` 변경(스크립트 로드 순서는 이미 `date-calc → child-timeline → todo-engine`), Firestore 규칙.

## 2. 현재 사실 (코드·데이터 확인)

- `todo-engine.js` 순수 UMD. `MONTH_DAYS = 30`; `computeWindow`는 `AGE_WINDOW`에서 `addMonths(birth, startMonth/endMonth)` = `birth + n×30일`(분수 월령 허용). `DATE_FROM_BIRTH`·`RELATIVE_TO_EVENT`는 일수 기반. 반복형(`firstSeasonRule`, `intervalMonths`)도 `×MONTH_DAYS`.
- **정의 개수 구분**: `data/todos/*.json`의 정의는 **66건**이고(`AGE_WINDOW` 50, `MILESTONE_EVENT` 5, `REFERENCE` 1, `RELATIVE_TO_EVENT` 1, occurrences/variants 보유 9), 앱이 실제로 엔진에 넣는 정의는 여기에 전국 지원금 `data/subsidies/national-todos.json` 12건(SB-*)을 합친 **78건**이다(`schedule.js`·테스트가 읽는 대상). 아래 "기존 정의"는 78건을 뜻한다.
- **`basis`와 `requiredValues`·새 트리거를 쓰는 정의는 0건.** `eligibilityCondition`은 **전국 지원금 5건(SB-05~SB-09)이 가지고 있고 모두 단일 `requiredValue` 형식**이다(예: `incomeBracket`, `prematureBirth`, `daycareEnrolled`). `schedule.js`가 `familyDeclaredAttributes: {}`를 넘기므로 지금은 모두 선언값이 없어 기존과 동일하게 `UNKNOWN`(status null)으로 처리되어 화면에서 제외된다. 새 `requiredValues` 코드는 이 5건이 지나는 분기와 같은 곳에 있어 단일 `requiredValue`의 통과·제외·UNKNOWN 판정이 이전과 같음을 전용 테스트로 고정한다. 메커니즘을 추가해도 데이터가 새 필드를 쓰지 않는다.
- **분수 월령 5곳**: `HC-01`(0.47, 1.17), `SL-02`(1.5), `VX-ROTA/dose-1`(endMonth 3.5, 2회 표기). `DateCalc.addMonthsClamped`는 정수 월만 받고 비정수는 `RangeError` → 이 값들은 `CALENDAR`로 표현할 수 없다(일수 단위 정의라 `LEGACY_30D`로 남겨야 함).
- `schedule.js buildTodoEngineEvents`: `familyDeclaredAttributes: {}`(항상 빈 값), `status === null`인 인스턴스는 화면에서 **제외**, `windowStart === null`(마일스톤 대기 제외)도 제외. → 엔진이 "판단 불가"를 `status:null`로 돌려주면 UI에는 자동으로 안 나온다(기존 `eligibility: "UNKNOWN"` 경로).
- `ChildTimeline`(72줄): `completedMonths`, `ageLabel`, `compute()`(school은 항상 `null`), `SERVICE_RANGE{maxMonths:36, pickerYearsBack:11}`. `DateCalc`: `addMonthsClamped`, `assertMonthCount`, `lastDayOfMonth`(`addYearsClamped`는 아직 없음).
- 기존 테스트: `todo-engine.test.js` 40개가 `LEGACY_30D` 동작을 고정.

## 3. 변경 설계

### 3-1. `basis` (`LEGACY_30D` | `CALENDAR`)
- 위치: Todo 정의 최상위 `basis`(occurrence 단위 덮어쓰기는 만들지 않음). 미지정·알 수 없는 값 → `LEGACY_30D`로 취급하지 않고 **알 수 없는 값은 계산을 거부(정의 오류)**: 오타가 조용히 옛 동작으로 가는 것을 막기 위해 테스트에서 검출.
- 적용 범위(추천): **`AGE_WINDOW`의 `startMonth`/`endMonth`만**. `CALENDAR`이면 `DateCalc.addMonthsClamped(birth, n)`(정수 월 필수). 다른 계산(`DATE_FROM_BIRTH` 일수, `RELATIVE_TO_EVENT` 일수, 반복 `intervalMonths×30`)은 A5 범위 밖(필요하면 별도 설계).
- `CALENDAR`인데 월 값이 비정수면 **정의 오류**(데이터 가드 테스트로 검출; 런타임에서는 해당 항목만 건너뛰고 `console.warn`, 앱 전체는 중단되지 않음 — I-4의 A안과 같은 방식).
- 엔진 의존성: `DateCalc`를 `calendar-model.js`처럼 `factory(getDateCalc)`로 주입(Node는 `require("./date-calc.js")`, 브라우저는 전역). 로드 순서는 이미 맞음.

### 3-2. `AGE_CALENDAR_WINDOW`
- 파라미터: `{ start: {years, months}, end: {years, months} | null }` — 모두 0 이상 정수.
- 계산: `windowStart = addMonthsClamped(birth, start.years×12 + start.months)`, `windowEnd`는 `end`가 null이면 null, 아니면 같은 방식. 의미와 반환 형태는 `AGE_WINDOW`+`CALENDAR`와 동일(상태 계산·`leadDays`·`catchUp` 재사용).
- ⚠ **중복 인정**: 정수 월에서는 `AGE_WINDOW`+`CALENDAR`와 결과가 같다. 차이는 "만 N세"를 연 단위로 읽기 쉽게 쓰는 입력 형식뿐이다. Q-G에서 승인된 항목이므로 **구현은 하되 얇은 별칭**으로 둔다(두 번째 계산 경로를 만들지 않음). → 결정 D-A5-1.

### 3-3. `SCHOOL_TERM_WINDOW`
- 파라미터(안): `{ anchor: "ENROLLMENT", yearOffset, startMonth, endMonth }` — 입학 학년도(`timeline.school.enrollmentYear`) + `yearOffset`년의 `startMonth`월 1일 ~ `endMonth`월 말일(학년도 3월 시작 가정은 정책값이라 코드에 없음). 예: 입학 직전 학년도(`yearOffset:-1`) 9~12월.
- 입력 필요: `ctx.timeline.school`. **`timeline`이 없거나 `school === null`(정책 미제공·`확인필요`)이면** 판단 불가로 `status:null` + `eligibility:"UNKNOWN"` 인스턴스를 돌려준다 → `schedule.js`가 이미 제외하므로 **화면에 확정 문구로 나오지 않는다**(§13-8 규칙).
- `enrollmentYear` 산정은 `ChildTimeline`이 `policy`(주입)로 계산한다(3-5). 정책값 자체(입학 학년도 산정 오프셋·학년도 경계)는 **A5에서 데이터로 만들지 않는다.** 테스트는 테스트용 정책 픽스처(가정값 명시, 검증 상태 `테스트 전용`)로만 수행.

### 3-4. `requiredValues`
- `eligibilityCondition: { attribute, requiredValue }`(단일, 기존) 또는 `{ attribute, requiredValues: [..] }`(신규). 통과 조건: 선언값이 목록에 포함. 미선언(undefined)은 기존처럼 `UNKNOWN`, 불일치는 `FAIL`(목록에서 제외).
- 둘 다 있으면 정의 오류. `requiredValues`가 빈 배열이면 정의 오류.
- 소비자: 지금은 `familyDeclaredAttributes`가 항상 `{}`라 아무 효과가 없다. `profile.care`(온보딩 칩, 미구현)가 생기기 전까지는 **메커니즘만** 존재.

### 3-5. `timeline` 입력과 `ChildTimeline` 확장
- `calculateTodoInstances(input)`에 **선택 필드** `input.timeline`을 추가(`ctx.timeline`으로 전달). 없으면 지금과 동일하게 동작.
- `schedule.js buildTodoEngineEvents`: 호출에 `timeline`을 한 줄 추가(`ChildTimeline.compute(...)`)할지는 **결정 D-A5-6**. 추천: A5에서는 `policy`를 주지 않으므로 `school:null`인 timeline을 넘기거나 아예 넘기지 않아 동작은 같다. 소비자 연결은 A6(실제 학교 항목이 생길 때)로 미루는 것도 가능.
- `ChildTimeline.compute({birthDate, asOf, stage, policy?})`에 `policy`가 있을 때만 `school{enrollmentYear, schoolYear, grade, stageBand, ...}`를 계산하는 순수 함수 추가. `grade`는 `"PRESCHOOL" | 1..6 | "AFTER_ELEMENTARY"`이고 `stageBand`는 설계 §13-3의 5종(`INFANT_TODDLER`·`PRESCHOOL`·`PRE_ELEMENTARY`·`ELEMENTARY_LOW`·`ELEMENTARY_HIGH`)만 쓴다 — **`grade === "AFTER_ELEMENTARY"`(초6 이후, 서비스 범위 밖)이면 `stageBand`는 `null`**(졸업 후 판정은 `grade`로 한다). 정책 입력 형식은 `{value, verificationStatus, source}`(§13-8); `verificationStatus !== "확인됨"`이면 `school:null`.

## 4. 기존 결과 불변 보장 (절대 조건)
1. **데이터 무사용**: 정의 78건(data/todos 66 + 전국 지원금 12) 모두 `basis`·`requiredValues`·새 트리거를 쓰지 않음을 정적 테스트로 고정한다. `eligibilityCondition`은 SB-05~SB-09 5건만 가지며 모두 단일 `requiredValue` 형식임도 고정 → 새 코드 경로는 실행되지 않고, 겹치는 `eligibilityCondition` 분기는 기존 판정과 같음을 별도 테스트로 확인한다.
2. **동결 스냅샷(V2)**: 변경 전·후 `calculateTodoInstances` 결과(모든 항목의 `windowStart/End`·`status`)를 프로필 3종(은찬 2026-06-20, 36개월, 말일생) × 기준일 격자로 비교 — 차이 0.
3. `todo-engine.test.js` 40개 무수정 통과, `auto-diff`(기준 `4bee41d`) 차이 0, T3/T4 메타모픽 통과.
4. 신규 코드는 *새로 조건이 걸린 경우에만* 진입(미지정 `basis` → 옛 코드 줄 그대로).
5. 플래그 OFF·가구 기능 영향 없음(엔진 입력만 변경).

## 6. 위험과 대응
- **R1 조용한 변경**: 새 분기가 기존 항목을 건드림 → 4번의 정적·스냅샷 테스트가 막는다.
- **R2 분수 월령**: `CALENDAR` 전환 시 5곳은 표현 불가 → 전환 대상에서 제외, 데이터 가드 테스트로 `CALENDAR`+비정수 조합을 차단.
- **R3 정책 가정값의 누출**: 입학 오프셋·3월 시작은 가정 → A5는 값을 코드/데이터에 넣지 않고 주입·테스트 픽스처로만 사용.
- **R4 `UNKNOWN`이 화면에 새어 나옴**: `status:null`은 `schedule.js`가 이미 제외 — 새 트리거도 같은 경로 사용, 테스트로 확인.
- **R5 엔진 순수성**: `DateCalc` 주입으로 DOM·시계 의존 없음 유지.
