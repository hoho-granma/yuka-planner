# 레거시 데이터 마이그레이션 계획 (v1 → v2)

작성일: 2026-09-28
전제: `js/sync-v2.js`에 구현한 `migrateLegacyFamilyIfNeeded()`가 이 계획을 코드로 옮긴 것이다. **이 함수는 아직 어디서도 호출되지 않는다** — 지금은 계획과 코드만 준비하고, 실제 실행은 app.js를 v2로 전환하는 다음 단계에서 한다.

## 왜 필요한가

기존 서비스는 `families/{code}` 문서 하나에 `{ profile, completed }`를 통째로 저장한다(v1). 이 서비스가 이미 배포되어 있고 실제로 가족코드를 발급받아 쓰고 있는 사용자가 있을 수 있으므로(정확한 사용자 수는 이 리포만으로 알 수 없음), v2 구조로 전환할 때 **그 데이터를 지우거나 방치하면 안 된다.**

## 전략: 지연 마이그레이션(lazy migration), 원본 보존

1. **자동 일괄 이관은 하지 않는다.** 몇 명이 쓰고 있는지, 서비스가 몇 대의 기기에서 열려 있는지 이 리포만으로는 알 수 없어서, 한 번에 전체를 변환하는 스크립트는 예상치 못한 상태(예: 동시에 데이터를 쓰고 있는 기기)와 충돌할 위험이 있다.
2. **대신, 가족코드가 입력되는 시점(`FamilySync.fetchFamily(code)`를 부르던 바로 그 지점)에 `migrateLegacyFamilyIfNeeded(code)`를 먼저 호출**하도록 다음 단계에서 `app.js`를 바꾼다. 이 함수는:
   - `families/{code}` 문서가 있고, `profile` 필드가 있고(=v1 형태), `archived`가 아니면 → v2 구조(`families/{autoId}` + `children` + `completions`)를 새로 만들고, 원본 문서에 `archived: true`, `migratedTo: <새 familyId>`만 표시한다. **원본은 삭제하지 않는다.**
   - 이미 `archived`거나 애초에 v1 형태가 아니면(=이미 v2 문서이거나 없는 코드) → 아무것도 하지 않고 `null`을 반환한다.
3. **이관 후 사용자에게 보여줄 코드가 바뀐다** — v1 코드(예: `A3F9K2`)로 접속했던 사용자는 이관 시점에 **새 코드**를 발급받는다(v2에서는 코드가 `families` 문서 ID가 아니라 `familyCodes` 컬렉션의 독립 문서이기 때문). 이 부분은 UI 변경이 필요하므로(다음 단계 범위) 지금은 함수가 `{ oldCode, newCode, familyId, childId }`를 반환하도록만 만들어두고, "새 코드를 사용자에게 보여주고 다시 저장하게 하는 처리"는 다음 단계에서 구현한다.

## 레거시 일정 ID ↔ v2 todo_id 매핑 문제 (미해결, 다음 단계 과제)

v1의 `completed` 맵은 `{ [일정id]: true }` 형태이고, 이 일정 ID는 `js/schedule.js`가 런타임에 만드는 ID(예: `H3`, `V-DTAP-2` 등 추정 — 정확한 규칙은 `schedule.js` 재확인 필요)다. v2의 `todo_id`(예: `HC-03`, `VX-DTAP`)와 **1:1로 맞는다는 보장이 아직 없다.** 지금 단계에서는:

- `planLegacyMigration()`이 레거시 ID를 **그대로** 새 `completions` 문서의 `todo_id`로 옮겨 적는다(변환 없이).
- 이 매핑표를 정확히 만드는 일은 **Todo 계산 엔진을 실제로 새 데이터모델로 전환하는 다음 단계**에서, 옛 `schedule.js`가 생성하던 ID 목록과 새 `data/*.json`의 `todo_id`를 나란히 놓고 확정한다(이번 단계 범위 밖 — 아직 Todo 엔진을 건드리지 않기로 했으므로).
- 따라서 **v1 완료 기록이 v2로 옮겨지긴 하지만, 엔진 전환 전까지는 그 기록이 새 화면에서 정확히 "어떤 Todo가 완료됐다"로 매핑되어 보이지는 않는다.** 이관 자체(데이터 보존)와 매핑 정합성(다음 단계)을 분리해서 처리한다.

## 실행하지 않은 것 (의도적)

- 이번 세션에서 `migrateLegacyFamilyIfNeeded()`를 실제 프로덕션 Firestore에 대해 실행하지 않았다 — 호출하는 코드가 아직 없고, 이 환경에는 Firebase CLI/인증정보가 없어 라이브 프로젝트에 직접 접속해 테스트할 수도 없다(아래 테스트 결과 참고).
- 기존 v1 문서를 삭제하거나 구조를 바꾸는 어떤 작업도 하지 않았다.
