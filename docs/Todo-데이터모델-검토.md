작성일: 2026-09-28

## 1. 3층 구조(TodoDefinition/CompletionRecord/TodoInstance) 검증

요청하신 9개 상황을 하나씩 대조했다.

| 상황 | 표현 가능? | 근거 |
|---|---|---|
| 한 번만 해야 하는 Todo | ✅ | `occurrenceKey="default"` |
| 매월/반복 Todo | ⚠️ **부분적** | `repeat` 필드는 있으나, "다음 회차 기준일"이 정의돼 있지 않다 — 아래 참고 |
| 여러 회차 예방접종 | ✅ (대부분) | `occurrenceKey="dose-N"` + 독립 AGE_WINDOW 또는 RELATIVE_TO_EVENT |
| 특정 이벤트 이후 발생 | ⚠️ **부분적 결함** | `CONDITION` triggerType은 있으나 "이벤트 보고"와 "완료 처리"가 같은 `CompletionRecord`에 뭉쳐있음 — 2번·4번에서 상술 |
| 기한이 있는 Todo | ✅ | windowEnd |
| 기한 지나도 따라잡기 가능 | ✅ | `catchUp: ALLOWED` |
| 기한 지나면 일반 완료 불가 | ✅ | `catchUp: NOT_ALLOWED` |
| 조건 충족돼야 시작 | ⚠️ **결함** | 발달마일스톤형 조건과 자격속성형 조건이 같은 구조로 뭉쳐있음 — 3번에서 상술 |
| 지역에 따라 달라지는 Todo | ⚠️ **부분적 결함** | "자격이 달라지는 것"(`regionCondition`)만 있고 "**금액이** 달라지는 것"(아동수당)을 표현할 필드가 없음 |

**결론: 3층 분리 자체는 옳다.** 문제는 층 구조가 아니라 `CONDITION`이라는 한 개념 안에 서로 다른 두 가지가 섞여 들어간 것과, 반복/지역 필드의 정의가 끝까지 안 내려간 것이다. 아래에서 구체화한다.

**반복 Todo의 "기준일" 결함**: `repeat.type: "interval"`(예: OR-04 정기치과검진 6개월 간격)일 때, 다음 회차의 windowStart가 "생년월일 기준 고정 월령"인지 "직전 완료일 + 6개월"인지 설계서에 명시돼 있지 않다. 의료/치과 검진은 후자가 맞다(아이가 검진을 늦게 받으면 다음 검진도 그만큼 밀린다). → **`repeat.type: "interval"`은 내부적으로 `RELATIVE_TO_EVENT(referenceEvent: "previous_occurrence_completion")`로 계산해야 한다고 명문화가 필요**(새 필드 추가가 아니라 기존 트리거 타입의 용례를 반복 Todo에도 적용하는 문서 수정 수준).

## 2. 일본뇌염 재검토

### 왜 "현재 구조로 표현 불가능"이라고 했는가 (재확인)

일본뇌염은 **(a) 제품(사백신/생백신) 선택에 따라 전체 회차 수·스케줄 자체가 갈라지고, (b) 그 안에서 회차 간 간격이 절대월령이 아니라 상대오프셋(1차→2차 7일, 2차→3차 12개월)**이라는 두 가지가 겹친다. `triggerParams`는 Todo 1개당 1개의 트리거만 담는 구조라, "제품별로 완전히 다른 회차 목록"을 하나의 `triggerType`+`triggerParams`로 표현할 수 없었다.

### 모델 자체의 문제인가, 일본뇌염만의 문제인가

**모델 자체의 문제다.** 재검토 결과, 이미 "조건 로직 추가 필요"로 분류했던 **로타바이러스도 똑같은 패턴**이다 — 로타릭스(2가)는 2회, 로타텍(5가)은 3회로 **제품 선택이 회차 구성 자체를 바꾼다.** 단지 로타는 상대오프셋이 없어서(둘 다 절대월령 2·4·(6)개월) 임시로 "조건부 파라미터 하나"로 뭉개고 넘어갈 수 있었을 뿐, 근본적으로는 일본뇌염과 같은 구조적 요구다. 즉 이 문제는 **"제품 선택에 따라 Todo의 회차 구성 자체가 달라지는 다회차 접종"이라는 하나의 일반 패턴**이며, 지금까지 두 백신에서 각기 다르게(하나는 임시방편, 하나는 포기) 처리한 것이 오류였다.

### 일반화된 해결 구조 (하드코딩 대신)

`TodoDefinition`에 `variants` 필드를 하나 추가한다 — **일본뇌염 전용이 아니라, 제품 분기가 있는 모든 다회차 접종에 재사용 가능**:

```
TodoDefinition.variants: {
  [productType: string]: { doses: [ { doseNumber, trigger: (AGE_WINDOW|RELATIVE_TO_EVENT) } ] }
} | null   // null이면 지금처럼 단일 스케줄(대부분의 백신)
```

부모가 접종 시작 시 제품을 1회 선택하면(그 선택 자체는 `CompletionRecord`가 아니라 "이 Todo에 대한 선택값"으로 별도 저장— 완료 기록이 아니므로 혼동하지 않도록 분리), 이후 회차는 선택된 `variants[productType].doses`를 그대로 따른다.

→ **73개 중 "표현 불가능"은 0건이 된다.** 로타·일본뇌염 둘 다 `variants` 필드 하나로 "필드 수정 필요" 등급으로 내려간다. 새로운 상태값이나 새로운 트리거 타입은 필요 없다 — 기존 AGE_WINDOW/RELATIVE_TO_EVENT를 variants 아래에 재배치하는 것뿐이다.

## 3. 상태값 검토

요청하신 7개 상황과 최종 상태값을 대조했다.

| 요청 상황 | 대응 상태 | 구분됨? |
|---|---|---|
| 아직 시작 전 | `SCHEDULED` | ✅ |
| 지금 할 시기 | `DUE` | ✅ |
| 완료 | `DONE` | ✅ |
| 아직 미완료 | `DUE`의 다른 표현(기간 내 미완료)으로 흡수 | ✅ (중복 상태를 만들지 않은 것은 적절) |
| 기한 초과 | `OVERDUE_CATCHUP` / `OVERDUE_FINAL` | ✅ (오히려 요청보다 세분화되어 있어 더 낫다) |
| 조건을 기다리는 상태 | `PENDING_CONDITION` | ✅ |
| 해당 없음 | 상태화하지 않고 **아예 목록에서 제외** | ⚠️ **여기가 진짜 구멍** |

**"확인 필요"를 상태가 아니라 배지로 처리한 판단**: 적절하다. `verificationStatus`는 시간에 따라 변하는 값이 아니라 "이 Todo 정의 자체가 얼마나 신뢰할 만한가"를 나타내므로, `DUE`이면서 동시에 "확인 필요"일 수 있다는 설계가 맞다. 상태와 배지를 분리한 것은 유지한다.

**"해당 없음"의 구멍**: 현재 모델은 "해당 없음"을 **지역/성별 필터에서만** 처리한다. 그런데 실제 15개 조건부 Todo 중 6개(SB-05 기저귀바우처, SB-06 미숙아의료비, SB-07/08 보육료·누리과정, SB-09 아이돌봄, CR-02 반편성확인)는 **소득구간·미숙아여부·어린이집이용여부** 같은, **생년월일·성별·지역 4개 입력값에 없는 속성**에 좌우된다. 지금 모델에는 이런 속성을 저장할 자리가 없다 — `CONDITION` triggerType은 "발달 마일스톤 이벤트"(첫니가 남, 기어다니기 시작함)만 상정하고 있어서, "우리 아이는 저소득 가구다"처럼 **시간과 무관한 참/거짓 속성**과 섞여 쓰이고 있다. 이 둘은 근본적으로 다르다:

- **마일스톤 이벤트형** (SF-02~05, OR-01, DV-09 = 6개): "무언가 일어났다"는 **사건**이고, 그 시점이 Todo의 시작 시점(windowStart)이 된다.
- **자격속성형** (SB-05/06/07/08/09, CR-02 = 6개): "우리 아이는 이런 상황이다"는 **속성**이고, 시작 시점과 무관하게 그 Todo가 이 아이에게 "해당되는지 아닌지"만 결정한다 — `regionCondition`/`genderCondition`과 같은 **필터**에 가깝다.

**결론: `CONDITION` triggerType 하나에 두 가지 다른 개념이 섞여 있다.** 이걸 분리해야 한다(아래 최종 판정의 수정 1번).

## 4. "놓친 Todo" 검토 — 가장 중요한 질문

> "이 아이가 지금까지 해야 했지만 아직 완료하지 않은 것은 무엇인가?"

**대부분의 경우 정확히 답할 수 있다.** 검증한 흐름:

- **AGE_WINDOW/DATE_FROM_BIRTH 기반 Todo**: windowEnd < 오늘 이고 완료기록 없음 → `catchUp` 값에 따라 `OVERDUE_CATCHUP`/`OVERDUE_FINAL`로 정확히 분류된다.
- **RELATIVE_TO_EVENT 기반 Todo(예: A형간염 2차)가 직전 회차 미완료라 windowEnd를 계산 못하는 경우**: 이 경우도 실제로는 문제가 안 된다 — **직전 회차(1차) 자체가 독립적인 AGE_WINDOW를 가지고 있어서, 1차가 이미 그 자체로 `OVERDUE_*` 상태로 잡히기 때문**이다. "2차가 안 잡힌다"가 아니라 "1차 미완료가 이미 놓친 것으로 잡히고, 2차는 자연스럽게 그 뒤를 따라간다." 사슬이 끊기지 않는다. **이 부분은 모델이 잘 설계됐다.**
- **CONDITION(마일스톤 이벤트)형 Todo가 이벤트 미보고 상태로 남는 경우**: 여기가 유일한 맹점이다. 부모가 "기어다니기 시작했어요"를 보고하지 않으면 해당 Todo는 영원히 `PENDING_CONDITION`에 머물고 절대 "놓친 것"으로 잡히지 않는다. 예를 들어 15개월 아이인데 안전장치 Todo가 계속 `PENDING_CONDITION`이면, 실제로는 이미 오래전에 걷기 시작했을 가능성이 높은데도 서비스는 이를 "놓친 것"으로 인지하지 못한다. → **이건 지금 단계에서 반드시 고칠 결함이 아니라 알려진 한계로 남겨도 된다** (마일스톤 자기보고형 Todo 자체가 원래 "정확한 시점"이 없는 관찰형이라, 억지로 "놓침"을 계산하면 오히려 부정확한 재촉 알림이 된다 — 과설계 방지 원칙과도 맞다). 다만 문서에 한계로 명시는 해둔다.
- **자격속성형(위 3번에서 발견한 것)이 필터로 안 걸러지면**: 소득조건이 있는 SB-05/06 등을 모든 부모에게 "지금 해야 함"으로 잘못 노출할 위험이 있다 — 이건 "놓친 Todo" 계산 자체의 오류라기보다 **애초에 이 Todo가 이 아이에게 해당되는지부터 잘못 판단하는 상위 단계의 문제**다(3번 결함의 연장선).

**결론: 핵심 질문("놓친 것 찾기")에 대한 답 자체는 모델이 정확하다.** 문제는 두 개의 다른 층위 — (a) CONDITION 개념 분리 필요, (b) 마일스톤 미보고 한계는 인지만 하고 넘어감 — 로 이미 위에서 다룬 것과 같다.

## 5. 73개 매핑 결과 재검토

2번(일본뇌염/로타 일반화)의 결과를 반영하면 분류가 바뀐다.

| 구분 | 기존 개수 | 재검토 후 개수 | 변경 사유 |
|---|---:|---:|---|
| 그대로 매핑 가능 | 50 | 50 | 변화 없음 |
| 필드 수정 필요 | 7 | **9** | 로타·일본뇌염이 `variants` 필드 추가로 해결 → 여기로 편입 |
| 조건 로직 추가 필요 | 15 | **13** | 로타·일본뇌염이 빠짐(2). 나머지 13개는 아래처럼 **명확히 2개 패턴**으로 묶인다 |
| 현재 구조로 표현 불가능 | 1 | **0** | 일본뇌염이 `variants` 구조로 해결됨 |

**"조건 로직 추가 필요" 13개가 사실상 같은 패턴으로 묶이는가?** — 그렇다, 정확히 **2개 패턴**으로 묶인다(3번에서 발견한 구분과 동일):

1. **마일스톤 이벤트 트리거 패턴** (6개): SF-02, SF-03, SF-04, SF-05, OR-01, DV-09 — 전부 "CompletionRecord에 이벤트 보고 날짜가 찍히면 그 날짜가 windowStart가 된다"는 동일한 로직.
2. **자격속성 필터 패턴** (7개): SB-05, SB-06, SB-07, SB-08, SB-09, CR-02, + VX-인플루엔자(최초 접종 시즌 2회 규칙은 "반복 Todo의 첫 회차 예외"라는 하위 패턴이라 이 그룹과는 다르지만 마찬가지로 "규칙이 하나 더 붙는" 유형) — "이 Todo가 이 아이에게 적용되는지"를 결정하는 참/거짓 속성 필터.

→ 지금까지 15개(→13개)를 개별적으로 다뤄야 할 것처럼 문서에 나열했지만, **실제로 새로 만들어야 할 로직은 2가지뿐**이다: (1) 이벤트 보고 → windowStart 계산, (2) 자격속성 필터. 각각을 한 번만 구현하면 13개 전부에 적용된다.

## 6. 과설계 여부

- **`genderCondition` 필드는 지금 제거하는 게 맞다.** 73개 중 실제로 값이 있는 항목이 0건이다. "있으면 좋은 필드"로 남겨뒀던 것 자체가 미래를 위한 선반영이라 이번 검토 기준(과도한 추상화 금지)에 어긋난다. 필요해지면 그때 컬럼을 추가하면 되고, 지금 스키마에 넣어봐야 항상 `null`인 필드가 하나 늘어날 뿐이다.
- **일본뇌염 전용 `VaccineSeries` 하드코딩안(이전 문서)은 기각하고 `variants` 필드로 대체한 것이 맞는 방향**이다 — 다만 이것도 "로타+일본뇌염 2건에만 쓰이는 필드"이므로 범용 "시리즈 엔진"으로 더 키우지 않는다(예: 조건 분기가 3단 이상인 경우까지 대비한 일반 규칙 엔진 등은 만들지 않는다). 지금 필요한 만큼(제품 2~3종 분기)만 지원하면 충분하다.
- **3층 구조(Definition/Instance/Completion) 자체는 과설계가 아니다** — 다회차·반복 Todo가 이미 실존하므로(백신만 12개), 완료기록을 최소한 `occurrenceKey` 단위로 쪼개는 것은 필수 최소 구조다.
- 반대로 부족한 곳(3·5번에서 발견한 자격속성 필터, 트리거 보고/완료 처리 분리)은 "과설계"가 아니라 "설계 누락"이었다 — 새로 추가해야 할 이유가 실제 15개 Todo의 요구사항에서 나온 것이지, 미래 대비용 확장이 아니다.

## 7. 최종 판정

**MODEL: CONDITIONAL GO**

아래 3가지만 수정하면 DB 스키마 설계로 넘어갈 수 있다.

1. **`CONDITION` triggerType을 두 개념으로 분리한다** — (a) 마일스톤 이벤트 트리거(기존 `CONDITION` 유지, 6개 Todo: SF-02~05/OR-01/DV-09에 적용)와 (b) 자격속성 필터(`eligibilityFlag`라는 새 필드, `regionCondition`/`genderCondition`과 같은 층위의 "필터"로 취급, 7개 Todo: SB-05~09/CR-02/VX-인플루엔자에 적용). 이걸 안 나누면 "놓친 Todo" 계산에서 소득조건 같은 자격속성이 필터링되지 않고 잘못 노출될 위험이 있다(3·4번 검토 결과).
2. **`CompletionRecord`에 `recordType: "trigger_report" | "completion"` 필드를 추가한다** — 마일스톤 이벤트 "보고"와 실제 "완료 처리"가 지금 구조에서는 구분이 안 된다(1번 검토 결과). 위 (a) 6개 Todo에만 해당.
3. **`TodoDefinition.variants` 필드를 추가하고, 로타바이러스·일본뇌염 2건을 여기로 재분류한다** — "표현 불가능" 1건을 없애는 동시에 로타의 임시방편 처리도 정리된다(2번 검토 결과).

이 3가지는 전부 **기존 필드를 나누거나(1,2) 필드 하나를 추가(3)하는 수준**이라, 모델을 다시 짤 필요는 없다. 수정 후에는 DB 스키마 설계로 넘어가도 된다.

(참고: `repeat.type: "interval"`의 기준일 정의, SB-04 아동수당의 "지역별 금액 차등" 표현 방법, `genderCondition` 제거는 위 3가지만큼 시급하지 않지만 스키마 설계 단계에서 함께 반영하면 좋다.)
