# 가족코드 접근권한 점검·전환 설계

작성: 2026-10-08. **운영 점검 완료 / 서버·권한 규칙·화면 모듈 준비 / 운영 전환 전.**

## 1. 실제 운영 점검 결과

Firebase `yuka-planner`의 firebaserules API에서 현재 게시 규칙을 직접 읽었다. 운영 규칙과 작업 시점의 로컬 `firestore.rules`는 동일했다(diff 0줄). Firestore 데이터는 읽기 전용으로 확인했다.

| 항목 | 결과 |
|---|---:|
| 계정 | 6개 |
| 가족에 연결된 계정 | 5개 |
| 계정↔구성원 UID 불일치 | 0개 |
| 현재 구조의 가족 캘린더 | 4개 |
| 현재 구조의 아이 링크 | 4개 |
| 현재 구조의 아이 프로필 | 4개 |
| 예전 `families/{아이코드}` 프로필 | 4개 |

`families` 최상위 8개에는 현재 가족 루트 4개와 예전 아이 프로필 4개가 함께 있다. 계정 연결 상태가 정상이라는 것은 가족 구성원 승인이 검증됐다는 뜻이 아니다.

현재 가입 흐름은 코드를 확인한 뒤 구성원 목록을 읽고, 빈 구성원에 자기 UID를 연결하거나 새 구성원을 만든 뒤 계정에 가족 ID를 기록한다. 관리자 승인이 없다. 일정·할 일·성장기록은 구성원 확인이 있으나, 이 가입 흐름을 통해 코드 소지자가 구성원이 될 수 있다. 아이 프로필·가족 루트·구성원 목록·옛 경로에는 공개 읽기 허용이 남아 있다. 초대코드 생성·수정에도 관리자 판정이 없다.

기존 가족 루트에는 관리자·생성자 UID가 없다. 구성원 생성 순서, 엄마/아빠 관계, 아이 생성자 기록만으로 가족 관리자를 자동 확정하지 않는다.

원본 점검 자료와 식별자 포함 전환 계획은 `/private/tmp/hannun-access-audit/`에 보관했다. 개인정보·UID·코드·인증 토큰은 이 문서에 포함하지 않는다. 임시 자료는 장기 백업이 아니므로 실제 전환 직전에 다시 점검해야 한다.

## 2. 목표와 실제 동작

가족코드는 초대 요청용이다. 로그인한 계정이 코드를 입력해도 승인 전에는 아이·일정·상태·가족 구성원 정보를 볼 수 없다.

로그인 → 초대코드 입력 → 참여 요청 → 관리자 승인 → 가족 캘린더 접근.

- 관계(`MOM`, `DAD`, `CHILD` 등)와 권한(`ADMIN`, `MEMBER`)을 분리한다.
- 첫 관리자는 서버가 가족 생성자 UID로 지정한다. 아이 계정은 가족 생성·관리자 역할을 맡을 수 없다.
- 승인은 일반 구성원 권한만 부여한다. 관리자 이전은 별도 작업이다.
- 아이 계정은 관리자가 살아 있는 아이 링크에 연결해야 한다. 기존의 자기 아이 일정 편집 범위는 유지한다.
- 가족의 정보 읽기는 현재 가족 공유 범위를 유지한다. 아이별 읽기 제한이나 돌봄 담당자에게 일부 정보만 보이는 기능은 별도 설계 대상이다.
- 마지막 관리자 제거를 막는다. 먼저 다른 승인된 보호자에게 관리자를 이전해야 한다.
- 제외된 구성원의 새 서버 읽기·쓰기를 차단한다. 이미 내려받은 정보·캡처까지 회수할 수는 없다.

## 3. 권한 데이터

| 경로 | 목적 | 클라이언트 쓰기 |
|---|---|---|
| `familyAccess/{hid}/members/{uid}` | 승인 상태·권한·관계·구성원 ID·아이 링크 ID | 금지 |
| `childAccess/{아이코드}` | 아이 프로필→가족 ID·기존 아이 링크 ID 연결 | 금지 |
| `privateFamilyInvites/{코드 SHA-256}` | 만료·취소·사용 상태·발급자·초대 관계 | 금지 |
| `familyJoinRequests/{uid}` | 계정별 참여 요청과 처리 상태 | 금지 |
| `familyRateLimits/{해시}` | 계정·IP별 코드 시도 제한 | 금지 |
| `accounts/{uid}` | 기존 프로필과 가족 연결 포인터 | 가족·구성원·권한 필드 수정 금지 |

권한 판정은 서버가 작성한 `familyAccess`를 근거로 한다. 클라이언트가 계정의 가족 ID나 표시용 구성원 문서를 조작해도 접근 권한이 생기지 않는다. 기존 아이 링크 ID는 아이코드와 다르므로 `childAccess.childKey`에 실제 링크 ID를 보존한다.

기존 구성원 이름·색·순서는 유지한다. 새 표시용 구성원을 만드는 기능은 승인된 보호자에게 유지하되, 그 문서에는 로그인 UID를 직접 붙일 수 없다.

## 4. 서버 기능과 초대 정책

`functions/family-access.js`에 트랜잭션 기반 서버 로직, `functions/index.js`에 Firebase Callable 진입점을 준비했다.

- 가족 생성, 초대 발급·취소, 참여 요청·상태 확인·취소, 요청 목록·승인·거절, 관리자 이전, 구성원 제외, 새 아이 등록·분리.
- 인증 UID는 클라이언트 입력이 아닌 Firebase 인증 컨텍스트에서 가져온다.
- 사용자 요청에 따라 개발·테스트에서 App Check를 적용하지 않는다. 서버 `APP_CHECK_ENFORCED=false`, 클라이언트 `appCheckEnabled:false`이며 App Check SDK·토큰·사이트 키 없이 호출한다. 배포 준비 단계에 두 설정을 함께 켠다. 로그인 인증과 승인 검증은 항상 유지한다.
- 8자리 코드는 암호학적 난수로 생성한다. 24시간 만료, 승인 완료 시 1회 사용 종료, 새 코드 발급 시 기존 코드 취소.
- 코드 입력은 10분에 계정별 10회·IP별 40회까지 허용한다. 틀린 코드도 횟수를 소비한다.
- 같은 초대의 동시 승인, 관리자 이전, 구성원 권한 변경을 트랜잭션으로 처리한다.
- 서버 응답은 승인 전 가족 ID·아이 정보·구성원 목록을 제공하지 않는다.
- 새 아이 등록은 프로필·가족 링크·권한 인덱스를 함께 만든다. 예전 아이코드만으로 다른 가족 기록을 가져오는 경로는 열지 않는다.
- 운영 전 `familyRateLimits.expiresAt`에 TTL 설정과 비용 알림을 준비해야 한다.

기술 근거: [Firebase Callable](https://firebase.google.com/docs/functions/callable), [App Check 강제 적용](https://firebase.google.com/docs/app-check/cloud-functions), [Firestore 중첩 규칙](https://firebase.google.com/docs/firestore/security/rules-structure).

## 5. 준비한 파일과 적용 상태

| 파일 | 상태 |
|---|---|
| `functions/` | 서버 모듈·SDK 의존성·잠금 파일 준비, 미배포 |

| `security/storage.approval.rules` | 동일 승인 기록을 쓰는 이미지 접근권한 후보, Storage 에뮬레이터 22개 검사 통과 |
| `js/family-access.js` | 앱 가입·복원·승인·아이 등록 경로 연결, 운영 활성화 플래그는 OFF |
| `js/family-access-view.js` | 승인 대기·관리자 요청 처리·초대·구성원 관리 화면 모듈 |

- 서버 로직·어댑터·화면 출력 15개, 앱 승인 복원 6개, OpenAI 메시지 분석 7개: 총 28개 통과. App Check SDK·사이트 키 없이 서버 호출하는 개발 모드도 검증했다.

- 테스트 개발 런타임은 Node 24이며 서버 배포 대상은 Node 22다. Node 22/Functions 에뮬레이터·Storage·실기기 검증은 운영 전환 전에 남아 있다.
- 운영 사용자 계정 생성/삭제, 운영 데이터 수정, 규칙·서버 배포, 커밋·push는 하지 않았다.

## 7. 남은 순서와 전환 조건

1. 사용자 확인: 모든 계정은 테스트 계정이다. 4개 가족의 연결 계정 5개를 승인 대상으로 잡고 가족별 최초 연결 보호자를 임시 관리자 후보로 정했다. 실제 운영 데이터 쓰기는 하지 않았다.
2. 현재 스냅샷 전환안은 권한 문서 9건을 새로 쓰며 기존 프로필·일정·색·아이 링크 ID를 보존한다. 미연결 아이 기록 1건은 삭제·임의 연결 없이 보존하고 접근권한을 부여하지 않는다. 이 테스트 전용 보존 정책이 명시된 전환안은 `ready:true`다. 새 스냅샷으로 배포 전 재검증해야 한다.
3. 코드 연결 완료: 기존 앱 가입·복원·초대·아이 등록을 새 서버로 연결했다. 기존 캘린더·아이 링크·반복 일정 ID를 유지한다. 복원은 만료되는 초대코드가 아닌 가족 ID와 승인 상태로 한다.
4. 코드 연결 완료: 승인 대기·거절·만료·권한 회수 화면을 연결했다. 권한 회수 때 구독을 끊고 캐시를 지우며, 미전송 변경은 다른 계정에서 접근하지 못하도록 격리한다. 네트워크 오류를 권한 회수로 오인해 데이터를 삭제하지 않는다.
5. App Check·결제/서버 운영 환경·Storage 권한 검증 완료. 실기기 UX 테스트를 완료한다. 브라우저 테스트는 프로젝트 고정 계정을 따른다. 익명/외부자 권한 검증은 분리된 에뮬레이터에서 한다.
6. 전환 직전 운영 규칙과 데이터 재점검, 백업, 원본 변경 없는 전환 쓰기 계획 검토. 다른 세션 변경과 충돌하지 않는지 확인한다.
7. 사용자 최종 배포 승인 후 서버·권한 데이터·앱·Firestore/Storage 규칙을 순서에 맞춰 전환하고, 구버전 코드 접근을 막는다. 규칙을 기존 파일 뒤에 덧붙이지 않고 공개 허용 블록을 제거한 최종 사본으로 배포한다.

배포 승인은 `AGENTS.md`의 **“Firestore 규칙 배포는 사용자 승인 사항이다.”**에 따른다. 운영 계정 전환·Storage·실기기 검증이 남아 있어 아직 배포 승인을 요청할 단계가 아니다.

## 8. OpenAI API 연결 및 개발 설정 (2026-10-08)

- 사용자 요청에 따라 App Check/reCAPTCHA Enterprise 설정은 배포 준비 단계로 보류한다. 앞서 요청한 사이트 키는 현재 개발에 필요하지 않다.
- 메시지 분석 서버는 OpenRouter 대신 OpenAI Chat Completions API를 직접 호출한다. 서버 Secret 이름은 `OPENAI_API_KEY`, 모델 설정은 `MESSAGE_PARSER_MODEL`(개발 기본 `gpt-4o-mini`)이다. 키는 브라우저에 넣지 않는다.
- 승인된 성인 ADMIN/MEMBER만 분석할 수 있다. 승인 대기·권한 회수·보기 전용·아이 계정은 외부 API 호출 전에 거부한다. 계정별 하루 20회 제한을 유지한다.
- Structured Outputs로 후보를 받고, 원문 근거·날짜·시간을 서버에서 다시 검증한다. 결과는 사용자 확인 후보로 반환하며 자동 저장하지 않는다. 요청에 `store:false`를 사용하며 원문/응답 로그를 남기지 않는다.
- 모의 OpenAI 응답 검증은 완료했다. 실제 OpenAI 유료 API 호출은 하지 않았으며 서버 키 설정 후 실제 응답 검증이 남아 있다.
- 근거: [공식 OpenAI Structured Outputs 문서](https://developers.openai.com/api/docs/guides/structured-outputs).
- 로컬 `file:` 미리보기 열기가 자동 승인 검토에서 거절돼 화면 시각 검증은 완료하지 않았다.

## 9. 가족 승인 기능 적용 준비 (2026-10-08)

이번 적용 범위는 가족 생성·참여 요청·관리자 승인·초대 만료/취소/재발급·구성원 해제·권한 이전·Firestore/Storage 접근권한이다. OpenAI 기능과 App Check는 이번 배포 묶음에서 제외한다.

- 운영 규칙과 로컬 `firestore.rules` 재대조 결과 동일(차이 0). 계정 6개 중 기존 연결 계정 5개, 가족 4개, 아이 프로필 5개를 확인했다.
- 읽기 전용 전환 사전검증: 원본 문서 32개 일치, 신규 권한 문서 9개 생성 예정, 기존 데이터 삭제 0개, 미연결 아이 프로필 1개 보존. 원본 변경이나 대상 권한 문서 존재 시 실행을 차단한다.
