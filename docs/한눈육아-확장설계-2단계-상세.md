# 한눈육아 확장 설계 2단계 — 상세 설계

작성: 2026-09-30 · 작성 시점 기준: v1.12.5(`54d57f2`) · 선행 문서: `한눈육아-확장설계-v1.md`
작성 당시에는 설계만이었고 코드·데이터·규칙 파일은 바꾸지 않았다. §14의 결정은 사용자 답으로 확정되었고, 이후 **A0~A4와 B0~B5가 구현·검증·커밋되었다(2026-10-01 기준 v1.12.18). 진행 현황은 §15 끝의 "진행 현황"** 참고. 설계 내용 자체는 바뀌지 않았다.

## 0. 확정된 결정과 이번 문서의 범위

### 0-1. 사용자 확정 사항 (2026-09-30)

| # | 결정 | 이 문서의 반영 위치 |
|---|---|---|
| 1 | 다자녀는 새 `households` 문서로. 기존 아이 문서는 건드리지 않음 | §2, §7 |

| 3 | 날짜 없는 사용자 일정은 캘린더 점으로 표시하지 않고 "이 달 기간 일정" 별도 영역 | §5, §9 |
| 4 | 날짜는 문자열(`eventDate`·`startTime`·`endTime`), `displayDate`는 자동 일정의 화면 배치용으로만 — `assignDisplayDays()`는 그대로 | §5 |
| 5 | 36개월/30일 문제는 별도 트랙. 연령 계산을 **하나의 기준으로 통일**하고 학년(학령)을 구분하는 **연령/학년 엔진**을 따로 설계 | §13 |

용어: 이 문서에서는 사용자 표기를 따라 **`displayDate`**라고 쓴다. 코드에서의 실체는 `calDisplayDays`(`app.js:987`) = `assignDisplayDays()` 결과(`hn-logic.js:88`), 화면 문구는 "추천일"이다. **코드 이름은 바꾸지 않는다.**

### 0-2. 1단계 문서(v1)에서 바뀌는 것 — 먼저 밝힌다

이번 상세 설계를 하면서 v1의 설계를 **아래 6곳에서 수정**했다. 모두 이유가 있다.

| # | v1 | 2단계(이 문서) | 이유 |
|---|---|---|---|
| R1 | 아이 문서 `profile.householdCode`로 가구 연결 | **아이 문서에 가구 정보를 넣지 않는다.** 가구 → 아이 방향 링크만 | 보안. 아이 코드만 아는 사람(조부모·돌보미에게 아이 하나만 공유한 경우)이 가구 전체(다른 아이·일정)에 접근하게 되는 **권한 상승**을 막는다(§2-4) |
| R2 | 일정의 `childKeys`에 아이 코드 저장 | **`childKey`(가구 내 무작위 ID)** 저장, 코드는 링크 문서에만 | 일정 문서에 비밀 코드가 퍼지지 않고, 코드 재발급에도 일정이 안 깨진다 |
| R3 | 가구 문서 ID = 코드 | **`householdCodes/{코드}` → `householdId` 간접 참조**(v2 설계의 `familyCodes` 원리를 새 데이터에만 채택), 코드 8자리 | 가구 코드 하나가 아이 여러 명+일정의 마스터 키라 재발급이 가능해야 한다 |
| R4 | 담당자 `assignee: {role,label}` | `assigneeMemberId` → `members/{memberId}` | 사용자가 `members`를 명시(엄마·아빠·이모님 이름 변경, 삭제 처리) |
| R5 | USER 이벤트를 하나의 `events[]`에 섞고 `origin` 가드를 5곳에 추가 | **AUTO와 USER를 별도 배열로 분리**(`CalendarModel`), 가드는 2차 방어 | 기존 소비자(홈·체크리스트·혜택·기록·진행률)가 USER를 **받을 수 없게** 만들면 회귀 위험이 구조적으로 사라진다(§4) |
| R6 | `dateKind`: FIXED / PERIOD 2종 | FIXED에 **선택 `endDate`**(확정된 연속 기간: 방학·캠프) 추가 | "기간"에는 **날짜 미확정("10월 중")**과 **확정된 연속 일정("7/25~8/24 방학")** 두 종류가 있는데 v1과 사용자 정의(`periodStart/periodEnd` = 유효 기간) 모두 이를 구분하지 못한다(§5-2) |

또한 **새로 발견한 기존 버그**를 §13-1에 별도로 보고한다(말일생 월 계산 오류 — 지금 0~36개월 서비스에서 이미 발생).

## 1. 현재 데이터 구조 확정 — "동결 계약(Freeze Contract)"

> 새 기능이 지켜야 할 **불변 목록**이다. 여기 있는 모양은 어떤 단계에서도 바꾸지 않는다. **추가만** 허용한다.

### 1-1. Firestore (v1 문서, 실사용 중)

```text
families/{6자리코드}
 ├ profile    { name, birthDate:"YYYY-MM-DD", birthOrder|null, stage:"born"|"pregnant",
 │              province, district, photoDataUrl: string|null }
 ├ completed  { [eventId]: { done:true, todo_id, occurrenceKey, recordType, recordedAt:ISO, memo? } }
 │              eventId 종류:  "<todoId>__<occurrenceKey>"  |  "<지역혜택ID>" (예: SEOUL-001)
 │                             "<id>__milestone" (recordType MILESTONE_REPORTED)
 │                             "<id>__na"        (recordType NOT_APPLICABLE, 미해당)
 ├ records    { [recId]: { category, title, date:"YYYY-MM-DD", memo, authorLabel,
 │                         createdAt:ms, updatedAt:ms, deletedAt?:ms } }
 └ updatedAt  serverTimestamp
```

- 쓰기 방식: `profile` = `set(merge)`, `completed` = **맵 통째 교체(`update`)**, `records.<id>` = 필드 단위.
- 규칙: 문서 **최상위 키**만 allow-list(`profile, completed, records, updatedAt, archived, migratedTo, migratedAt`). `profile`·`records` 내부 키는 제한 없음.

### 1-2. localStorage

| 키 | 내용 |
|---|---|
| `yukjigi_profile` | 프로필(사진 포함, `birthDate`는 ISO) |
| `yukjigi_completed` | `completed` 사본 |
| `yukjigi_active_cats` | 체크리스트 카테고리 필터 |

| `hannun_author_label` | 이 기기의 작성자 표시명 |

### 1-3. 정적 데이터·런타임 계약
- `data/todos/*.json`(9카테고리) + `data/subsidies/**` — **이번 확장에서 스키마 불변**(§13의 새 필드도 전부 **선택**이며 없으면 현재 동작).
- 이벤트 모양(`schedule.js`): `id, category(6그룹), scheduleKind(fixed|window|monthly), fixedDate, windowStart, windowEnd, date, isEngineEvent, engineStatus, detail…` — **AUTO 이벤트의 모양은 불변.**
- `displayDate`(추천일) 알고리즘과 입력·출력 — **불변**.

### 1-4. 허용되는 추가 (이것만)

| 대상 | 추가 |

| 클라이언트 | 새 JS 파일(별도 모듈), 새 함수 |

### 1-5. 호환성 검증용 "골든 픽스처" (구현 1단계에서 확보)
현재 실사용 가족 문서 1건을 **개인정보 제거 후 export**(또는 고정 테스트 계정 `은찬·서울 구로구·2026-06-20`의 문서)해 테스트 픽스처로 고정한다. 모든 단계에서 "새 클라이언트가 이 문서를 읽고도, 사용자가 가구 기능을 쓰기 전에는 **한 바이트도 다르게 쓰지 않는다**"를 검증한다(§12 T1).

## 2. households 구조

### 2-1. 경로와 필드

```text
householdCodes/{CODE8}                    코드 → householdId 조회 전용 (재발급 가능)
   { householdId: string, active: boolean, createdAt: ms, revokedAt: ms|null }

households/{householdId}                  (문서 ID = Firestore 자동 ID)
   { v: 1, name?: string, createdAt: ms, updatedAt: ms }

  ├ children/{childKey}                   "이 가구에 속한 아이" 링크 — 프로필 복사본이 아니다
  │    { v:1, familyCode: string,         ← 기존 families/{코드}의 코드(자격증명)
  │      displayName: string,             ← 표시용 캐시(원본은 families/{코드}.profile.name)
  │      order: number, colorKey: string, addedAt: ms, removedAt?: ms }
  │
  ├ members/{memberId}                    담당자가 될 수 있는 사람들(계정 아님)
  │    { v:1, role:"MOM"|"DAD"|"GRANDPARENT"|"CAREGIVER"|"OTHER",
  │      label: string, order: number, createdAt: ms, updatedAt: ms, deletedAt?: ms }
  │
  └ schedules/{scheduleId}                § 3
```

### 2-2. 원칙
1. **기존 아이 문서(`families/{코드}`)는 이 구조의 어떤 동작으로도 쓰지 않는다**(§1 동결). 아이 정보의 **원본은 항상 아이 문서**이고, `children` 링크 문서의 `displayName`은 캐시일 뿐이다(불일치 시 아이 문서가 이긴다). → 사용자 확정안의 `households/children`을 **프로필 복사가 아닌 링크 목록**으로 해석했다(이중 진실 방지). 다른 해석이면 알려 달라.
2. `members`는 **로그인 계정이 아니다.** "누가 담당하는가"를 표시하는 라벨 목록이다(이 서비스에는 인증이 없다).
3. 일정 문서·`members`는 `childKey`/`memberId` **내부 ID만** 참조한다. 코드는 `children` 링크에만 있다(R2).

### 2-3. 생명주기

| 이벤트 | 동작 | 기존 데이터 영향 |
|---|---|---|
| **가구 생성**(지연) | 사용자가 "가족 캘린더 만들기"(또는 첫 사용자 일정·두 번째 아이 추가) 동의 시: `households` 생성 → `householdCodes` 코드 발급 → 현재 아이 `children` 링크 → 기본 `members`(엄마·아빠) 시드(이름은 즉시 수정 가능) → 화면에 **가구 코드 안내**("이 코드로 아이 전부와 일정을 볼 수 있어요") | 없음 |
| **새 기기 참여** | 가구 코드 입력 → `householdCodes` → `households` → `children` 목록 → 각 `familyCode`로 기존 `fetchFamily` 경로(무변경) | 없음 |
| **아이 추가** | 기존 "새 아이 추가"(새 `families` 문서 생성, 기존 코드 그대로) 후 활성 가구가 있으면 `children` 링크 자동 생성. 새 아이의 "몇째" 입력칸에 (아이 수+1)을 **제안만** 함(값을 채우지 않음) | 없음 |
| **아이 분리** | `children.removedAt` 표시(소프트). 아이 문서는 그대로 | 없음. 그 `childKey`를 참조하는 일정은 "(분리된 아이)"로 표시, 삭제하지 않음 |
| **가구 코드 재발급** | 새 `householdCodes` 문서 생성 + 이전 코드 `active:false` (v2 `familyCodes` 방식) | 없음 |
| **아이 코드 재발급** | 이번 범위 밖(현재도 불가). 링크 문서 `familyCode`만 갱신하면 되도록 구조는 열어 둠 | — |

### 2-4. 보안 경계 (R1의 근거)

```text
가구 코드  ──▶ 가구(아이 목록·일정·담당자) ──▶ 각 아이 코드 ──▶ 각 아이 문서
아이 코드  ──▶ 그 아이 문서만          (가구·다른 아이·일정으로 거슬러 올라가는 길이 없다)
```
- 아이 문서에 `householdId/householdCode`를 저장하면 아이 코드 보유자가 가구를 찾아갈 수 있다 → **저장하지 않는다.** "이 아이가 어느 가구인가"는 **이 기기의 localStorage**(`hannun_household_code`)와 가구의 `children` 링크에서만 안다.
- 결과: 가구 코드는 **마스터 키**다. 그래서 (a) 8자리(31^8 ≈ 8.5×10¹¹, 아이 코드 6자리는 ≈ 8.9×10⁸) (b) 재발급 가능(R3) (c) 안내 화면에 "가족에게만 공유"를 명시.
- 한계(기존과 동일, 숨기지 않는다): 인증이 없으므로 코드를 아는 사람 = 접근 권한자. 무차별 대입·문서 생성 남용은 규칙으로 못 막는다(App Check는 후순위, OCR 전 재검토).

## 3. schedules 구조 (사용자 일정 문서)

`households/{householdId}/schedules/{scheduleId}` — **USER 일정만 저장한다.** AUTO 일정은 저장하지 않는다(엔진 계산).

### 3-1. 필드

| 필드 | 타입 | 필수 | 설명·예시 |
|---|---|---|---|
| `v` | number | ✅ | `1` |
| `sourceType` | `MANUAL`\|`OCR`\|`VOICE`\|`IMPORT` | ✅ | 입력 출처 |
| `title` | string ≤100 | ✅ | `"피아노"` |
| `category` | `LESSON`\|`INSTITUTION`\|`MEDICAL`\|`FAMILY`\|`ETC` | ✅ | 학원·수업 / 어린이집·유치원·학교 / 병원·검진 / 가족 / 기타(표시 문구는 UX에서) |
| `tags` | string[] | 예약 | 예: `["CLOSED_DAY"]`(휴업일 — §8 공백 감지용). **이번엔 값만 저장 가능, 로직 없음** |
| `scope` | `CHILD`\|`FAMILY` | ✅ | |
| `childKeys` | string[] | scope=CHILD | `children` 링크 ID들(형제 공동 일정 가능) |
| `dateKind` | `FIXED`\|`PERIOD` | ✅ | FIXED = 날짜 확정 / PERIOD = **날짜 미확정** |
| `eventDate` | `"YYYY-MM-DD"`\|null | FIXED·비반복 | 실제 일정 날짜 |
| `endDate` | `"YYYY-MM-DD"`\|null | 선택 | FIXED가 **확정된 연속 기간**일 때 마지막 날(방학·캠프·1박2일) |
| `periodStart`/`periodEnd` | string\|null | PERIOD | 원본이 말한 미확정 기간(`"10월 중"` → 10/1~10/31) |
| `allDay` | boolean | ✅ | |
| `startTime`/`endTime` | `"HH:mm"`\|null | allDay=false | 실제 시각(로컬 벽시계) |
| `recurrence` | object\|null | 선택 | §6 |
| `exceptions` | map | 선택 | §6 |
| `assigneeMemberId` | string\|null | 선택 | `members` ID. null = 담당 미정 |
| `needsAssignee` | boolean | 예약 | 담당 미정 경고 대상 여부(기본값은 category로 UX가 결정). **필드만 예약** |
| `status` | `TODO`\|`DONE`\|`CANCELLED`\|`RESCHEDULED` | 비반복 | v1 UI는 `TODO`/`DONE`만 노출, 나머지는 **스키마에 미리 허용**(추후 마이그레이션 방지) |
| `location`, `memo` | string | 선택 | ≤100 / ≤500 |
| `provenance` | object\|null | OCR·VOICE·IMPORT | `{confirmedByUser:true, rawText?}` — **원본 이미지는 저장하지 않는다** |
| `createdAt`,`updatedAt` | ms | ✅ | |
| `deletedAt` | ms | | 소프트 삭제 |
| `authorLabel` | string | 선택 | 기록자 표시명(`HNRecords.authorLabel()` 재사용) |

명명 규칙은 기존 코드에 맞췄다(camelCase, 날짜 `YYYY-MM-DD` 문자열은 `records.date`와 동일, 시각 ms 숫자는 `records.updatedAt`과 동일, enum 대문자).

### 3-2. 불변식 (저장 전 검증 — 클라이언트 순수 함수 + Firestore 규칙 양쪽)

| # | 규칙 |
|---|---|
| I1 | `dateKind=FIXED`이고 `recurrence`가 없으면 `eventDate` 필수, `periodStart/End`는 null |
| I2 | `dateKind=PERIOD`이면 `eventDate`·`endDate`·`recurrence`는 null, `periodStart ≤ periodEnd` 필수 |
| I3 | `recurrence`가 있으면 `dateKind=FIXED`, `eventDate`는 null(반복의 시작은 `recurrence.startDate`), `periodStart/End`는 null |
| I4 | `endDate`가 있으면 `endDate ≥ eventDate`, `recurrence`와 함께 쓰지 않음 |
| I5 | `allDay=false`이면 `startTime` 필수, `endTime`이 있으면 `endTime > startTime`(자정 넘김은 v1 미지원) |
| I6 | `allDay=true`이면 시각 필드는 null |
| I7 | `scope=CHILD`이면 `childKeys` 1개 이상, `FAMILY`이면 비어 있음 |
| I8 | `sourceType ∈ {OCR, VOICE, IMPORT}`이면 `provenance.confirmedByUser === true` (확인 없이 저장 불가) |
| I9 | **원본에 없는 날짜 금지**: OCR/VOICE 후보는 원문에서 확인된 값만. 연도·요일이 없으면 필드를 비운 채 확인 화면에서 사용자가 채운다. 채우지 못하면 `PERIOD`로만 저장 가능 |
| I10 | `exceptions`의 키는 `YYYY-MM-DD`(점 `.` 불가), 최대 200개 |
| I11 | 날짜·시각 문자열은 **타임존 변환 없이** 그대로(Asia/Seoul 벽시계) |
| I12 | `displayDate`는 저장 문서에 **없다**(스키마에 필드 자체가 없음) |

## 4. 자동 일정 / 사용자 일정 분리

### 4-1. 핵심 설계 변경(R5): **한 배열에 섞지 않는다**

```text
[AUTO]  profile ─▶ TodoEngine ─▶ buildSchedule() ─▶ autoEvents[]  ─▶ (기존 소비자 전부: 홈·체크리스트·혜택·기록·진행률)
                                                   └▶ assignDisplayDays(autoEvents) ─▶ displayDate Map   (기존 그대로)
[USER]  households/.../schedules ─▶ validate ─▶ expand(범위) ─▶ userOccurrences[]
                                                                        │
                        autoEvents + displayDate Map + userOccurrences ─▼─ buildCalendarModel()  ─▶ 캘린더 화면 전용
```

- 기존 소비자(`visibleSchedule`, 홈, 체크리스트, 혜택, 기록, 진행률)는 **`autoEvents`만 받는다.** USER를 받을 방법이 없으므로 v1 문서가 우려한 회귀(6그룹 가정 TypeError, 추천일 오부여, 진행률 오염, 기록 orphan)가 **구조적으로 발생하지 않는다.**
- `origin` 필드는 **2차 방어**로 유지: USER 이벤트가 혹시 잘못 흘러들어도 각 함수가 무시하도록(`origin === "USER"` 제외) 가드를 심는다.
- 이 분리로 **메타모픽 테스트**가 가능해진다(§12 T4): "USER 일정을 아무리 추가·삭제해도 `autoEvents`와 `displayDate` Map은 바이트 단위로 동일하다."

### 4-2. 새 모듈(신규 파일, 기존 파일 무수정으로 시작)

| 모듈 | 책임 | 순수 함수(입출력만 명시) |
|---|---|---|
| `js/user-schedule.js` | 검증·정규화·반복 전개 | `validate(doc) → {ok, errors[]}` · `expandOccurrences(doc, rangeStart, rangeEnd) → Occurrence[]` · `normalizeFromCandidate(candidate, today) → {doc\|null, needsUserInput[]}` |
| `js/calendar-model.js` | 캘린더 화면용 집계 | `buildCalendarModel(input) → CalendarModel` (§9) |
| `js/household-sync.js` | 가구·일정 Firestore I/O·로컬 미러·재시도 | (§11) |
| `js/child-timeline.js` | 연령/학년 통합 계산 | (§13) |

### 4-3. Occurrence(런타임 표현)

```text
Occurrence {
  key:   "u:<scheduleId>@<YYYY-MM-DD>"        // 비반복도 동일 형식, 날짜=eventDate
  origin:"USER", sourceType, scheduleId, childKeys, scope, category, title,
  date:  "YYYY-MM-DD",                        // 이 회차가 화면에 놓이는 실제 날짜(예외로 옮겨졌으면 옮긴 날짜)
  originalDate:"YYYY-MM-DD",                  // 반복 규칙상 원래 날짜(예외 키)
  endDate?, allDay, startTime, endTime, assigneeMemberId, status, isMoved?, memo, location
}
```
`key` 공간(`u:…`)은 `completed`의 키 공간과 **절대 겹치지 않고**, USER의 완료는 `completed`에 넣지 않는다(§10).

## 5. 날짜·기간·추천일 규칙

### 5-1. 용어집 (이 문서 전체의 기준)

| 용어 | 어디에 | 의미 | 실제 일정 날짜? | 저장 |
|---|---|---|---|---|
| `eventDate` | USER 문서 | 사용자가 확인한 **그날** | ✅ | ✅ |
| `endDate` | USER 문서 | 확정된 연속 일정의 마지막 날 | ✅ | ✅ |
| `startTime`/`endTime` | USER 문서 | 그날의 시각 | ✅ | ✅ |
| `periodStart`/`periodEnd` | USER 문서(PERIOD) | 날짜가 **미확정**인 일정이 놓일 기간 | ❌ | ✅ |
| `recurrence.startDate`/`until` | USER 문서 | 반복 규칙의 **유효 기간** | 규칙의 범위일 뿐 | ✅ |
| `windowStart`/`windowEnd` | AUTO 이벤트 | 엔진이 계산한 권장 기간 | ❌ | ❌ (계산) |
| `fixedDate` | AUTO 이벤트 | 확정 날짜(혜택 신청 시작일) | ✅ | ❌ (계산) |
| **`displayDate`** | AUTO(화면 배치) | 캘린더 위치용 "추천일" | ❌ **절대 아님** | ❌ **저장 안 함** |

사용자 정의의 "`periodStart/periodEnd` = 일정 가능/유효 시작·종료일"은 **"날짜 미확정 일정이 놓일 기간"**으로 좁혀 확정한다. 반복 일정의 유효 기간은 `recurrence.startDate/until`에 둔다(§6). 그렇게 나누지 않으면 "매주 화·목 피아노(10월~2월)"가 PERIOD로 오해되어 기간 목록에 들어간다.

### 5-2. "기간"의 두 종류를 구분한다 (R6)

| | 날짜 미확정 기간 | 확정된 연속 기간 |
|---|---|---|
| 예 | "10월 중 부모 상담" | "7/25~8/24 여름방학", "10/16~17 1박2일" |
| 저장 | `dateKind=PERIOD`, `periodStart/End`, `eventDate=null` | `dateKind=FIXED`, `eventDate`+`endDate` |
| 캘린더 | **점 없음.** "이 달 기간 일정" 목록 | 걸친 **모든 날 칸에 표시** |
| 사용자에게 | "날짜가 아직 안 정해졌어요" | 실제 일정 |

### 5-3. 유형별 날짜 처리표

| 유형 | 저장 날짜 | 캘린더 | `displayDate` | 원본에 없는 날짜 생성 |
|---|---|---|---|---|
| AUTO_FIXED(`fixed`, 혜택) | 계산된 `fixedDate` | 그날 표식 | 미사용 | 금지 |
| AUTO_PERIOD(`window`) | `windowStart/End` 계산 | 추천일 표식 | **사용** | 표시용만. 저장·완료·기록·알림에 쓰지 않음 |
| AUTO_AGE(`monthly`) | 없음 | 추천일 표식 | **사용** | 위와 동일 |
| USER·FIXED | `eventDate`(+`endDate`, 시각) | 실제 날짜 표시 | **미사용** | **금지** |
| USER·PERIOD | `periodStart/End`만 | **"이 달 기간 일정" 목록**(점 없음) | **미사용** | **금지** |
| USER·반복 | `recurrence`(+예외) | 전개된 각 날짜 | 미사용 | 금지(규칙이 만든 회차는 사용자가 정한 규칙의 결과) |
| OCR/VOICE 후보 | 원문에서 확인된 값만 | 확인 화면에서 사용자 확정 후에만 | 미사용 | **금지**(I9) |

### 5-4. `displayDate` 규칙 (기존 그대로 + 명문화)
1. **AUTO 전용**, 화면 배치 파생값. 저장·동기화·기록·완료일·알림·USER에 쓰지 않는다.
2. `assignDisplayDays()`의 시그니처·알고리즘을 바꾸지 않는다. 입력은 `autoEvents`뿐이다(§4).
3. 안내 문구는 유지·강화: 선택한 날짜 패널을 **3묶음**으로 나눠 제목을 분리 — "내 일정" / "혜택 신청 시작" / **"추천 항목(정해진 날이 아니에요)"**. 지금은 제목이 "11월 12일"이라 아래 항목이 그날인 것처럼 읽히는 위험이 있다(v1 §2 ⑦).
4. **상대 표현 처리(음성 등)**: "다음 주 화요일"은 오늘 기준으로 확정 가능한 날짜 하나를 **후보로 제시**하고(예: "2026-10-06(화)로 이해했어요") 사용자가 확인해야 저장한다.

## 6. 반복 일정 구조

### 6-1. 저장

```jsonc
{
  "dateKind": "FIXED", "eventDate": null, "allDay": false,
  "startTime": "16:00", "endTime": "16:50",
  "recurrence": {
    "freq": "WEEKLY",            // v1: WEEKLY만 (격주는 interval:2). MONTHLY는 예약
    "interval": 1,
    "byDay": ["TU","TH"],        // MO TU WE TH FR SA SU
    "startDate": "2026-10-06",   // 첫 적용일(확정값)
    "until": "2027-02-26"        // null 허용(무기한). 전개는 항상 화면 범위로 자른다
  },
  "exceptions": {
    "2026-10-08": { "status": "CANCELLED", "note": "휴강" },
    "2026-10-13": { "status": "RESCHEDULED",
                    "movedTo": { "date":"2026-10-14", "startTime":"17:00", "endTime":"17:50" } },
    "2026-10-15": { "status": "DONE" },
    "2026-10-20": { "assigneeMemberId": "m2" }
  }
}
```

### 6-2. 규칙
- **회차는 저장하지 않는다.** `expandOccurrences(doc, rangeStart, rangeEnd)`가 화면 범위(월/주)만 전개한다. 전개 상한 `MAX_EXPANSION_DAYS`(예: 400일) — 범위가 그보다 크면 거부.
- 회차 정체성 = `originalDate`(규칙상 날짜). `RESCHEDULED`는 `originalDate`를 키로 유지하고 표시 `date`만 `movedTo.date`. 이동 후 날짜가 다른 회차와 겹쳐도 별개 Occurrence로 둔다.
- 규칙에 해당하지 않는 날짜의 예외는 **무시**(전개 결과에 영향 없음, 정리 대상).
- 예외 편집은 **필드 단위 쓰기**(`exceptions.2026-10-08`, dot-path) — 두 기기가 서로 다른 날의 예외를 동시에 넣어도 충돌하지 않는다(§11).
- 날짜 산술은 **로컬 날짜 산술만**(`new Date(y, m, d+n)`). UTC 변환·`toISOString` 금지(생년월일 하루 밀림 버그의 재발 방지).
- 반복 일정의 "완료"는 기본 개념이 아니다(수업이 끝났다고 체크하지 않는다). 필요할 때만 `exceptions[날짜].status="DONE"`.
- 공휴일 자동 휴강은 **없음**(사용자 예외 입력). 공휴일 데이터는 외부 연동 트랙.
- **편집 범위**: v1 = "이 날만(예외)" + "전체 수정". "이후 모두"는 **문서 분할**(기존 문서 `until` 확정 + 새 문서 생성, `splitFromScheduleId` 예약 필드)로 구현 가능 — 후순위.
- 단발 추가 수업(보강)은 **별도 FIXED 일정**으로 추가(반복에 끼워 넣지 않음).

### 6-3. 저장량
문서 크기 ∝ 예외 수(≤200). 주 2회×1년(≈100회차)도 문서 크기 증가 없음 → `completed` 맵에 회차를 쌓는 방식(통째 교체, 1MB 압박)을 피한다.

### 7-1. 식별자 정리

| 개념 | 식별자 | 위치 |
|---|---|---|
| 아이(원본 데이터) | 가족코드 6자리 | `families/{코드}` (기존) |
| 가구 내 아이 | `childKey` | `households/{hid}/children/{childKey}` 링크 |

### 7-2. 캘린더 필터 의미

| 필터 | USER 일정 | AUTO 일정 |
|---|---|---|
| 전체 | 모든 일정 | **활성 아이**의 AUTO(+ §7-3 형제 합산) |

형제 공동 일정(`childKeys` 2개 이상)은 "전체"에서 **한 번만** 표시하고 아이 배지를 여러 개 붙인다.

### 7-3. 형제 AUTO 합산 — 한계와 최소 안 (v1 충돌 C7-b의 결론)
- 현재 앱은 `completed`·`profile`이 **활성 아이 1명의 전역 상태**다(`app.js`). 그래서:
  - **1차(필수)**: "전체"에서 USER 일정은 모든 아이, **AUTO는 활성 아이만**.
  - **2차(선택)**: 형제 AUTO를 **읽기 전용**으로 합산 — `children` 링크의 코드로 각 아이 문서를 `fetchFamily`(1회 + 필요 시 리스너), 각 아이의 `profile`·`completed`로 `buildSchedule`을 따로 돌려 `childKey` 태그. **형제 AUTO 항목을 눌러 완료 처리하지 않고**, 누르면 `switchToChild`로 그 아이로 전환 후 상세를 연다. 이렇게 하면 `completed`의 "활성 아이 전역" 가정을 깨지 않는다.
  - 엔진은 순수 함수라 아이 N명 = N회 계산이지만 **성능은 측정하지 않았다** → 구현 1단계 측정 항목.
- **홈·체크리스트·기록·혜택은 계속 활성 아이 기준.** 가구 전체 뷰는 **캘린더 화면 한정**.

### 7-4. 아이별 색
`colorKey`(링크 문서). AUTO의 카테고리 색(6개: 파랑·보라·초록·노랑·빨강·슬레이트)과 **혼동되지 않도록** USER 표식은 **모양을 달리하고**(원이 아닌 막대) 색은 아이색을 쓴다. 팔레트 값은 UX 결정 사항(§14).

## 8. 담당자 구조

- 저장: 일정 `assigneeMemberId`(null = 담당 미정), 회차 단위 덮어쓰기는 `exceptions[날짜].assigneeMemberId`.
- `members`: 가구 생성 시 "엄마·아빠" 시드, 사용자가 이름 변경·추가(이모님·할머니 등)·소프트 삭제. `role` enum은 아이콘·정렬용. 삭제된 담당자를 참조하는 일정은 "(삭제된 담당자)"로 표시하고 **데이터는 유지**.

- 이 기기 사용자 매핑(`hannun_active_member`, 선택)은 **이번 범위 밖**(나중에 "내 일정만" 필터·기본 담당자 제안에 쓸 수 있음). 기존 `hannun_author_label`(기록 작성자 표시)과 **다른 개념**이므로 합치지 않는다.

### 충돌·공백 감지에 예약해 두는 데이터 (로직은 없음)

## 9. 캘린더 데이터 집계 구조

### 9-1. `buildCalendarModel` 계약 (순수 함수, `js/calendar-model.js`)

```text
입력 {
  view:  "month" | "week",
  range: { start:"YYYY-MM-DD", end:"YYYY-MM-DD" },          // 화면 범위
  filter:{ scope:"ALL"|"CHILD"|"FAMILY", childKey?, showAuto:boolean },
  auto:  { events: autoEvents[], displayDates: Map<eventId, Date[]>, completed }, // 활성 아이(+2차: autoByChild[])
  user:  { schedules: ScheduleDoc[], childLinks: ChildLink[], members: Member[] }
}
출력 CalendarModel {
  days: Map<"YYYY-MM-DD", {
     user:   Occurrence[],       // allDay 먼저, 그다음 startTime 오름차순
     benefit: AutoEvent[],       // 혜택 신청 시작(fixed) — 기존 calendarDayItems.fixed
     planned: AutoEvent[]        // 추천일(displayDate)인 항목 — 기존 calendarDayItems.planned
  }>,
  periodList: Occurrence[],      // PERIOD(날짜 미확정) — 범위와 겹치는 것, periodEnd 오름차순 → 제목순
  counts: { userItems, benefit, planned, periodItems }
}
```

### 9-2. 표시 규칙
- 날짜 칸 표식: **USER 먼저**(실제 시각이 있으므로) → 혜택 → 추천일. 기존처럼 최대 3개 + `+N`(N은 세 종류 합).
- 확정 연속 일정(`endDate`)은 걸친 모든 날 칸에 들어간다.
- 선택일 패널 3묶음: 내 일정(시각순) / 혜택 신청 시작 / 추천 항목(정해진 날 아님).
- **월 화면**: 그리드 아래에 **"이 달 기간 일정"** 섹션 = `periodList`. 각 줄에 "날짜 미정 · 10/1~10/31" 표기.
- **주 화면**: 7일 열 + 종일 행 + 시각순 카드, 상단에 기간 띠(주와 겹치는 PERIOD). 추천일 항목은 **접힘 묶음**("이 주 추천 항목 N개")으로 두어 실제 일정과 시각적으로 분리.
- 기존 `calendarDayItems`(`app.js:993`) 결과는 `days[..].benefit/planned`와 **동일해야 한다** → 골든 테스트(§12 T3).
- 기존 UI 대비 변경 크기: 그리드 알고리즘 무변경, `renderCalendar`·`renderSelectedDayPanel` 데이터 소스 교체, 필터·토글·기간 섹션 신규.

### 9-3. 왜 별도 모듈인가
`app.js`가 2,500줄 IIFE라 화면 로직 추가가 가장 위험하다. **집계는 순수 함수**로 빼서 Node 테스트로 잠그고, `app.js`는 결과를 받아 그리기만 한다(UX 개편 때 `hn-logic.js`로 분리한 방식과 동일).

### 10-1. 소비자 × 입력 표 (누가 무엇을 받는가)

### 10-2. 진행률의 정의
- 기존 진행률은 **AUTO 전용**으로 그대로. USER에는 "완료율"이라는 개념이 자연스럽지 않다(학원 수업은 체크 대상이 아님). 캘린더 상단에 "이번 달 내 일정 N개"를 **개수만** 별도 한 줄로 보여줄 수 있다(퍼센트 없음). **하나의 % 안에 섞지 않는다.**

### 10-3. 체크리스트의 역할
- **육아 체크리스트 = AUTO 전용**(연령별 Todo·카테고리 필터·완료 상태·현재 월령). 캘린더의 "자동 일정 함께 보기" 토글은 캘린더 표시 필터일 뿐 체크리스트와 무관.
- "Calendar → 육아 체크만 보기"는 캘린더 필터(`showAuto` + USER 숨김)로 **구현 가능하지만 체크리스트를 대체하지 않는다**(체크리스트는 월령 전체를 훑는 화면, 캘린더는 날짜별 화면).
- 36개월 초과 시 그룹 라벨 확장은 §13-6.

### 10-4. 기록 연결
USER 일정 완료 → "기록 추가?" 프롬프트로 `HNRecordsView.openEditor`를 제목·날짜 미리 채워 열고 저장 시 `records.<id>.scheduleRef = {scheduleId, date}`. **USER 완료 자체는 `records`를 자동 생성하지 않는다**(중복 방지, 기존 `deriveAutoRecords`는 AUTO 전용 유지).

## 11. Firestore 저장·동기화 구조

### 11-1. 읽기·쓰기·리스너

| 항목 | 설계 |
|---|---|
| 읽기 시작 | `hannun_household_code`가 있으면 `householdCodes/{코드}` get → `households/{hid}` |
| 리스너 | 4개: `households/{hid}`(1문서), `children`, `members`, `schedules` (각 컬렉션 1리스너). 활성 아이의 기존 `families/{코드}` 리스너는 **그대로** |
| 쓰기 단위 | **문서 단위**(`set`/`update`) + `updatedAt`. `exceptions.<날짜>`는 **dot-path 필드 단위** |
| ID | 클라이언트 생성(`s`+시각+난수, `records.js`의 `newId`와 동일 방식) |
| 삭제 | 소프트(`deletedAt`). 하드 삭제 금지 |
| 충돌 | 문서 단위 `updatedAt` 큰 쪽이 이김(`mergeRecordMaps`와 동일 정책을 문서 목록으로 일반화 `mergeById`). 서로 다른 예외 날짜의 dot-path 쓰기는 **교환 가능**(충돌 없음) |
| 크기 | 문서 1개 ≈ 0.5~1.5KB(예외 200개 시 수 KB) → 1MB와 무관. 가구당 일정 ≈ 수십~수백 개 예상(**실측 아님**) |

### 11-2. 오프라인·실패 처리 (기존 `completed`의 결함을 따르지 않는다)
현재 `completed`는 실패를 `console.error`로 삼키고, 재시작 시 서버 값으로 덮어써 **오프라인 체크가 유실될 수 있다**(v1 §13-1 #10). 새 데이터는 `records.js` 수준 이상으로:
1. **로컬 우선**: 저장 즉시 `hannun_household:<hid>`(가구 미러: 아이 링크·담당자·일정)에 반영 → 화면 즉시 갱신.
2. **대기열**: 서버 쓰기 실패·오프라인이면 `hannun_household_pending:<hid>`에 `{op,path,payload,ts}` 추가.
3. **재시도**: 앱 시작·`online`·`visibilitychange`(기존 update 확인 훅과 같은 자리)에서 대기열 flush. 성공 시 제거.
4. **덮어쓰기 방지**: 서버 스냅샷을 받아도 **대기열에 있는 문서는 로컬이 이긴다**(flush 후 재병합).
5. **표시**: 대기열이 비어 있지 않거나 `permission-denied`면 "이 기기에만 저장됨" 배너(`HNRecords.syncError`와 같은 패턴). **실패를 조용히 삼키지 않는다.**
- Firestore SDK 오프라인 영속성(`enablePersistence`)은 **쓰지 않는다**: 현재 미사용이고, iOS WKWebView·다중 탭에서의 동작을 이 환경에서 검증할 수 없다. 자체 미러+대기열이 검증 가능하다.

### 11-3. 규칙 설계(안 — 배포는 사용자, 에뮬레이터 검증 후)

```text
householdCodes/{code}
  get: 허용 / list: 금지 / create: keys ⊆ {householdId,active,createdAt,revokedAt}, active==true / update: active,revokedAt만 / delete: 금지
households/{hid}
  get: 허용 / list: 금지 / create: keys ⊆ {v,name,createdAt,updatedAt} / update: name,updatedAt만 / delete: 금지
households/{hid}/children/{childKey}
  get,list: 허용(hid를 아는 경로) / create,update: keys ⊆ {v,familyCode,displayName,order,colorKey,addedAt,removedAt}
                                     + familyCode is string && size ≤ 8 / delete: 금지
households/{hid}/members/{memberId}
  get,list: 허용 / create,update: keys ⊆ {v,role,label,order,colorKey,createdAt,updatedAt,deletedAt}, role ∈ enum, label size ≤ 20 / delete: 금지
households/{hid}/schedules/{sid}
  get,list: 허용 / create: v==1, sourceType ∈ enum, dateKind ∈ enum, title size ≤ 100, memo size ≤ 500,
                          keys ⊆ 허용목록(§3-1, displayDate 포함 안 함), exceptions.size() ≤ 200
                update: 위와 동일 허용 키 + createdAt 불변 / delete: 금지
```
- 규칙은 **프로젝트 단위 배포**라 잘못된 규칙 하나가 **기존 동기화 전체를 막을 수 있다.** 그래서 ① 기존 `families/**` 규칙 블록은 **한 글자도 수정하지 않고** 새 블록만 **추가** ② 규칙 논리 테스트(`test/firestore-rules.logic.test.js`는 실제 에뮬레이터가 아니라 규칙을 JS로 재현한 것 — 파일 헤더에 명시)로 새 블록 검증 ③ 실제 검증은 사용자가 `test/firestore-v2-manual-test.html` 방식으로 ④ 배포 전 **현재 배포본을 먼저 export**해 롤백본으로 보관.
- **롤아웃**: 기능 플래그(`FEATURES.household`) OFF로 출시 → 규칙 배포 확인 → 능력 탐지(가구 문서 쓰기 시도가 `permission-denied`면 UI를 숨기고 "준비 중") → 고정 테스트 계정으로 2기기 테스트(§12) → ON.
- 남는 한계(기존과 동일): 문서 생성 남용·코드 무차별 대입은 규칙으로 막을 수 없음(App Check는 OCR 전 재검토).

### 11-4. 비용
초기 리스너 로드 = 컬렉션 문서 수만큼 읽기, 이후 변경분만. 현재 서비스 대비 세션당 읽기가 늘지만 **수십~수백 건 수준으로 예상**한다. 정확한 과금 수치는 확인하지 않았다.

| A8 | 생년월일 선택기 범위 | `thisYear-8`(`app.js:618`) | 초등 6학년(만 12세)은 선택 불가 |

> A2는 기존 사용자에게 **지금** 영향을 주는 결함이다. 수정하면 표시가 바뀌므로 **동작 변경 결정**이 필요하다(§14 Q-A). 확장 작업과 분리해 승인 후 진행한다.

### 13-2. 설계 원칙

1. **연령·학년 질문은 `ChildTimeline` 하나로만 답한다.** 다른 모듈은 `ageInMonths`·`addMonths`·`<= 36` 같은 산술·리터럴을 **직접 쓰지 않는다.**
2. **기존 0~36개월 결과를 바꾸지 않는 것이 기본값.** 새 계산은 명시적으로 선택된 항목에만 적용한다(§13-5). 바꾸는 것은 승인된 목록만.
3. **정책값(입학 규칙·학기 경계·반 나이 기준)은 코드가 아니라 설정 데이터**로 두고 각각 검증 상태를 단다. 이번 단계에서 **정책 데이터를 새로 만들지 않는다**(§13-8 출처 조사 트랙).
4. **학년은 파생값이고 다니는 곳은 사용자 선언값이다.** 둘이 다르면 선언값이 우선하고, 서비스는 "다니는 곳을 알려 주세요" 제안만 한다(값을 추정해 채우지 않음).
5. 엔진(`todo-engine.js`)은 순수 함수를 유지한다. `ChildTimeline`은 **입력으로 주입**한다.

### 13-3. `ChildTimeline` — 출력 구조 (`js/child-timeline.js`, 순수)

```text
computeTimeline(input { birthDate, asOf, stage, care?, enrollmentYearOverride?, policy }) → {
  age: {
    years, months, days,            // 만 나이 + 달력 기준 나머지 (예: 만 6세 4개월 12일)
    totalMonths,                    // 달력 기준 총 개월(정수) — 기존 ageInMonths와 대응
    fractionalDaysSinceBirth        // 일수(영아기 소수 월령 호환용)
  },
  calendar: { birthYear, yearAge /* 기준연도 − 출생연도 */ },
  school: {                         // policy 없으면 null
    enrollmentYear,                 // 초등 입학 학년도 (override 우선)
    schoolYear,                     // asOf가 속한 학년도(3월~다음 2월)
    grade,                          // "PRESCHOOL" | 1..6 | "AFTER_ELEMENTARY"
    yearsToEnrollment,              // 입학까지 남은 학년도 수 (예비초등 = 0, 즉 입학 직전 학년도 등)
    semester,                       // 1 | 2 | null(방학 경계 등은 policy)
    stageBand                       // "INFANT_TODDLER" | "PRESCHOOL" | "PRE_ELEMENTARY" | "ELEMENTARY_LOW" | "ELEMENTARY_HIGH"
  },
  label: "생후 5개월" | "만 3세 2개월" | "초1 · 2학기",   // 화면 표기 단일 출처
  serviceRange: { maxMonths }        // 서비스가 다루는 상한(하드코딩 36 대체)
}
```

### 13-4. 날짜 산술 규칙 (단일 구현)

| 함수 | 규칙 |
|---|---|
| `addMonthsClamped(date, n)` | 결과 월에 그 일자가 없으면 **그 달 말일**(예: 1/31+1개월 = 2/28 또는 2/29). `setMonth` 넘침 금지 |
| `addYearsClamped(date, n)` | 2/29 생일은 평년에 **2/28**로(안 D 추천, §14 Q-B) |
| `completedMonths(birth, asOf)` | 달력 기준 완료된 개월 수(말일 클램프 규칙 적용) |
| `diffYMD(birth, asOf)` | years/months/days 분해 |
| 일수 기반 | `legacyDaysFromBirth(birth, months)` = `birth + months×30일` — **기존 엔진 호환 전용**(§13-5) |

- 모든 함수는 **로컬 날짜(`Date(y,m,d)`)** 만 다룬다. `toISOString` 금지.
- 기존 5개 구현은 **삭제하지 않고 얇은 위임 래퍼**로 바꿔 호출부를 그대로 둔다(`ageInMonths(b, t)` → `timeline.age.totalMonths`). 다만 A2 수정이 포함되므로 **차이 목록을 생성해 승인**한다(§13-9).

### 13-5. 엔진 통합 — 선택지와 추천

| 안 | 내용 | 기존 영향 |
|---|---|---|
| **A(추천)** | `AGE_WINDOW` 등 기존 트리거는 **기본 `basis:"LEGACY_30D"`로 동결**(40개 테스트가 고정). 새 선택 필드 `basis:"CALENDAR"`를 가진 항목만 달력 기반. 새 트리거 `AGE_CALENDAR_WINDOW`(`{years,months}` 시작·끝, 생일 기준 클램프)와 `SCHOOL_TERM_WINDOW`(`{anchor:"ENROLLMENT", yearOffset, startMonth, endMonth}` — 학년도 기준 달력 기간)를 **추가**. 엔진은 `timeline`을 입력으로 받음 | 기존 결과 불변, 새 case만 추가 |

| C | 초등 항목은 엔진 없이 사용자 일정으로만 | 자동 일정 확장 목표 포기 |

**추천 A** — 기존 동작을 바꾸지 않고, 중복 없이 확장. ※ "새 trigger type 추가 금지"라는 기존 문서 원칙과 충돌하므로 **사용자 승인 사항**(§14 Q-G).

30일 근사로 계산되는 기존 항목(A5의 10개 등)은 **자동으로 바꾸지 않는다.** 항목별로 (a) 정책상 기준이 "출생 후 N개월"인지 "N번째 생일"인지 (b) 오차가 실제로 문제인지를 데이터 트랙에서 확인해 **`basis:"CALENDAR"`로 전환할 것만 승인 후 변경**한다(변경 전·후 창 날짜 diff를 첨부).

### 13-6. 소비자 변경 (설계만)

| 소비자 | 현재 | 변경 |
|---|---|---|
| `visibleSchedule` (`app.js:764`) | `ageInMonths(...) <= 36` | `timeline.serviceRange.maxMonths` 기준. 값의 근거는 설정(초6까지 등, §14 Q-H) |
| 체크리스트 그룹 | `displayMonth` 정수 + `LATE_BUCKETS`(~36) | **`displayGroup`** 개념: `{kind:"AGE_MONTH"\|"AGE_YEAR"\|"GRADE", value}`. 기존 `displayMonth`는 `AGE_MONTH`로 자동 해석(데이터 무변경). 36개월 이후는 `AGE_YEAR`(만 3세…), 취학 전후는 `GRADE`(예비초등·초1~) |

### 13-7. "현재 다니는 곳"과의 관계

```text
profile.care (사용자 선언)          ─┐
timeline.school.stageBand (파생)    ─┼▶ eligibility 조건값 / 제안 배너 / 체크리스트 그룹
profile.enrollmentYearOverride(선택) ─┘   조기입학·취학 유예처럼 입학 학년도가 다를 때만 사용자가 입력
```
- 엔진의 `eligibilityCondition {attribute, requiredValue}`(현재 `familyDeclaredAttributes:{}`로 항상 비어 있어 미사용)로 `care`를 전달하되, 단일 값 동등 비교의 한계(어린이집 **또는** 유치원)는 `requiredValues:[…]` 배열 지원(소규모 확장)으로 해결 — 이 역시 §14 Q-G 승인 대상.
- 만 나이만으로는 부족한 이유(**같은 만 6세가 서로 다른 단계**) — 아래 예는 입학 학년도 = 출생연도 + 7이라는 **가정**(정책 검증 필요, §13-8)으로 계산했다:

```text
2026-10 시점의 만 6세 두 아이
 · 2019-12-05생: 입학 학년도 2026 → 지금 초1 2학기          (학령 진입 후)
 · 2020-05-10생: 입학 학년도 2027 → 지금 취학 전 마지막 해   (예비초등)
→ 나이(만 6세)가 같아도 필요한 일정 체계가 다르다. `school.grade`·`stageBand`로 구분해야 한다.
```

### 13-8. 정책값 — 이번 단계에서 만들지 않는 것 (조사 트랙 요청)

| 항목 | `policy` 설정 키(예) | 상태 |
|---|---|---|
| 초등 입학 학년도 산정 | `enrollmentOffsetYears`(가정 7) | **공식 확인 필요**(초·중등교육법·교육부 취학 안내) |
| 학년도·학기 경계 | `schoolYearStart`(3/1 가정), `semesters` | **확인 필요**, 학교별 상이 가능 → 사용자 일정으로 덮어쓰기 가능 |
| 어린이집·유치원 반 나이 기준 | `classAgeBasis` | **확인 필요**(연 나이 vs 특정일 기준 만 나이) |
| "예비초등"의 정의 | `preElementaryDefinition` | **제품 정의**(§14 Q-C) |
| 조기입학·유예 | `enrollmentYearOverride` | 사용자 입력 |

모든 값은 `{value, verificationStatus, source}` 형태로 두어 기존 Todo와 같은 검증 표기(`확인됨`/`확인필요`)를 따른다. **`확인필요` 값에 의존하는 항목은 화면에 확정 문구로 노출하지 않는다**(기존 규칙과 동일).
