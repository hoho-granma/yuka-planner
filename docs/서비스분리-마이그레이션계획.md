# 한눈육아 / 쓰앵님 서비스 분리 — 마이그레이션 계획

작성일: 2026-10-14 · 상태: **v3 (결정 반영 완료, 0단계 시작 가능)** · 코드는 아직 건드리지 않았다.

## 1. 확정된 결정

| # | 결정 |
|---|---|
| 1 | 36개월 이상 **AUTO 일정(학교 준비·학령기 검진·접종)은 한눈육아에 남긴다.** 한눈육아의 메인은 가족 캘린더, 쓰앵님의 메인은 성장기록. |
| 2 | Firebase 프로젝트(`yuka-planner`)·로그인·가구를 **공유**한다. |
| 3 | 두 앱 모두 **Firebase Hosting**으로 배포한다 (한눈육아도 GitHub Pages에서 이전). |
| 4 | **GitHub 리포 2개**로 간다 (모노레포 아님). |
| 5 | 쓰앵님은 **웹 + iOS + Android** 동시 출시. |

## 2. 분리 기준 = "기능"이지 "아이 나이"가 아니다

결정 1 때문에 이전 초안의 "각 앱은 자기 연령대 아이만 보여준다"는 폐기한다. 한눈육아는 36개월 이상 아이도 계속 보여 주고(캘린더·할일·AUTO), 쓰앵님은 성장기록·교육 기능을 맡는다.

| | 한눈육아 | 쓰앵님 |
|---|---|---|
| 메인 | 가족 캘린더 | 성장기록 |
| 기능 | 일정·할일(USER), AUTO 일정(전 연령 포함 36개월 이상), 어디갈까, 지원금, 사진·문자 일정 등록 | 성장기록, 교육정보, 학습점검, 교육트렌드 |
| 공통 | 계정·가구·가족 공유, 일정·할일 등록 | ← 동일 (공통 코어) |

- 한눈육아의 36+ 메뉴(홈·캘린더·할 일, `over36-view.js`)는 **그대로 둔다.** 현재 36+ 메뉴 중 성장기록 탭만 쓰앵님 진입 카드로 바뀐다.
- 쓰앵님은 일정·할일 화면이 필요하므로 `over36-view.js`·날짜 시트 등 36+ 홈/할일 UI를 **공통 코어**로 올려 두 앱이 함께 쓴다.
- 쓰앵님에서 일정·할일을 등록하면 같은 가구의 한눈육아 캘린더에 그대로 보인다 (같은 `families/{hid}/schedules·todos`).

## 3. 현재 구조 (조사 결과)

- **한 앱·한 코드베이스**: `index.html` 하나에 JS 약 90개, `js/app.js` 8,464줄. 번들러 없이 `<script>` 순서로 로드.
- **분기 이음매**: `app.js`의 `acct36Child(profile)` / `acct36Active()` — 이 분기는 이제 "연령 메뉴"로만 남고 **분리의 경계가 아니다.** 분리의 경계는 "성장기록·교육" 기능 묶음이다.
- **쓰앵님으로 이동할 묶음**: `growth-*.js`(evidence/sync/records/learning-view), `learning-check*.js`, `education-*.js`(9개), `edu-3to5-view.js`, `edu-trend.js`, `css/growth-records.css`·`learning-check.css`·`education-research.css`·`character-ui.css`(성장기록용 여부 확인), `learning-check-paper.html`, `curriculum-map*`, `data/education/*`, `functions/education-directory/`.
- **한눈육아에 남는 묶음**: `over36-view.js`, `auto-after36.js`, `school-policy.js`, `auto-steps.js`, `places*`, `subsidy-*`, `month-tiers.js`, `next-stage*.js`, `data/policy`, `data/todos`, `data/subsidies`, `data/places.json`.
- **공통 코어**: `sync.js`, `auth-service.js`, `account-*.js`, `household-*.js`, `family-access*.js`, `user-schedule*.js`, `schedule-kinds.js`, `calendar-*.js`, `date-picker.js`, `time-*.js`, `todo-engine.js`, `child-todos.js`, `capture/*`, `date-calc.js`, `child-timeline.js`, `korean-holidays.js`, `over36-view.js`.
- **미분류(0단계에서 확인)**: `curation.js`(앱에 연결 안 된 순수 함수 — 한눈육아에 두고 필요 시 이동), `character-ui.js`, `app.js` 안의 성장기록·교육 로직(192건 `acct36*` 중 일부가 성장기록 진입 코드).
- **백엔드**: Firestore `accounts/{uid}`, `families/{hid}`(+`members`·`childLinks`·`schedules`·`todos`·`growthRecords`), `familyAccess`, `children`(레거시), `placeUsageStats`. Storage `families/{hid}/growthRecords/...`. 함수 `functions/message-input`, `functions/education-directory`.
- **현재 배포**: GitHub Pages(`hoho-granma/yuka-planner`) + `ios/`(Capacitor, **Android 없음**) + `www/`(자동 동기화되지 않는 복사본). Firebase Hosting 사이트는 `yuka-planner`(https://yuka-planner.web.app) 하나가 이미 존재하며, `firebase.json`에는 hosting 설정이 아직 없다.

## 4. 설계 결정

### D1. 공유: 같은 Firebase 프로젝트·계정·가구
- 데이터 복사가 없다. 성장기록 문서와 사진이 지금 경로 그대로 쓰앵님에서 열린다.
- **규칙(Firestore·Storage)은 한 리포(한눈육아)만 소유하고 배포한다.** 쓰앵님 리포는 규칙 파일을 두지 않거나 읽기 전용 사본만 둔다. 두 리포가 각자 배포하면 상대 앱 경로를 막는 사고가 난다.
- Cloud Functions는 코드베이스 단위로 나눈다: `message-input` = 한눈육아, `education-directory` = 쓰앵님 리포로 이동. 쓰앵님 리포에서는 반드시 `firebase deploy --only functions:education-directory`처럼 **범위를 지정**한다 (코드베이스가 빠진 채 전체 배포하면 다른 리포 함수 삭제 프롬프트가 뜬다).

### D2. 코드 공유 — 리포가 2개라서 필요한 장치
- 공통 코어의 **원본은 한눈육아 리포의 `core/`**에 둔다.
- 쓰앵님 리포는 `tools/sync-core.sh`로 한눈육아 리포의 **특정 태그**(`core-v1`, `core-v2`…)에서 코어를 복사해 오고, 어느 태그를 받았는지 `core.version`에 기록한다.
- 코어 수정은 한눈육아 리포에서만 하고, 태그를 올린 뒤 쓰앵님이 받는다. 쓰앵님 리포의 `core/`를 직접 고치지 않는다 (다음 동기화 때 덮어써진다).
- 한계: 두 리포가 어긋날 수 있다(코어 버전 차이). 어긋남이 잦아지면 모노레포나 3번째 리포(git submodule)로 옮긴다 — 파일 구조가 `core/` 한 폴더로 이미 모여 있으므로 옮기기 쉽다.
- 번들러는 도입하지 않는다. 앱별 `index.html`의 스크립트 목록만 나눈다.

### D3. 아이 노출 규칙 (확정)
- 한눈육아: 가구의 모든 아이를 보여준다 (현행 유지).
- 쓰앵님: **36개월 이상 아이만** 칩에 보인다. 36개월 미만 아이만 있는 가구는 한눈육아 안내 화면을 보여 준다.
- 36개월 기준값은 `ChildTimeline.OVER36_FROM_MONTHS` 하나를 코어에서 읽는다.

### D4. Firebase Hosting
- 멀티사이트: 한눈육아 = 기존 사이트 `yuka-planner`(→ `yuka-planner.web.app`), 쓰앵님 = **새 사이트** (`firebase hosting:sites:create <사이트ID>`, ID는 사용자 결정). 각자 `firebase.json`의 hosting 설정과 `.firebaserc` 타깃으로 `firebase deploy --only hosting:<타깃>`.
- 배포 대상 폴더는 빌드 산출물 하나(`dist/`)로 통일하고 `www/` 수동 복사본은 폐지한다.
- **GitHub Pages → Firebase Hosting 전환의 함정 (한눈육아)**
  1. origin이 바뀌므로 `localStorage`·서비스워커·캐시가 **전부 새로 시작**한다. 계정 데이터(Firestore)는 안전하지만 `hannun_private_archive:*`, 완료 숨김 설정, 선택된 아이, **오프라인 큐**, 레거시 가족코드 모드의 로컬 상태는 이전되지 않는다. → 이전 필요한 키를 목록화하고, 구 주소(github.io)의 마지막 빌드에 "새 주소로 이동" 화면 + 로컬 데이터 1회 전달(쿼리/`postMessage`) 기능을 넣어 둔다. 계정 로그인 사용자는 이전 없이도 복구된다.
  2. Firebase Auth **승인된 도메인**에 새 도메인을 추가해야 로그인이 된다 (현재 `authDomain: yuka-planner.firebaseapp.com`).
  3. PWA 홈 화면 설치본은 origin이 바뀌면 **새로 설치**해야 한다 → 안내 배너.
  4. 구 GitHub Pages는 한동안 유지하되 이동 안내만 보이게 한다. (Pages 설정을 끄는 건 사용자 승인 사항.)
  5. `sw.js`의 `CACHE_NAME`·`SHELL_ASSETS`는 앱별로 분리하고, Hosting의 캐시 헤더(`sw.js`는 no-cache)를 `firebase.json`에 명시한다.
- 쓰앵님은 새 origin이므로 localStorage 키 접두사를 `ssaeng_*`로 쓴다.

### D5. 네이티브 앱 (iOS·Android)
- Capacitor로 웹 빌드(`dist/`)를 감싼다. 한눈육아의 `ios/`는 그대로, **쓰앵님은 리포를 새로 만들어 `ios/`·`android/`를 새로 생성**한다. (`android/`는 지금 어느 쪽에도 없다.)
- 쓰앵님은 **앱 ID(번들 ID/패키지명)를 새로 정해야** 한다. 한 번 스토어에 올리면 바꿀 수 없다. 개발자 계정(Apple Developer, Google Play) 준비 필요.
- 네이티브 WebView의 origin은 `capacitor://localhost`·`https://localhost`라서 Firebase Auth 로그인 방식(팝업/리다이렉트)이 달라진다. 현재 로그인 방식이 네이티브에서 도는지 한눈육아 `ios/`로 이미 검증됐는지 0단계에서 확인한다.
- 앱 심사: 앱스토어/플레이 심사는 며칠~수 주 걸릴 수 있어 **웹 출시와 일정을 분리**한다 (웹이 먼저 열리고 앱은 심사 통과 후 공개해도 "동시 출시 준비"는 유효).

## 5. 단계별 계획

각 단계 끝에 **기존 한눈육아가 지금과 똑같이 동작**해야 한다. 단계마다 별도 커밋, push는 지시 후에만.

### 0단계 — 동결·기준선 (읽기 전용)
1. `main`을 태그(`pre-split-v2.0.72`)로 고정. 롤백 기준점.
2. `test/` 159개를 분류: 코어 / 한눈육아 / 쓰앵님 이동 대상.
3. `codebase-memory`로 `app.js` 호출 그래프를 뽑아 **성장기록·교육 묶음이 `app.js`의 어느 함수와 얽혔는지** 목록화. 이 목록이 2단계 추출 범위를 정한다.
4. (확인 완료) 리포: `yuka-planner`(한눈육아), `ssanim`(쓰앵님, 비어 있음).
5. 현재 Firestore 규칙(배포본) vs 로컬 diff, 백업 (`~/Documents/firestore.rules.backup-*`).
6. 네이티브(Capacitor) 로그인이 현재 어떻게 동작하는지, `firebase.json`에 hosting을 추가했을 때 기존 `yuka-planner.web.app`에 무엇이 떠 있는지(비어 있는지) 확인.

### 1단계 — 한눈육아를 Firebase Hosting으로 이전 (분리보다 먼저)
- 분리와 이전을 동시에 하면 문제가 났을 때 원인을 찾기 어렵다. **먼저 지금 앱 그대로 호스팅만 옮긴다.**
1. `firebase.json`에 hosting 추가, 빌드 산출물(`dist/`) 스크립트.
2. `yuka-planner.web.app`에서 동작 확인(고정 테스트 계정 은찬, 서울 구로구, 2026-06-20) + Auth 승인 도메인 추가.
3. GitHub Pages 쪽에 이동 안내 화면, 로컬 데이터 전달 장치(D4-1).
4. 사용자 승인 후 구 주소 안내 배포.

### 2단계 — 공통 코어 분리 (한눈육아 리포 내부)
1. 공통 파일을 `core/`로 이동 (`sw.js`·`index.html`·테스트의 경로 하드코딩 갱신). `over36-view.js`·날짜 시트·todo-engine·capture는 공통.
2. 성장기록·교육 묶음을 `apps-ssaeng-candidate/`(임시 폴더)로 한 번에 격리해 두고, 한눈육아에서 그 진입점만 "쓰앵님 진입 카드"로 교체. 이 시점에는 두 곳 모두 코드가 있어 되돌릴 수 있다.
3. `app.js`에서 성장기록·교육 관련 함수를 분리하며, **한눈육아 빌드에서 이 묶음을 로드하지 않아도 앱이 정상 동작**하는지 확인.
4. `tools/build.js`: 앱별 스크립트 목록으로 `dist/` 생성.

### 3단계 — 쓰앵님 리포 부트스트랩
1. 새 리포에 앱 셸: 4탭(홈·캘린더·할 일·성장기록) + 교육정보, 이름·아이콘·테마(딥포레스트)·manifest·SW.
2. `tools/sync-core.sh`로 코어 태그 `core-v1` 동기화.
3. 성장기록·교육 묶음과 `functions/education-directory`를 이 리포로 이동. **Firestore/Storage 경로는 변경하지 않는다.**
4. Firebase Hosting 새 사이트 생성·배포. Auth 승인 도메인 추가.
5. 한눈육아의 쓰앵님 진입 카드 링크를 이 주소로 연결.

### 4단계 — 한눈육아 정리
1. 격리해 둔 성장기록·교육 코드를 한눈육아 리포에서 삭제 (3단계에서 쓰앵님에 들어갔는지 확인 후).
2. `AGENTS.md`(방향·디자인 톤·성장기록 AI 점검·학원 후기·테스트 섹션), `docs/한눈육아-서비스방향설계서.md`, `docs/한눈육아-메뉴별UX지침.md`를 새 범위에 맞게 수정. **성장기록·학원후기 관련 규칙은 쓰앵님 리포 `AGENTS.md`로 옮긴다.**
3. 36개월 이상 홈/캘린더/할일/AUTO와 어디갈까는 유지.

### 5단계 — 쓰앵님 네이티브·출시
1. Capacitor `ios/`·`android/` 생성, 새 앱 ID, 아이콘·스플래시.
2. 스토어 등록·심사, 웹은 심사와 무관하게 먼저 공개 가능.

### 롤백
- 데이터 이관·삭제가 없어 **데이터 롤백은 필요 없다.** 코드는 0단계 태그로, 호스팅은 Firebase Hosting 이전 버전 롤백(콘솔)로 복귀. 규칙을 바꿨다면 백업 규칙 재배포.

## 6. 위험과 대응

| 위험 | 대응 |
|---|---|
| 호스팅 이전(origin 변경)으로 로컬 데이터 유실 | 1단계에서 분리와 별도로 먼저 수행, 이동 화면 + 전달 장치, 계정 사용자는 Firestore로 복구 |
| `app.js`에 성장기록/교육 로직이 얽힘 | 2단계에서 임시 폴더로 격리 후 한눈육아만 로드해 검증 |
| 리포 2개 → 코어 버전 어긋남 | `core-vN` 태그 + `core.version` 기록, 코어는 한눈육아 리포에서만 수정 |
| 규칙·함수 배포가 서로 덮어씀 | 규칙은 한눈육아 리포 단독, 함수는 `--only functions:<코드베이스>` |
| 네이티브 로그인 | 0단계에서 현 동작 확인, 쓰앵님 5단계 전에 실제 기기 검증 |
| 쓰앵님 앱 ID·개발자 계정 | 3단계 시작 전에 확정 |
