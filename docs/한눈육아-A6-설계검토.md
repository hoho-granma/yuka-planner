# 한눈육아 A6 설계 검토 — 정책값·36개월 이후·`schedule.js` 연결

작성: 2026-10-01 · 상태: **D-A6-1~9 승인됨, A6-0 정책 조사 결과 반영(§9) — A6-1 구현은 다음 승인 후 시작** · 기준 커밋: `764cb7b`(A5 완료)
근거: `한눈육아-확장설계-2단계-상세.md` §13-3·§13-5~§13-9·§14(Q-C·Q-G·Q-H), `한눈육아-A5-설계서.md`, `한눈육아-확장설계-v1.md` §19, 실제 코드·데이터(아래 §2)

## 1. A6의 위치와 이 문서의 목적

A5가 끝나 엔진은 `basis`·`AGE_CALENDAR_WINDOW`·`SCHOOL_TERM_WINDOW`·`requiredValues`·`timeline` 입력을 받을 수 있지만 **어떤 데이터도 쓰지 않고, 앱은 `timeline`을 넘기지 않는다.** 로드맵상 A6는 "콘텐츠 트랙 합류 — 예비초등·초1~2 데이터"다. 그런데 A6에는 성격이 다른 일이 섞여 있다(정책 확인, 데이터 작성, 코드 연결, 사용자에게 보이는 변화). **구현 전에 범위를 쪼개고, 선행 조건과 사용자 영향이 있는 결정을 먼저 확정**하는 것이 이 문서의 목적이다.

## 2. 현재 사실 (코드·데이터 확인)

**36개월 상한이 걸려 있는 곳**
- `app.js` `visibleSchedule` → `ChildTimeline.isWithinServiceRange(birth, e.date)` (`SERVICE_RANGE.maxMonths = 36`). 이벤트 날짜 기준 월령이 36을 넘으면 화면에서 제외.
- `app.js` `repeatMonthRangeOf`: `endMonth == null`이면 상한(36)까지만 월 그룹에 반복 노출.
- 체크리스트 그룹: `CHECKLIST_BUCKETS`의 마지막 구간이 `24~36`(A4에서 `ChildTimeline`으로 이동). 36개월 이후 그룹 체계 없음.
- 표기: 헤더 "생후 N개월"(`ChildTimeline.ageLabel`), `manifest.json`/랜딩의 "0~36개월" 문구.
- 이미 풀린 것: 생년월일 선택기는 올해 초6 출생연도(올해−11)까지 입력 가능(`4bee41d`). 즉 **초등학생 아이를 등록할 수는 있지만 자동 일정은 36개월까지만** 나온다.

**36개월 초과 데이터 (전체 정의 78건 중)**
- 36개월 초과 구간을 가진 정의 15건: `LF-02`(~48), `FD-05`·`FD-09`·`FD-10`·`OR-04`(열린 구간), `SF-01`(~72), `VX-DTAP`·`VX-IPV`·`VX-MMR`(시작>36, ~72), `VX-JEV`(시작>36, ~144), `VX-FLU`(열린), `SB-04`(~108), `SB-08`(~72), `SB-09`(~156), `SB-12`(~156, 확인필요).
- **상한 때문에 지금 숨겨지는 항목**: 은찬 프로필(서울 구로구)로 실제 `buildSchedule`을 돌려 확인 — 138건 중 **5건**(`VX-DTAP`×1, `VX-IPV`×1, `VX-MMR`×1, `VX-JEV`×2). 이전 설계(A0~A4 계획 D2)가 예고한 "접종 5건"과 일치. 지역 지원금 이벤트는 이 프로필에서는 숨겨지는 것이 없다(지역별로 다를 수 있음 — 미확인).
- 초등(예비초등·초1~) 대상 Todo는 **0건**. 학교·학년 정책 데이터도 저장소에 없다.

**연결 지점 (A5까지 준비된 것)**
- `ChildTimeline.compute({birthDate, asOf, stage, policy?, enrollmentYearOverride?})` → 정책이 `확인됨`일 때만 `school{enrollmentYear, schoolYear, grade, stageBand, gradeLabel}`, 아니면 `school:null`. `stageBand`는 5종, `grade==="AFTER_ELEMENTARY"`이면 `stageBand:null`.
- `TodoEngine.calculateTodoInstances`가 `input.timeline`을 받음. `schedule.js buildTodoEngineEvents`는 아직 넘기지 않고 `familyDeclaredAttributes: {}`(항상 비어 있음).
- `profile.care`·`enrollmentYearOverride`·온보딩 칩은 **미구현**(B4 잔여).
- `data/subsidies`·`data/todos`는 앱이 `fetch`로 읽는다(서비스워커가 `data/**`는 캐시하지 않음).

## 4. 불변 보장·검증 게이트 (A5와 동일 기준)
- 각 단위 종료 기준: 전체 테스트, `auto-diff`(기준 `4bee41d`)에서 **승인된 차이만**, 골든(`test/fixtures/todo-engine-legacy-windows.json`) 비교, T4 메타모픽, 고정 테스트 계정 화면 점검.
- A6-1·A6-2는 **결과 동일**이 게이트(차이 0). A6-3·A6-4·A6-5는 **의도된 차이 목록을 사전 승인**하고 그 목록과 정확히 일치해야 한다(예: A6-3 = 위 5건, 프로필별로 확인).
- 확인되지 않은 정책값에 의존하는 항목은 화면에 확정 문구로 노출하지 않는다(`school:null` → 엔진이 UNKNOWN으로 숨김 — A5에서 구현·테스트됨).

## 5. 위험
- **R1 정책 가정의 누출**: A5 테스트의 오프셋 7·3월 시작·입학 직전 1년은 가정값. A6-0 확인 전에 코드·데이터에 들어가면 틀린 일정을 확정처럼 보여준다.
- **R2 상한 해제의 파급**: `visibleSchedule`·`repeatMonthRangeOf`·체크리스트 그룹·헤더 표기·문구가 같은 36에 의존. 일부만 바꾸면 그룹/표기 불일치.
- **R3 지역 지원금 이벤트**: 상한이 올라가면 지역 지원금(만 6세까지 등)도 나타날 수 있다 — 지역별 영향은 이번 검토에서 일부 프로필만 확인했다.
- **R4 데이터 로드 순서**: 정책 파일이 늦게 로드되면 첫 화면이 `school:null`로 그려졌다가 바뀔 수 있다(A6-2에서 로드 완료 후 계산하도록 설계 필요).
- **R5 다른 세션과의 충돌**: `data/todos`·`app.js`·`index.html`·`schedule.js`를 다른 세션이 동시에 수정한 이력이 있다. A6-2~A6-4는 착수 전 작업 트리 확인과 hunk 선별 커밋이 필요.

## 9. A6-0 정책 조사 결과와 결정 (2026-10-01)

범위: A5 `ChildTimeline.computeSchool()`이 쓰는 정책 키 3개와 그 보조 사실. 코드·정책 데이터는 이 단계에서 만들거나 고치지 않았다.

### 9-1. 값과 구분 — "공식 정책값"과 "제품 정의"를 섞지 않는다

| 키 | value | 구분 | verificationStatus | 근거(source) |
|---|---|---|---|---|
| `enrollmentOffsetYears` | **7** (입학 학년도 = 출생연도 + 7) | **공식 정책값** (법령) | **확인됨** | 초·중등교육법 제13조 제1항 — "모든 국민은 보호하는 자녀 또는 아동이 6세가 된 날이 속하는 해의 다음 해 3월 1일에 그 자녀 또는 아동을 초등학교에 입학시켜야 하고, 초등학교를 졸업할 때까지 다니게 하여야 한다." 같은 해 1월 1일~12월 31일 출생이 한 코호트(교육청 취학아동명부 안내와 일치) |
| `schoolYearStartMonth` | **3** (학년도 = 3월 1일 ~ 다음 해 2월 말일) | **공식 정책값** (법령) | **확인됨** | 초·중등교육법 제24조 제1항 — "학교의 학년도는 3월 1일부터 시작하여 다음 해 2월 말일까지로 한다." |
| `preElementaryYearsBefore` | **1** | **제품 정의** (공식 정책값 아님) | **제품정의** (아래 9-2) | 법령·교육부에 "예비초등" 정의가 없다. 사용자 결정(2026-10-01, 설계 Q-C): **"예비초등 = 입학 학년도 바로 직전 학년도(3월~다음 해 2월)"**. 공식 정책값처럼 표시·표현하지 않는다 |

보조 사실(정책 키가 아님):
- **초등학교 수업연한 6년** — 초·중등교육법 제39조 → `grade` 1~6, 6학년 이후는 `AFTER_ELEMENTARY`(`stageBand`는 `null`). **확인됨.**
- **조기입학·입학연기** — 제13조 제2항(5세 또는 7세에 입학 가능). 정책값으로 다루지 않고 **`enrollmentYearOverride`(사용자 입력)가 항상 우선**한다(기존 설계 유지).
- **`semester`** — 학기 경계는 학교장이 정하는 날이라 전국 공통 값이 없다(시행령 제44조). **`semester = null` 유지.**
- **반 나이 기준(어린이집·유치원)** — `computeSchool()`에 필요하지 않아 조사 대상이 아니다.

### 9-2. verificationStatus 설계 — 정책 검증과 제품 정의의 구분

정책 파일(`data/policy/school.json`, A6-1)의 각 항목은 아래 형식을 따른다. **`kind`로 출처 유형을 구분하고, `verificationStatus`는 그 유형에 맞는 값만 허용**한다.

```jsonc
{
  "enrollmentOffsetYears": { "value": 7, "kind": "OFFICIAL_POLICY", "verificationStatus": "확인됨",
                              "source": "초·중등교육법 제13조 제1항 (국가법령정보센터)", "effectiveDate": "2026-09-11" },
  "schoolYearStartMonth":  { "value": 3, "kind": "OFFICIAL_POLICY", "verificationStatus": "확인됨",
                              "source": "초·중등교육법 제24조 제1항 (국가법령정보센터)", "effectiveDate": "2026-09-11" },
  "preElementaryYearsBefore": { "value": 1, "kind": "PRODUCT_DEFINITION", "verificationStatus": "제품정의",
                              "source": "제품 정의 — 입학 학년도 바로 직전 학년도 (설계 Q-C, 사용자 결정 2026-10-01)" }
}
```
- `OFFICIAL_POLICY`: `verificationStatus`는 `확인됨` 또는 `확인필요`. `확인됨`일 때만 사용(기존 규칙 그대로).
- `PRODUCT_DEFINITION`: `verificationStatus`는 `제품정의`(법령 검증 대상이 아니며 제품에서 정한 값). 화면·문서에서 법령 기준처럼 쓰지 않는다.
- ⚠ **A5 구현과의 차이(A6-1에서 처리, 승인 필요)**: 현재 `ChildTimeline.computeSchool`은 세 키 모두 `verificationStatus === "확인됨"`일 때만 계산한다. 위 구분을 쓰려면 **키별 허용 상태**(`enrollmentOffsetYears`·`schoolYearStartMonth` = `확인됨`, `preElementaryYearsBefore` = `제품정의`)로 검증을 조정하는 작은 변경이 A6-1에 필요하다. 이번 단계에서는 코드를 바꾸지 않았다.
- `effectiveDate`는 확인한 법령 시행일(국가법령정보센터 현행 시행본: 2026-09-11, 법률 제21424호). 법령이 개정되면 이 값을 갱신하고 `확인필요`로 되돌려 재확인한다.

### 9-4. 반영 결과 요약
- `enrollmentOffsetYears = 7`, `schoolYearStartMonth = 3`: **확인됨(공식 정책값, 현재 시행 법령 기준)**.
- `preElementaryYearsBefore = 1`: **제품 정의 채택** — 입학 학년도 바로 직전 학년도. 공식 정책값으로 표현하지 않는다.
- `semester = null` 유지, `enrollmentYearOverride`는 사용자 입력 우선(기존 설계).
- **A6-1(정책 파일 `data/policy/school.json` 생성·로더)은 다음 승인 후 시작한다.** 이 단계에서는 정책 데이터를 만들지 않았다.
