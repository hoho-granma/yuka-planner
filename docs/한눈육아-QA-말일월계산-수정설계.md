## 2. 무엇이 어떻게 틀렸나 (실측)

`schedule.js`식 `setMonth` 계산 결과:

| 출생일 | +n개월 | 현재(오류) | 올바른 값(말일 규칙) |
|---|---|---|---|
| 2026-01-31 | +1 | **2026-03-03** | 2026-02-28 |
| 2026-01-31 | +3 | 2026-05-01 | 2026-04-30 |
| 2026-08-31 | +1 | 2026-10-01 | 2026-09-30 |
| 2024-02-29 | +12 | 2025-03-01 | 2025-02-28 |

→ 1/31생은 **2월에 시작하는 월령 슬롯이 없고**(k=1이 3/3 시작, k=2가 3/31 시작) 3월에 두 슬롯이 붙는다.

### 영향 미리보기 (고정 데이터로 수정 전/후 비교 — 프로젝트 코드는 그대로, 임시 스크립트로 계산)
조건: 서울 구로구, 확인완료 혜택 + 전체 Todo 정의, 오늘 2026-09-30. `monthKeysOf`는 앱 내부 함수를 Node에서 실행할 수 없어 `displayMonth`로 단순화한 **근사**다(실제 앱의 숫자는 조금 다를 수 있음).

| 출생일 | 날짜 필드 변경(혜택 시작·마감) | 추천일(`displayDate`) 위치 변경 | 홈 분류 변경 | 비고 |
|---|---|---|---|---|
| 2026-06-20 | **0건** | 0/76 | 없음 | 대조군(20일생) |
| 2026-01-28 | **0건** | 0/76 | 없음 | 대조군(28일생 — 경계) |
| 2026-01-31 | 2건 | 3/76 | 있음 | |
| 2026-03-31 | 7건 | 19/76 | 있음 | |
| 2026-08-31 | 5건 | 16/76 | 있음 | |
| 2024-02-29 | 12건 | 12/76 | 있음 | 마감일 8건 포함 |

확인된 사실:
1. **28일생 이하는 결과가 한 글자도 바뀌지 않는다**(대조군 2개로 확인).
2. `windowStart/windowEnd`(엔진 계산)는 **한 건도 바뀌지 않는다** — 엔진 30일 근사는 이번 수정과 무관함이 실측으로 확인됨.
3. 바뀌는 것 3가지: ⒜ **혜택 신청 시작일**(`entryDate`/`fixedDate`) 최대 2~3일 앞당겨짐 ⒝ **혜택 신청 마감일**(`deadlineDate`) 앞당겨짐 — 예: 2024-02-29생 마감일 `2025-03-01 → 2025-02-28`, 105개 혜택이 `birth_relative_months` 마감 방식이라 해당 가능 ⒞ **`monthly` 월령 슬롯 범위**가 바뀌어 그 결과 **추천일 배치와 홈 "이번 달 챙길 것" 분류**가 29~31일생에서만 바뀜.
4. **마감일이 늦게 표시되던 것이 정정된다.** 오류 상태에서는 실제보다 최대 3일 늦은 마감일을 보여 줬다(사용자가 신청 가능 기간을 더 길게 오해). 말일 규칙은 이를 앞으로 당겨 정정한다. 참고: "월로 정한 기간의 마지막 월에 해당일이 없으면 그 월의 말일에 만료"라는 기간 계산 원칙(민법 제160조 3항으로 알고 있음 — **확인 필요**)과 같은 방향이다.
5. 영향 대상: **29·30·31일생**(전체의 약 10%로 추정 — 출생일 균등 가정, 실제 비율 미확인).
6. 데이터 스캔: 혜택 JSON의 월 값 855개가 **전부 정수**(비정수 0개). 함수는 정수만 받도록 정의한다(§3).

## 3. 설계

### 3-1. 공통 함수 — 신규 파일 `js/date-calc.js`

`hn-logic.js`와 같은 UMD 패턴(브라우저 전역 `DateCalc` / Node `require`). 순수 함수, DOM·Firestore 무관.

```text
DateCalc.addMonthsClamped(date: Date, n: integer) → Date
DateCalc.addYearsClamped(date: Date, n: integer)  → Date      // = addMonthsClamped(date, 12n) — Q-B 규칙 그대로
DateCalc.lastDayOfMonth(year: number, monthIndex: number) → number
```

**명세(구현은 이 문서 승인 후):**
1. 결과의 **연·월 = 원본 연·월에 n개월을 더한 달**. 넘침이 절대 일어나지 않는다.
2. 결과의 **일 = min(원본 일, 결과 월의 말일)**.
3. **시·분·초·밀리초는 원본을 보존**한다(기존 `setMonth` 방식도 보존했다).
4. `n`은 **정수**(음수·0 허용). 비정수·`NaN`·`Infinity`는 `RangeError`(오류를 조용히 삼켜 잘못된 날짜를 만들지 않는다). 현재 데이터는 전부 정수라 실제 발생하지 않으며, **데이터 정수 검사 테스트**(§5-E)가 새 데이터의 유입을 막는다.
5. **항상 원본 출생일에서 한 번에 계산한다. 결과를 다시 더하는 연쇄 호출은 금지**: `f(f(1/31,+1),+1) = 3/28`, `f(1/31,+2) = 3/31` — 다르다. 현재 모든 호출처가 `birthDate`에서 직접 계산하므로 문제없고, 이 사실을 테스트 주석과 문서에 명시한다.
6. 로컬 날짜만 다룬다(`new Date(y, m, d, …)`). `toISOString`·UTC 금지.

## 7. 설계상 충돌 보고 — Q-A2: `ageInMonths`/`ageMonthsAt`를 함께 고칠 것인가

- **현재 구조**: 개월 "수"를 세는 `ageInMonths`(`schedule.js:62`)·`ageMonthsAt`(`hn-logic.js:372`)는 `today.getDate() < birth.getDate()`이면 미완 개월로 본다. 말일 넘침 버그는 없지만 **말일 규칙과 다르다.**
- **문제**: `addMonths`만 말일 규칙으로 고치면 두 정의가 1~3일 어긋난다.
  예) 2026-01-31생 — 수정 후 1개월 기간 시작 = **2/28**, 그런데 `ageInMonths`는 2/28에 **0개월**이고 3/1에 1개월이 된다(수정 전에는 기간 시작 3/3, 나이 1개월 3/1로 우연히 비슷했다). 4/30에는 수정 후 3개월 기간이 시작되나 `ageInMonths`는 2개월(30<31).
  영향받는 소비자: 프로필 헤더 "생후 N개월"(`renderProfileHeader`), 혜택 상태 판정(`subsidyStatus`의 `ageNow` vs `minAgeMonths`), 체크리스트 현재 월령 그룹, `visibleSchedule ≤36`, `records-view`의 "생후 N개월".
- **선택지**
  - **(a)** 범위대로 `addMonths`·`addMonthsD`만. 나이 표기는 그대로 → 말일생만 1~3일 어긋남이 남음.
  - **(b)** `ageInMonths`·`ageMonthsAt`도 "`addMonthsClamped(출생일, m) ≤ 기준일`을 만족하는 최대 m"으로 재정의. 기간 시작과 개월 수가 **구성상 일치**. 28일 이하 출생은 결과 동일(속성 테스트로 전수 확인), 29~31일생만 개월 수가 1~3일 일찍 오름.
- **추천: (b)**, 단 **별도 승인 항목으로 분리**(핵심 수정과 독립 커밋). 이유: (a)는 이번 수정이 새로운 1~3일 불일치를 만든다. (b)는 표시 변경 범위가 같은 대상(29~31일생)이고 폭도 같다.
- **기존 기능 영향**: (b) 승인 시 위 소비자의 개월 수가 29~31일생에서 최대 3일 일찍 바뀜. 20일생 이하 무변경. 엔진 무관.
- (b) 채택 시 추가 테스트: 2026-01-31생 개월 수 — 02-27 → 0, **02-28 → 1**, 03-30 → 1, **03-31 → 2**, 04-29 → 2, **04-30 → 3**(수정 전 02-28 → 0, 04-30 → 2), 2024-02-29생 — 2025-02-27 → 11, **2025-02-28 → 12**, 2028-02-29 → 48.

## 9. 이 문서에서 확인하지 못한 것
1. 영향 수치는 **근사**다 — 앱 내부 `monthKeysOf`(반복 월령 포함)를 Node에서 실행할 수 없어 `displayMonth`로 단순화했고, 서울 구로구 확인완료 혜택만 사용했다. 실제 앱의 변경 건수는 다를 수 있으므로 **골든 비교(D)가 정본**이다.
2. 화면에서 오류를 직접 재현하지 않았다(코드·산술·Node 계산으로 확인).
3. 민법 제160조 3항 인용은 기억에 의한 것이라 **확인 필요**(기능 결정에는 필요하지 않음 — 말일 규칙은 사용자가 이미 확정).
4. `www/` 복사 절차, 실제 출생일 분포(영향 비율 ≈10%는 균등 가정 추정).
