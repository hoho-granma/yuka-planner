# 가족코드 시나리오와 기존 회원 이전

작성 2026-10-12. 코드·서버 로직까지 반영했고 **함수 배포 전**이다. 운영 DB는 읽지 못했다(아래 "확인하지 못한 것").

## 1. 가족코드가 바뀐 방식

| | 예전(~2.0.22) | 지금(2.0.23~) |
|---|---|---|
| 코드 | 가족마다 고정 8자리 코드 | **초대코드**: 관리자가 만들면 24시간 유효, 1회용 |
| 합류 | 코드만 입력하면 바로 합류 | 코드 입력 → **참여 요청** → 관리자 **승인** |
| 권한 | 코드를 아는 사람은 누구나 | `familyAccess/{가족}/members/{uid}` 승인 문서가 있는 계정만 |
| 관리자 | 없음 | 가족을 만든 사람 = ADMIN. 관리자만 초대·승인·해제 |

그래서 예전 코드는 더 쓸 수 없고, "가족코드가 안 된다"는 증상의 대부분은 이 변화에서 나온다.

## 2. 시나리오

**A. 새 가족을 시작한다 (엄마)**
가입 → 가족 만들기 → 관리자가 된다. 가족코드는 따로 없다. 가족을 부를 때 "가족 초대·참여 관리 → 초대코드 만들기".

**B. 가족이 합류한다 (아빠·조부모·이모님)**
1. 관리자가 초대코드를 만든다(관계 선택. 같은 관계의 미연결 구성원 자리가 있으면 그 자리가 자동으로 걸린다).
2. 합류할 사람이 가입 화면 "가족 코드로 함께하기"에 코드를 넣는다 → 참여 요청.
3. 관리자가 같은 화면에서 승인한다 → 합류 완료. 코드는 그때 사용 끝.
- 코드가 24시간이 지났거나 이미 쓰였거나 새로 만들어서 이전 것이 취소됐으면 "초대코드가 없거나 만료됐어요" 안내가 뜬다.

**C. 기존 회원 (예전 방식으로 가입한 사람, 예: 수아네 중빠)**
- 승인 문서가 이미 있으면(2026-10-08 전환 때 만든 9개) 그대로 로그인된다.
- 승인 문서만 없고 예전 가입 기록은 남아 있으면 → **2.0.47부터 로그인 때 자동 이전**(아래 3번). 코드 입력이 필요 없다.
- 가족 기록 자체가 사라졌으면(고아 계정) → 관리자에게 초대코드를 받아 "가족 연결 다시 하기"로 합류. 예전엔 "이미 연결된 가족이 있어요"에서 막혔고 이제는 통과한다.
- 관리자가 일부러 해제한 계정은 되살리지 않는다. 다시 합류하려면 새 초대가 필요하다.

**D. 가족 만들기를 이미 눌러 새 가족이 생긴 경우**
예전 가족 데이터는 서버에 남아 있고 새 가족은 비어 있다. 이전 기록이 필요하면 새 가족을 쓰지 말고 C로 복구해야 하므로 먼저 알려야 한다(새 가족은 나중에 정리).

## 3. 자동 이전 (`claimLegacy`, 서버 함수 `familyAccess`의 새 액션)

로그인 직후 상태가 `REVOKED`/`NONE`이면 앱이 한 번 호출한다.

증거(서버만 쓰는 값 둘이 일치): `accounts/{uid}.householdId·memberId` 와 `families/{가족}/members/{memberId}.uid == uid`, 그 구성원이 삭제되지 않았고 승인 문서가 아직 없음.
- 가족을 만든 계정(`createdByUid`)이면 ADMIN, 아니면 MEMBER 로 승인 문서를 만든다(`migratedFromLegacy:true` 표시).
- 구성원 자리·색·이름은 그대로라 일정의 담당자 표시가 유지된다.
- 증거가 없거나 `REVOKED` 문서가 있으면 아무것도 하지 않는다. 남의 자리를 가리키는 계정도 거절한다.
- 같은 변경으로 새 가족 만들기·초대 합류가 "승인 문서 없음 = 이미 연결됨"으로 막히던 것을 풀었다. 복구 가능한 예전 구성원은 여전히 막고(먼저 이전), 증거 없는 고아 계정만 통과시킨다.

검증: `node test/family-access-legacy.test.js` (메모리 가짜 DB. 이전·거절·고아 합류 시나리오). 에뮬레이터 테스트는 이번에 돌리지 않았다.

## 4. 배포 순서

1. 운영 DB를 읽기 전용으로 점검(아래 표) — 계정별로 어느 경우인지 확인.
2. `functions/family-access.js` 변경을 `familyAccess` 함수에만 배포(사용자 승인 필요. 규칙·데이터는 건드리지 않는다).
3. 앱 2.0.47 push(GitHub Pages 자동 배포).
4. 중빠 계정으로 로그인해 확인. 안 되면 5번.
5. 관리자(수아엄마)에게 "가족 초대·참여 관리 → 초대코드 만들기(아빠)" → 중빠가 "가족 연결 다시 하기"에서 입력 → 승인.

### 점검할 것 (읽기 전용)

| 컬렉션 | 볼 것 |
|---|---|
| `accounts/{uid}` | `householdId`·`memberId` 가 있는가 |
| `familyAccess/{가족}/members/{uid}` | 위 계정마다 문서가 있는가, `status` 가 ACTIVE 인가 |
| `families/{가족}/members/{memberId}` | `uid` 가 그 계정과 같은가, `deletedAt` 이 없는가 |
| `families/{가족}` | `createdByUid`(관리자 후보)가 있는가 |

판정: 계정에 householdId 가 있고 members.uid 가 일치하는데 승인 문서가 없다 → 3번 자동 이전 대상. 계정에 householdId 가 없다 → 합류 코드 필요(B). householdId 가 있는데 가족 문서가 없다 → 고아(C의 세 번째).

## 5. 확인하지 못한 것

- 운영 Firestore 상태. Firebase CLI 로그인 토큰을 꺼내 직접 읽는 방식은 자동 권한 검사에서 거부돼 읽지 못했다. 위 점검표를 사용자가 직접 보거나, 읽기 권한을 따로 허용해 주면 진행한다.
- 중빠 계정이 실제로 어느 경우(승인 문서 없음 / householdId 없음 / 고아)인지.
- 실기기 로그인 흐름.
