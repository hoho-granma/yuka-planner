## 저장 구조

```text
families/{familyId}/growthActivities/{activityId}
families/{familyId}/growthRecords/{recordId}
Storage: families/{familyId}/growthRecords/{recordId}/{attachmentId}
```

아이 프로필은 children/{childCode}, 가족 소속 관계는 families/{familyId}/childLinks/{childKey}를 사용한다. 기록은 가족 소유이며 childKey를 반드시 저장한다. 새로운 최상위 growth 컬렉션을 만들지 않는다.

### 활동

childKey, group(school/academy/activity/home), name, status(active/archived), linkedScheduleIds[], createdByUid, createdAt, updatedAt.

교육트렌드에서 등록한 학원 일정은 기존 schedules 문서를 연결한다. 반복 회차마다 새 활동을 만들지 않는다. 활동 ID는 고유하며 이름만으로 자동 병합하지 않는다. 학원 이름이 같은 서로 다른 아이의 활동은 별개다. 메인 잎 크기는 활동 수가 아니라 실제 성장기록 수로 계산한다.

### 기록

schemaVersion, childKey, activityId, group, recordDate(YYYY-MM-DD), title, text, attachment metadata[], createdByUid, updatedByUid, createdAt(server timestamp), updatedAt(server timestamp), legacyCreatedAt(optional), deletedAt(optional), importKey(optional).

- 이미지 본문/base64/Blob은 Firestore에 넣지 않는다.
- 첨부 메타데이터에는 attachmentId, storagePath, contentType, size, uploadState를 둔다. 공개 영구 URL을 저장하지 않고 권한이 있는 클라이언트가 이미지를 가져온다.
- 날짜별 기록은 recordDate 내림차순, createdAt 내림차순으로 조회한다.
- 연결 활동이 없어지거나 이름이 바뀌어도 기록은 유지한다. 활동 삭제는 기본 보관 처리다.
- 기록 완료/할일 완료/일정 참석을 임의로 같은 상태로 취급하지 않는다.

## 공유·권한 제안 (권장 정책 승인됨)

읽기: 로그인했고 해당 가족의 살아 있는 members 문서에 uid가 연결된 사용자만.

권장: 엄마·아빠·보호자는 가족의 모든 아이 기록을 작성·수정할 수 있고, 아이 계정은 자기 childKey의 기록만 작성·수정한다. createdByUid는 생성 시 현재 UID와 일치하고 이후 불변이다. role·가족 소속은 사용자가 폼에서 보낸 값이 아니라 서버 구성원 문서를 기준으로 판정한다. 아이 계정과 childKey 연결 필드가 현재 없으면 먼저 명시적으로 연결해야 한다. 다른 아이의 정보에 접근할 수 없도록 Firestore와 Storage 모두 같은 판정을 적용한다.

대안: 작성자만 수정, 가족은 열람만. 사용자가 권장 정책을 승인했으므로 보호자 공동 수정·아이 본인 기록 수정으로 구현한다. 초안은 아직 운영 배포 전이다.

삭제: 기본 소프트 삭제, 가족의 지정 관리자/기록 작성자 범위는 정책 선택. 첨부 정리 작업은 삭제 유예 이후 실제로 삭제된 기록만 처리한다. 역할 변경을 자기 권한 상승에 사용할 수 없도록 구성원 관리 규칙도 함께 검토한다.

## 기기 기록 이전

1. 로그인한 계정·가족·아이 연결을 먼저 확인한다. 기존 scope를 UID와 childCode에 정확히 매핑한다. 불명확한 scope는 사용자에게 대상 확인을 요청하고 임의로 배정하지 않는다.
2. 기기에 저장된 텍스트와 사진의 이전 가능 건수를 표시하고, 로컬 원본은 유지한다. 다른 기기의 IndexedDB는 서버 관리자가 조회할 수 없으므로 각 기기에서 이전을 실행한다.
3. importKey = hash(원래 계정 scope + 기존 기록 ID). 같은 로컬 기록을 재실행해도 같은 서버 문서가 되도록 한다. 서로 다른 기기의 독립 ID를 제목/날짜가 같다는 이유로 자동 병합하지 않는다.
4. 기록 초안을 준비하고 첨부를 해당 가족·기록 경로로 업로드한다. 실패 시 재시도 위치를 저장한다. 동일 importKey의 내용을 덮어쓰기 전에 서버 수정 여부를 확인한다.
5. 텍스트·날짜·제목·이미지 크기와 해시를 검증한 뒤 이전 완료 표시. 서버 읽기로 검증되지 않은 사진은 완료로 표시하지 않는다.
6. 가족의 다른 기기에서 확인 후 서버를 기본 읽기 경로로 전환한다. 기기 원본 제거는 별도 명시적 동의 전에는 하지 않는다.

## 조회·인덱스·동기화

기본 조회는 family 하위에서 childKey를 필수 조건으로 한다. 필요 인덱스: childKey + deletedAt + recordDate(desc) + createdAt(desc), childKey + activityId + deletedAt + recordDate(desc). 실제 쿼리 형태 확정 후 필요한 인덱스만 배포한다. 첫 화면은 최근 20건, 추가 읽기는 커서 페이지네이션.

메인 잎 건수는 실제 서버 기록(삭제 제외) 집계로 계산한다. 먼저 Firestore count 쿼리와 저장 성공 후 재조회로 구현하고, 클라이언트가 임의 count를 직접 수정하도록 허용하지 않는다. 규모가 커지면 트랜잭션/서버 트리거 기반 집계로 전환한다.

기록 저장 성공 시 활동/나무/날짜 목록을 함께 갱신하고, 실패하면 완료처럼 표시하지 않는다. 이미지 업로드는 Firestore 오프라인 대기열과 별개이므로 uploadState와 재시도 UI가 필요하다.

## 구현 순서

1. 가족 공동 수정 vs 작성자 전용 정책, 아이 계정의 childKey 연결, 삭제 권한 확정.
2. activity/record 스키마·쿼리·첨부 저장소·규칙·이전 재시도 구현 및 테스트.
3. Firestore/Storage 규칙과 필요 인덱스 배포·권한 검증.
4. 앱 배포 후 각 실제 기기에서 이전, 데이터 검증, 서버 기본 읽기 전환.
5. 다른 가족 차단·형제 분리·재시도 중복·첨부 실패·기록 수정 충돌 검증.

현재 일정/할일 규칙은 생성·수정에 작성자 제한이 없다. 이 규칙을 성장기록에 그대로 복제하지 않는다.


## 기존 휴대폰 기록의 추후 이전

현재 운영 기록과 사진 Blob은 해당 앱 출처의 IndexedDB `hannun-growth-records`에 저장된다. 서버 저장을 활성화한 뒤, 기록이 남아 있는 같은 기기·같은 앱 출처에서 동일 아이를 열면 `기기 기록 서버로 옮기기`를 제공하는 구현을 준비했다. 기기 원본은 삭제하지 않는다.

- scope(아이/계정 범위)를 정확히 확인하고 다른 범위의 기록은 이전하지 않는다.
- 기록 ID와 scope로 이전 ID를 생성하고 내용 지문을 검사하여 같은 기록을 다시 올려도 중복 생성하지 않는다.
- 사진은 업로드 후 내려받아 크기/해시가 맞는지 확인한 뒤 문서를 저장한다. 실패 항목은 다시 시도할 수 있으며 성공으로 표시하지 않는다.
- 서버에서 가족이 수정한 기록은 이전 재시도로 덮어쓰지 않는다.
- 서버 활성화 전 브라우저 데이터 삭제, 앱 출처 변경, 기기 초기화 시 로컬 기록에 접근할 수 없을 수 있다. 서버가 다른 출처로 출시되면 기존 출처에서 내보내기/이전 경로가 별도로 필요하다.
- 아직 서버 저장 스위치는 OFF이며 Storage 저장소·결제 설정 준비 전이다. 기존 운영 기록은 자동 업로드되지 않는다.

## 2026-10-08 서버 저장 활성화 — v2.0.21

사용자의 명시적 승인 후 Firebase Storage 서비스 계정에 `roles/firebaserules.firestoreServiceAgent` 역할을 추가했다. 실제 Firebase SDK 인증 검사 8건을 통과했다: 사진 업로드/바이트 다운로드 일치, 미로그인/다른 가족 사진 차단, 성장기록 저장/조회 및 외부 차단, 일정·할일 저장/조회. 모든 임시 계정·가족 문서·사진을 정리했다. 이는 서버/SDK 검사이며 휴대폰 UI 직접 조작 검증은 아니다.

Firestore 성장기록 규칙과 Storage 가족 전용 규칙은 배포했고 CORS도 설정했다. `growthServer:true`로 활성화한다. 기존 기기 기록은 자동 이전하지 않고, 같은 로그인·아이 범위의 `기기 기록 서버로 옮기기` 버튼에서 이전한다. 기기 원본은 삭제하지 않는다. 서버에서 수정된 기록은 재이전으로 덮어쓰지 않는다. IndexedDB 저장 데이터나 앱 출처를 삭제/변경하지 말아야 한다.

사진은 현재 15MB까지 원본 저장하며 압축·썸네일·페이지 단위 조회는 후속 최적화다. 현재 날짜/시간은 클라이언트 밀리초 기준이며 서버 시각 전환은 후속 설계다.
