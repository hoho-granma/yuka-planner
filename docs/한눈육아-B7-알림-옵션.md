# B7 알림 옵션 — 선택지·장단점·추천

상태: 결정 대기(구현 없음). 근거는 현재 repo에서 확인된 사실만 쓰고, 확인 못 한 것은 **추가검증 필요**로 표시합니다.

## 현재 사실
- 앱에 알림 기능이 없다(docs/한눈육아-확장설계-v1.md: "알림 기반은 없다"). iOS 네이티브 래퍼는 Capacitor이고 `@capacitor/cli·core·ios`만 있어 로컬/푸시 알림 플러그인이 없다.
- 웹에는 "정해진 시각에 앱이 닫혀 있어도 뜨는 로컬 예약 알림"이 없다. 앱이 꺼진 상태의 알림은 **서버가 푸시를 보내야** 한다.
- Firebase 프로젝트(`yuka-planner`)는 Firestore만 쓰고 있다. 서비스워커(`sw.js`)는 앱 파일 캐시용이고 푸시 처리는 없다.
- 알림에 쓸 일정 데이터는 이미 앱 안에 있다: 홈 '다가오는 우리 가족 일정' 카드(가족 일정), AUTO 접종·검진(기간), 예약 일정 연결(autoRef).

## 옵션 A. 홈 화면 웹앱 + 웹푸시(iOS 16.4+)
- 방식: 사용자가 사파리에서 '홈 화면에 추가'한 웹앱에서 알림 권한을 허용 → 웹푸시(서비스워커 push 이벤트)로 수신. iOS에서 웹푸시는 홈 화면에 추가된 웹앱에서만, iOS/iPadOS 16.4 이상.
- 장점: 앱스토어 심사·네이티브 코드 없이 웹 코드만. 안드로이드/PC 브라우저에도 같은 방식 확장.
- 단점: 설치(홈 화면 추가) + 권한 허용 2단계로 도달률 낮음. **발송 서버가 필요**(예약 시각에 보내는 주체). iOS 웹푸시 동작 제약(백그라운드 제한, 설정 의존)은 추가검증 필요.
- 필요 작업: 서비스워커 push 핸들러·권한 UI·구독 정보 저장·발송 로직(옵션 B와 겹침).

## 옵션 B. FCM(Firebase Cloud Messaging) 조건부 도입
- 방식: FCM으로 토큰을 받아 서버(예: Cloud Functions 예약 실행)가 대상 기기에 푸시 발송. 웹(옵션 A와 같은 기술 위에서 FCM이 발송 서비스) 또는 Capacitor iOS 앱(APNs 연동) 모두 후보.
- 장점: 앱이 꺼져 있어도 도달, 가족 구성원별 발송 가능, 이미 쓰는 Firebase 생태계.
- 단점: 서버 로직(일정→발송 시각 계산·중복 방지·해지)과 **토큰 저장(개인정보·보안 규칙·스키마 변경)** 이 필요해 범위가 크다. Cloud Functions 사용 가능 여부·요금제(Blaze 필요 여부)는 **추가검증 필요**. iOS 네이티브는 푸시 플러그인 추가·APNs 키·앱 재배포 필요(추가검증 필요).
- '조건부' = 사용자가 알림을 켜고 토큰을 등록한 경우에만 발송, 기본은 꺼짐.

## 옵션 C. 앱 내 '오늘·곧' 배지만 (알림 발송 없음)
- 방식: 앱을 열었을 때 홈/캘린더에 '오늘 · 곧(3일 이내)' 배지와 목록을 강조. 서버·권한 없음. 기존 홈 카드(F1)·월/주 캘린더·AUTO 기간 데이터를 재사용.
- 장점: 비용·개인정보·규칙 변경 0, 구현 작음, 플래그 OFF 시 불변 보장 쉬움.
- 단점: 앱을 열지 않으면 알려 주지 못함(진짜 '알림'은 아님). 홈 화면 앱 아이콘 배지(Badging API)로 보완 가능한지는 **추가검증 필요**.

## 비교
| | A 웹푸시(iOS16.4+) | B FCM | C 앱 내 배지 |
|---|---|---|---|
| 앱이 꺼져도 알림 | 가능(서버 필요) | 가능(서버 필요) | 불가 |
| 서버·비용 | 필요 | 필요(요금제 확인) | 없음 |
| 개인정보/규칙 변경 | 구독 저장 필요 | 토큰 저장 필요 | 없음 |
| 사용자 설정 부담 | 홈 화면 추가+권한 | 권한(+설치) | 없음 |
| 구현 크기 | 큼 | 가장 큼 | 작음 |

## 사용자 결정이 필요한 것
1. 알림을 **앱이 꺼져 있어도** 받아야 하는가(A/B가 필요한가), 아니면 앱을 열 때 보이면 충분한가(C).
2. 대상 범위: 가족이 직접 만든 예약 일정만 / 접종·검진 같은 AUTO까지.
3. 시각 정책: 전날 저녁·당일 아침·시작 1시간 전 등 기본값(문구 승인 포함).
4. 가족 공유: 일정 담당자(엄마/아빠)에게만 보낼지, 가구 전체에 보낼지.
5. 서버 운영·비용·토큰 저장(개인정보 처리) 허용 여부 — A/B를 택할 때만.

## 추천안 (1개)
**1단계로 옵션 C(앱 내 '오늘·곧' 배지) 먼저**, 사용 반응을 본 뒤 필요하면 옵션 B(FCM, 웹푸시 포함)를 후속으로. 이유: 서버·권한·개인정보·규칙 변경 없이 바로 가치를 주고, 플래그 OFF 불변을 지키기 쉽다. A와 B는 같은 발송 서버가 필요해 따로 하지 않고 B로 묶어 판단한다.

## 추가검증 필요 (요약)
- iOS 16.4+ 홈 화면 웹앱 웹푸시의 실제 동작 제약(백그라운드·권한 재요청)과 FCM의 iOS 웹푸시 지원 범위
- Firebase 요금제(Cloud Functions/예약 실행 가능 여부)
- Capacitor iOS 앱에 푸시/로컬 알림 플러그인을 추가할 때의 앱 재배포·심사 부담
- 홈 화면 앱 아이콘 배지(Badging API) 사용 가능 여부
