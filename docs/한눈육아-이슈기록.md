## I-1. `ageInMonths`/`ageMonthsAt`와 새 말일 규칙의 1~3일 불일치
- **현재**: 개월 "수"를 세는 `ageInMonths`(`schedule.js:62`)·`ageMonthsAt`(`hn-logic.js:372`)는 `오늘 일자 < 출생 일자`이면 미완 개월로 본다. 월 계산(`addMonths*`)은 Q-A로 말일 규칙이 됐다.
- **문제**: 29~31일생은 월령 기간 시작(예: 1/31생의 1개월 = 2/28)과 개월 수 표기("생후 N개월"이 늘어나는 날 = 3/1)가 1~3일 어긋난다. 영향: 프로필 헤더 "생후 N개월", 혜택 상태 판정(`subsidyStatus`의 `ageNow`), 체크리스트 현재 월령 그룹, `visibleSchedule ≤36`, `records-view`의 "생후 N개월".
- **선택지**: (a) 그대로 둔다 (b) "`addMonthsClamped(출생일, m) ≤ 기준일`을 만족하는 최대 m"으로 재정의(28일 이하 출생은 결과 동일, 29~31일생만 개월 수가 최대 3일 일찍 오름).
- **결정**: 이번 Q-A 범위에서 제외(사용자). 이 불일치는 Q-A 수정의 실패가 아니라 별도 이슈. 이후 `ChildTimeline` 단계에서 재검토.
- **예시(2026-01-31생)**: 개월 수는 02-28에 0개월, 03-31에 2개월, 04-30에 2개월(옛 규칙 유지). 새 월 계산이 말일로 보정하는 날(02-28, 04-30)과 어긋난다.

## I-2. `calAdd`(app.js:452)의 주석이 실제와 다르다
- 주석 "엔진의 addMonths는 30.4375일 근사"는 실제 엔진 값(`MONTH_DAYS = 30`)과 다르다. `calAdd` 자체는 말일 보정이 이미 되어 있어 동작에는 문제 없다. 주석 정정만 필요. 이번 범위 밖(`app.js` 무변경 조건).

## I-3. 엔진 30일 근사의 누적 오차
- `todo-engine.js`의 `MONTH_DAYS=30` 때문에 n개월 창이 `출생 + n×30일`로 계산되어 나이가 많을수록 앞당겨진다(36개월 ≈16일, 72개월 ≈32일, 144개월 ≈63일). 24개월 이후 구간을 가진 Todo 31개 중 36개월 초과 10개(`LF-02`, `SF-01`, `VX-DTAP`, `VX-IPV`, `VX-MMR`, `VX-JEV`, `SB-04`, `SB-08`, `SB-09`, `SB-12`)가 가장 영향이 크다.
- 처리: 확장 설계 2단계 §13(연령 엔진 트랙 A). Q-G 조건 — 기존 항목의 `basis` 전환은 항목별 승인 + 전후 날짜 차이표 + 골든 스냅샷 검증.

## I-4. 혜택 데이터의 `deadlineValue` 형식 오류
**발견 경위**: `test/data-month-integers.test.js`(월 값 정수 검사)를 작성하다가 발견. 이전 사전 점검(월 값 855개 "전부 정수")은 **문자열·객체 모양 오류를 검사하지 않아 틀린 결과**였다(내 검사가 숫자 타입의 소수만 봤다).

| 항목 | 위치 | HEAD(배포 커밋) 상태 | `deadlineType` / `deadlineValue` | 수정 전 코드의 동작 |
|---|---|---|---|---|
| `GGM-GWACHEON-03` | `gyeonggi/과천시/subsidies.json` | **확인완료(노출)** | `age_window` / 문자열 `"96~155개월(만 8세~13세 미만)"` | `s.deadlineValue.maxMonths`가 `undefined` → `addMonths(birth, undefined)` = **Invalid Date**. 화면 문구는 "생후 undefined~undefined개월 사이 신청" |
| `GGM-YANGJU-04` | `gyeonggi/양주시/subsidies.json` | **확인완료(노출)** | `age_window` / 숫자 `36`(객체가 아님) | 위와 동일(Invalid Date + "undefined~undefined") |
| `MAPO-001` | `seoul/districts/마포구.json` | 확인완료(노출) → **작업 트리에서는 `확인필요`로 바뀌어 미노출** | `birth_relative_months` / 문자열 `"12"` | `getMonth() + "12"`가 문자열 이어붙이기가 되어 마감일이 **2068-09-19**(의도 2027-06-20) |

- **Q-A 수정과의 상호작용(핵심)**: 승인된 정책대로 `DateCalc.addMonthsClamped`가 비정수 월을 `RangeError`로 거부하면, 위 항목이 노출되는 지역(과천시·양주시)에서 **`buildSchedule`이 예외로 중단되어 일정 계산 전체가 실패**한다. 실행으로 확인: 과천시·양주시 = 수정 전 정상(Invalid Date 1건) / 수정 후 `RangeError`. 수원시·서울 구로구는 양쪽 정상.
- 사용자 데이터(배포 커밋)에 이미 있는 오류이며 Q-A로 생긴 것이 아니다. 그러나 `RangeError` 정책이 "조용한 잘못된 화면"을 "지역 전체 화면 실패"로 바꾼다.
- **결정(2026-09-30, 사용자): A안 승인.** `DateCalc`는 엄격하게 `RangeError`를 유지하고, `schedule.js addMonths`·`hn-logic.js addMonthsD` 래퍼가 그 항목만 Invalid Date로 남기며(수정 전과 동일한 상태) `console.warn`으로 기록한다(항목 id 포함, 같은 경고는 1회). 잘못된 값을 정상 날짜로 보정하지 않고 A'의 옛 `setMonth` 폴백은 쓰지 않는다. 데이터 가드 테스트는 `GGM-GWACHEON-03`·`GGM-YANGJU-04` 2건만 이슈 번호와 함께 **알려진 위반**으로 허용하고, 그 밖의 새 위반(`MAPO-001`이 확인완료로 바뀌는 경우 포함)은 계속 실패한다. 이 3건의 데이터 자체는 이번 작업에서 수정하지 않았다.
- **검증**: 과천시·양주시는 수정 전/후 모두 정상 완료(각 75건/71건, 해당 항목만 Invalid Date, 수정 후 경고 1건씩). 수원시·서울 구로구·서울 마포구는 변화 없음.
- **선택지(결정 전 검토 내용)**
  - **A. 경계 래퍼에서 격리(채택)**: `schedule.js addMonths`·`hn-logic.js addMonthsD` 래퍼가 `RangeError`를 잡아 그 항목만 Invalid Date로 처리하고 `console.warn`. `DateCalc`와 데이터 가드 테스트는 엄격하게 유지. 잘못된 항목은 수정 전과 같은 결과(Invalid Date)이고 앱 전체는 중단되지 않는다. 다른 지역·정상 항목 영향 없음. (`MAPO-001` 문자열 `"12"`는 수정 전 2068 → Invalid Date로 바뀌나 작업 트리 데이터에서는 미노출)
  - **A'. 완전 동일 유지**: 잘못된 입력에 한해 옛 `setMonth` 계산으로 폴백(수정 전과 바이트 단위 동일, 옛 버그 코드가 래퍼에 남음).
  - **B. 데이터를 먼저 고친다**: 3건을 올바른 형식(`{minMonths, maxMonths}` / 숫자)으로. 이번 작업의 "데이터 변경 금지" 조건과 데이터 트랙 소유 문제이고, 배포 순서가 코드와 묶인다. 양주시 `minMonths` 등은 원 출처 확인이 필요.
  - **C. `RangeError` 정책 유지 + 데이터 수정 전까지 Q-A 배포 보류.**
- **데이터 가드 테스트**: 알려진 위반 목록(허용 목록, 이슈 번호 표기)으로 2건만 허용한다. 데이터가 고쳐지면 `test/data-month-integers.test.js`의 `KNOWN_VIOLATIONS`에서 해당 줄을 지운다(고쳐졌는데 남아 있으면 안내만 출력).
- **후속(데이터 트랙)**: 과천시 `GGM-GWACHEON-03`은 `{minMonths:96, maxMonths:155}`로, 양주시 `GGM-YANGJU-04`는 객체 형식(최솟값은 원 출처 확인 필요)으로 고쳐야 화면의 "생후 undefined~undefined개월 사이 신청" 문구가 사라진다.

## I-6. 작업 트리 동시 수정
Q-A 작업 중 `index.html`(`css/style.css?v=47 → 48` 한 줄)과 `css/style.css`(한 줄), `data/subsidies/**`에 **Q-A와 무관한 미커밋 수정**이 생겼다. Q-A 커밋에는 포함하지 않는다. `index.html`은 Q-A의 스크립트 태그 수정과 같은 파일이므로 **Q-A hunk만 스테이징**해야 한다(`git add -p` 불가 환경 → HEAD 기준으로 만든 사본을 인덱스에 직접 올리는 방식).
또한 `www/`는 iOS용 변형(Firebase vendor 로컬 사본, 서비스워커 등록 없음, `sw.js` 없음)이라 루트 파일을 통째로 복사하지 않고 Q-A 변경분만 반영했다.
