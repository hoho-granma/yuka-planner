### 1-2. 저장 방식 (localStorage)

- `yukjigi_profile` : 이름·생년월일(ISO)·birthOrder·stage·시도·시군구·photoDataUrl(240px base64)
- `yukjigi_completed` : `{ [eventId]: { done, todo_id, occurrenceKey, recordType, recordedAt } }`
  - eventId = `todoId__occurrenceKey` (지원금은 `SEOUL-001` 처럼 단일 id)
  - MILESTONE형은 `${id}__milestone` 키가 추가로 생김
  - 구버전 값 `true` 는 엔진이 무시(알려진 비호환)
- `hannun_family_code` : 가족코드
- 아이는 **한 명만** 저장된다. "새 아이 추가"는 프로필을 지우고 새 코드를 발급하는 동작(현재 아이의 코드는 나중에 재입력해야 복구).

### 1-3. 가족코드 동기화 (v1, 실사용)

- Firestore `families/{6자리코드}` 문서 하나에 `{ profile, completed, updatedAt }` 통짜.
- `completed` 는 `update()` 로 **맵 전체 교체** — 두 기기가 동시에 체크하면 마지막 쓰기가 이김(현재도 존재하는 위험).
- 프로필 사진(base64)이 이 문서에 같이 들어간다 → 문서 1MB 한도에 사진·기록이 함께 쌓임.
- 수신은 `onSnapshot` 으로 profile/completed를 통째로 덮어씀.
- API 키 하드코딩(Firebase 웹 키는 원래 공개값이라 그 자체는 문제 아님, **보안은 규칙에 달림**). 배포된 규칙이 무엇인지 이 저장소로는 확인 불가.

### 1-4. 일정 데이터의 실제 성격 — 이번 개편의 핵심 발견

엔진은 **"날짜"가 아니라 "기간(window)"** 을 계산한다. 서울 구로구·생후 5개월 샘플로 측정(활성 99건):

| 성격 | 건수 | 비고 |
|---|---|---|
| 기간 ≤60일 (현재 코드가 `isDateSpecific=true`로 취급) | 29 | 접종 18, 발달 3, 이유식 4 등. **windowStart는 "접종 가능 시작일"이지 예약일이 아님** |
| 기간 >60일 | 50 | 안전·구강·이유식 등 |
| 기간 없음(열린 구간) | 8 | |
| 마일스톤 보고 대기 | 5 | 뒤집기 시작 등 |

즉 **지금 데이터에 "이날 하세요"라고 말할 수 있는 확정 예정일은 사실상 없다.**
확정 날짜로 볼 수 있는 것은 ① 지원금 신청 마감일(출생일 기준 상대 일수/개월) ② 출산예정일 ③ 사용자가 직접 입력한 완료일 뿐이다.
현재 달력은 "그 달 항목을 월 전체에 고르게 분산 배치"(`computeDisplayDayMap`)하는데, 이 날짜는 **어떤 데이터에도 없는 값**이다.
→ 지시서 §4-2 "임의로 날짜를 생성하지 않는다"와 정면으로 충돌하므로 이 함수를 폐기한다.

### 1-5. 기존 기능 중 개편에서 재사용 가능한 것

- `eventItemHtml`, 상세 바텀시트(`openDetail`), 완료 토글·완료일 입력(`toggleComplete`/`setCompletionDate`), 월령 아코디언(`renderChecklistTab`), 카테고리 색(`CATEGORY_META`), 지원금 활성 판정(`subsidyIsActiveNow`), 프로필 시트(`showProfileSheet`).
- 지원금도 `completed[id]` 로 완료 처리가 이미 된다 → **"신청 완료"는 새 저장소 없이 기존 완료 상태를 재사용**할 수 있다.

### 1-6. 지시서 요구 vs 현재 코드의 간극

| 요구 | 현재 | 간극 |
|---|---|---|
| 아이 전환 | 아이 1명. 전환 개념 없음 | 다중 아이 저장 구조 필요 (§5-1) |
| 부모 직접 성장·활동 기록 | 없음 | 신규 데이터 + 동기화 (§5-2) |
| 기록 사진 첨부 | 프로필 사진만 | 저장소 필요 (§5-3) |
| 기록 작성자 표시 | 계정 없음 | 기기별 표시명으로 대체 검토 |
| 지원금 "신청 상태" | 완료 토글로 대체 가능 | 신규 저장소 불필요 |
| 공식 신청 페이지 링크 | `officialUrl` 있음 | 유지 |
| 자동 테스트 | 엔진/규칙 로직 node 테스트만, UI 테스트 없음 | 브라우저 수동 검증 필요 |

## STEP 2. UX 구조 설계

### 2-1. 내비게이션

하단 탭 4개: **홈 · 캘린더 · 기록 · 지원금**. 상단 세그먼트 탭 제거.
체크리스트는 탭이 아니라 홈의 "전체 할 일 보기" → **전체 할 일 화면(서브 화면, 뒤로가기 있음)**. 월령 아코디언·완료 하단 이동·그룹 카운트 유지.
가족 공유는 프로필 카드 시트(기존 위치)에서 접근 — 탭 추가 없음.

### 2-2. 일정 3유형 (정직한 표기 규칙)

| 유형 | 정의 (데이터 근거) | 표기 |
|---|---|---|
| **예정일** | 실제 날짜가 데이터에 있는 것: 지원금 마감일, 출산예정일, (사용자가 입력한 완료일) | 달력 칸에 **채운 점** + "N월 N일까지" |
| **권장 기간** | 엔진의 windowStart~windowEnd (≤60일 폭) | 달력 칸에 **연한 띠**(기간에 걸친 날들) + "N/N~N/N 사이" |
| **월령별 체크** | 폭이 넓거나 열린 항목, 마일스톤형 | **달력 칸에 찍지 않음.** 달력 아래 "이 달 월령 체크" 목록 + "그때그때" |

- 60일 기준은 기존 `DATE_SPECIFIC_MAX_WIDTH_DAYS` 를 그대로 재사용(새 기준을 만들지 않음). 이름만 `isDateSpecific` → `scheduleKind: 'fixed'|'window'|'monthly'` 로 세분화.
- `computeDisplayDayMap` 삭제. 날짜 선택 패널은 "이 날 예정" / "이 날이 기간에 포함된 권장" 두 묶음.
- 월간 진행률 = (그 달과 겹치는 예정일·권장기간·월령체크 항목 중 실제 `completed` 인 수) / 전체. 기준을 화면 라벨에 명시("이번 달 확인할 항목 N개 중 M개 완료").

### 2-3. 화면 와이어프레임

**홈**
```
┌─────────────────────────────┐
│ 👶 은찬 · 생후 5개월    [⇄]  │  ← 프로필(탭=프로필 시트, ⇄=아이 전환)
│ 📍 서울 구로구               │
├─────────────────────────────┤
│ 오늘 챙길 것          3      │  ← 진행 중인 권장기간+지금 열린 예정일, 미완료 우선
│ ○ B형간염 3차  9/1~9/30     │
│ ○ …                         │
│  (없으면) "오늘 급한 일은 없어요 🌿" │
├─────────────────────────────┤
│ 이번 달 주요 일정 (검진·접종·발달) │  카테고리 색 점, 최대 4개 + 더보기→캘린더
├─────────────────────────────┤
│ ⚠ 신청 가능한 지원금  (주황 강조 카드) │ 마감 임박(D-30 이내) 먼저, 최대 3개 → 지원금 탭
├─────────────────────────────┤
│ 다음 달 미리보기  → 캘린더(다음 달) │
├─────────────────────────────┤
│ 최근 기록  (완료 최근 3건)  → 기록 상세 │
├─────────────────────────────┤
│ [ 전체 할 일 보기 › ]        │
└─────────────────────────────┘
 홈 | 캘린더 | 기록 | 지원금
```
- "오늘의 할 일" 정의(데이터 근거만 사용): 엔진 status가 지금 시점에서 열려 있는 것(권장기간에 오늘이 포함 / 지난 미완료 / 마감 임박 지원금). 임의 우선순위 부여 없음 — 엔진의 `priority`·`exposureLevel` 을 그대로 정렬 키로 사용.

**캘린더**: 월 그리드(예정일=점, 권장기간=띠) → 선택일 패널(예정/기간 두 묶음) → "이 달 월령 체크" 목록. 범례에 3유형 표기.

**기록**: 상단 필터 칩(전체·건강·성장·발달·생활·활동) + 시간순 목록 + 우하단 "＋ 기록 추가". 항목 = 자동(완료 유래) / 직접(부모 작성) 배지로 구분. 상세 시트: 제목·날짜·월령·카테고리·메모·사진·"관련 다음 일정".
- "관련 다음 일정": 같은 `todo_id` 의 다음 `occurrenceKey`(접종 2차→3차) 또는 같은 카테고리에서 엔진이 다음으로 여는 항목. 엔진에 관계가 없으면 표시하지 않는다(지어내지 않음).

**지원금·제도 탭**: 상단 세그먼트 [신청 가능 | 신청 예정 | 신청 완료] + 하단 필터 [전체·전국·지역]. 마감 임박은 "신청 가능" 안에서 상단 고정 + 배지. 상세 시트에 지원 대상·금액·신청 시점/마감·방법·공식 링크·"신청 완료로 표시".
- 지원금 6영역(신청 가능/예정/마감 임박/완료/전국/지역)은 **상태 3분류 × 범위 필터 2**로 압축해 탭 내부 복잡도를 줄인다(지시서 §6 "한 화면에 과다 정보 금지").
- 데이터에 없는 필드(신청 방법이 비어 있는 항목 등)는 빈 줄을 만들지 않고 숨긴다.

**온보딩**: CTA 문구 변경, 지역 아래 안내문("선택한 지역의 지원금·제도도 함께 알려드려요"), 임신 중은 결과 화면에서 "출산 전 준비 / 출산 후 일정" 두 구간으로 홈 상단 구분.

### 2-4. 기록 데이터 모델 (기존 완료 내역 보존이 최우선)

기록 = **두 출처의 합성 뷰**. 완료 유래 기록은 **별도 저장하지 않는다.**
- 자동 기록: `completed` 맵 + 일정 메타에서 렌더 시점에 파생 → 기존 완료 내역이 마이그레이션 없이 그대로 기록이 됨, 이중 저장·불일치 없음.
- 완료 기록에 메모를 붙이고 싶으면 `completed[id].memo` (선택 필드 추가, 구버전 값과 호환).
- 직접 기록: 신규 `records` 맵 `{ [recId]: { category, title, date, memo, photoRef?, authorLabel, createdAt, updatedAt } }` (월령은 저장하지 않고 date·생년월일로 계산 → 생년월일 수정 시 자동 정정).
- 삭제는 소프트 삭제(`deletedAt`)로 하여 동기화 중 부활 방지.

### 2-5. 다중 아이 (아이 전환)

가족코드가 이미 "아이 1명 = 코드 1개" 구조. 로컬에 `hannun_children = [{code, name}]` 목록만 두고, 전환 = 해당 코드로 기존 `handleLoadCode` 경로 재실행. 데이터 마이그레이션 없음.

### 3-2. 변경 파일

- `index.html` : 뷰 컨테이너(home/calendar/records/subsidy/todo-all), 4탭 nav, 문구
- `css/style.css` : 홈 카드·기간 띠·지원금 카드·기록 카드·FAB (기존 토큰·색 재사용)

- `js/app.js` : 탭 라우팅, 캘린더 렌더 교체. **비대해진 파일이므로** 신규 화면은 새 파일로 분리
- 신규 `js/records.js`(기록 저장·동기화·자동기록 파생), `js/home.js`, `js/subsidy-view.js` — app.js가 노출하는 `window.HN` 컨텍스트(읽기용 상태 + 액션 콜백)를 통해 접근
- `js/sync.js` : `records` 필드 단위 갱신 함수 추가(전체 교체 금지)
- `sw.js` : 캐시 목록에 신규 파일 추가, 버전 갱신
- `test/` : 분류·파생 로직 node 단위 테스트 추가

### 3-3. 위험 식별

1. **동기화 덮어쓰기**: `completed`는 이미 전체 교체 방식. `records`는 `records.<id>` 점 표기 필드 업데이트로 기기 간 동시 작성 충돌을 피한다. (`completed`의 기존 위험은 이번 범위에서 건드리지 않고 보고에만 기재)
2. **배포된 Firestore 규칙 불명**: 규칙이 v1 문서의 허용 필드를 `profile/completed/updatedAt…` 로 제한하는 버전이 이미 배포돼 있으면 `records` 쓰기가 거부된다. 앱은 실패를 조용히 삼키지 않고 "동기화 실패, 이 기기에만 저장됨"을 표시하도록 구현.
3. **문서 1MB**: 사진 base64를 v1 문서에 넣으면 금방 초과 → 기록 사진은 문서에 넣지 않는다.
4. **UI 자동 테스트 부재**: 각 단계마다 브라우저(모바일 폭)로 직접 확인. 지정 테스트 계정(은찬·서울 구로구·2026-06-20)으로 검증.
5. **캘린더 의미 변경**: 기존 사용자에겐 "점이 예전 자리에 없다"는 변화. 첫 진입 시 1회 안내 배너로 설명(달력 점이 실제 날짜가 아니었다는 점을 숨기지 않음).

### 3-4. 이번 범위에서 하지 않는 것(미리 명시)

- 새 지원금·신청 조건 추가, 접종/검진 데이터 재검증(기존 "미검증" 항목은 그대로 두고 보고에 유지)
- 알림(푸시), 로그인/계정
- v2 Firestore 스키마 전환(별도 프로젝트 — 문서 `Firestore-마이그레이션-계획.md`)

## 5. 착수 전 결정이 필요한 것

1. **아이 전환**: 로컬 코드 목록 방식(마이그레이션 없음, 권장) vs 이번엔 제외
2. **직접 기록 저장 위치**: v1 가족 문서의 `records` 필드(권장, 규칙 확인 필요) vs 로컬 전용(기기 간 공유 안 됨)
3. **기록 사진**: 이번엔 로컬(IndexedDB) 저장만 + 공유 불가 명시(권장) vs Firebase Storage 도입(프로젝트 설정·규칙·비용 확인 필요)

## 6. 구현 결과 (2026-09-29, v1.2.0)

**결정(§5)**: 아이 전환=로컬 코드 목록 방식 / 기록=가족 문서 `records` 필드 / 사진=기기(IndexedDB) 저장만.

**계획 대비 변경**: 신규 화면 파일을 `home.js`·`subsidy-view.js`·`records-view.js`(+`records.js` 저장소, `hn-logic.js` 순수 로직)로 나눴다. 설계의 `window.HN` 컨텍스트는 `app.js`의 `hnCtx()` 함수로 구현.

**확인된 사실**: 배포된 Firestore 규칙이 `records` 필드 쓰기를 거부한다(`permission-denied`). 저장소의 `firestore.rules` 는 `records` 를 허용하도록 고쳤지만 **배포는 하지 않았다**. 배포 전까지 직접 기록은 이 기기에만 저장되고, 기록 탭에 그 사실이 표시된다.

**테스트**: `node test/hn-logic.test.js` 17건 + 기존 엔진 40건 통과. 브라우저(테스트 프로필)로 홈·캘린더·전체 할 일·기록 추가/삭제·지원금 상세/신청 완료/취소 확인.

## 7. 이후 변경 (v1.3 ~ v1.12, 2026-09-29~30)

- **달력**: 정해진 날짜가 없는 항목은 각자의 기간 안에서 "추천일"로 배치(접종 묶음·평일 우선·분산). 혜택은 신청 시작일에 표시. 배치 로직은 `hn-logic.js` `assignDisplayDays`(테스트 있음).
- **혜택**: "지원금" 표기를 "혜택"으로 변경. 해당(신청 완료)/미해당 두 버튼, 미해당은 `completed[id+"__na"]`로 저장하고 기록 탭 "미해당 항목 보기"에서 복구.
- **홈**: 이번 달 챙길 것(카테고리별 한 줄 요약, 줄을 누르면 그 카테고리 팝업) + 신청 가능한 혜택. 과거 미완료 항목은 홈에 올리지 않고 체크리스트에서 확인. 분류 로직 `classifyHomeItems`.
- **하단 메뉴 5개**: 홈·캘린더·체크리스트·육아 혜택·기록. 체크리스트는 카테고리 필터 + "전체" 토글(탭을 벗어나면 전체 켜짐으로 초기화), 그룹 안 카테고리순 정렬, 지금 월령만 펼침.
- **팝업**: 오른쪽 위 ✕ 닫기, 카테고리색 확인/완료 버튼(혜택은 살구색), 완료일은 연필 아이콘 + 작은 자체 달력.
- **데이터**: 어린이집 항목(CR-01~04)을 안전·돌봄 → 생활·수유로 이동.
- **프로필**: 사진 미리보기 후 저장, 이름 옆 연필 아이콘으로 정보 수정, 사진은 가족 문서에 저장되어 같은 가족코드의 다른 기기에도 반영(서버 기준, 삭제는 null).
- **미배포**: `firestore.rules`의 `records` 허용은 저장소에만 반영. 배포 전까지 직접 기록은 기기 로컬 저장.
