# 한눈육아 개발 및 인프라 현황과 출시 아키텍처 검토 요청서

기준일: 2026년 10월 8일  
운영 앱 버전: v2.0.19

안녕하세요. 현재 개발 중인 **한눈육아**의 기술 구조와 웹·모바일 출시 방향에 대해 검토를 요청드립니다.

현재 구현, 운영 배포, 개발 중인 기능을 구분해 정리했습니다. Firebase를 계속 사용할지뿐 아니라, 초기 테스트부터 장기적인 데이터 누적까지 감당할 수 있는 구조인지 의견을 받고 싶습니다.

## 1. 서비스 목적

한눈육아는 임신부터 초등까지 아이의 월령·나이·학년·거주 지역과 가족 상황을 기준으로, 부모에게 필요한 정보를 먼저 찾아주고 행동·할일·일정·가족 공유로 연결하는 서비스입니다.

핵심 경험은 다음과 같습니다.

- 매번 직접 찾아보지 않아도 된다.
- 중요한 검진·접종·지원·학교 준비를 놓치지 않는다.
- 가족이 같은 정보를 보고 함께 챙긴다.
- 우리 아이에게 지금 필요한 것을 한눈에 알 수 있다.

캘린더나 기록 기능 자체를 확대하기보다 **정보 → 필요한 행동 → 할일·일정 → 가족 공유 → 완료·성장기록**의 연결을 중심으로 개발하고 있습니다.

## 2. 메뉴별 기능과 현재 구현 상태

현재 운영 구조는 36개월 전후에 따라 일부 메뉴가 달라집니다. 모든 연령의 메뉴를 통합하는 구상은 검토했지만 현재는 보류한 상태입니다.

| 영역 | 현재 기능·데이터 | 확인하거나 확장할 부분 |
|---|---|---|
| 홈 | 오늘의 가족 일정, 필요한 안내, 연령별 챙길 내용·할일, 다른 메뉴 진입 | 가족 전체·아이별 상태의 일관성 |
| 가족 캘린더 | 가족 구성원 필터, 직접 등록 일정, 반복·예외, 자동 안내와 일정 연결 | 가족 공동 편집, 충돌 처리, 조회 범위 |
| 체크리스트·할일 | 월령별 자동 안내와 완료 상태, 직접 등록한 가족 할일·기한·카테고리 | 기기 상태와 서버 상태의 통합 |
| 육아혜택 | 나이·지역별 지원 정보, 신청 링크, 해당·미해당·신청 완료 처리 | 공식 정보 갱신, 상태 공유 범위 |
| 교육트렌드·교육 정보 | 학년·연령별 안내, 지역·교육 링크, 등록 학원 일정과 주간 횟수 | 기관 정보 운영과 동의 기반 통계 설계 |
| 어디갈까 | 지역·연령·실내외·비용 등으로 장소 탐색, 이용 집계 | 데이터 갱신과 위치정보 사용 범위 |
| 성장기록 | 아이 중심의 활동 지도, 학교·학원·그 외 활동·가정 활동별 날짜·메시지·사진 기록 | 장기 서버 보관, 과거 기록 이전·검색 |
| 프로필·가족 관리 | 계정, 가족 초대코드, 아이 정보, 구성원 역할·수정·삭제 | 초대·탈퇴·아이 계정 연결 권한 |

혜택·장소·교육 안내 등에는 정적 JSON 기반 데이터가 포함되어 있습니다. 모든 콘텐츠가 서버 DB나 외부 API에서 자동 갱신되는 구조는 아닙니다.

교육트렌드는 현재 **우리 가족이 등록한 학원 일정**을 활용합니다. 지역·학년별 또래 활동의 실제 집계 데이터는 아직 없으며, 검증되지 않은 평균·순위는 표시하지 않습니다.

## 3. 성장기록의 장기 방향

성장기록에는 앞으로 새로 생기는 기록뿐 아니라 **아이의 기존 활동과 과거 기록도 누적 등록**할 계획입니다.

예를 들면 다음과 같습니다.

- 과거 학교·어린이집·유치원 활동
- 현재 및 이전 학원·방과후 활동
- 운동·체험·가족 활동
- 선생님이 보내준 메시지와 안내문 캡처
- 활동 사진, 부모 메모, 아이가 남긴 말

활동을 선택하면 관련 날짜별 기록을 보여주고, 전체 화면에서는 아이가 어떤 활동을 이어왔는지 살펴볼 수 있도록 구성하려고 합니다.

다만 **등록된 기록이 적다는 이유만으로 아이의 능력이나 경험이 부족하다고 판단하면 안 됩니다.** 활동 수·기록 수·참여 횟수를 구분하고, 화면에서 무엇을 기준으로 표현하는지 명확하게 하려고 합니다.

이 방향 때문에 다음 구조를 검토받고 싶습니다.

| 설계 대상 | 검토 요청 |
|---|---|
| 활동과 개별 기록 | 활동의 시작·종료·기관·이름 변경과 날짜별 기록을 분리하는 것이 적절한가 |
| 과거 기록 | 실제 활동일과 서비스 등록일을 별도로 저장해야 하는가 |
| 아이의 당시 상태 | 과거 기록에 현재 학년 대신 당시 나이·학년을 어떻게 연결할 것인가 |
| 일정 연결 | 반복 일정, 실제 참여, 기록 작성 상태를 어떻게 구분할 것인가 |
| 일괄 등록·이전 | 여러 사진·메시지를 가져올 때 중복·실패·재시도를 어떻게 처리할 것인가 |
| 검색·조회 | 아이·기간·기관·활동·카테고리별 검색과 페이지 조회 구조 |
| 파일 관리 | 압축본·썸네일·원본 선택 보관, 교체된 사진·실패한 업로드 정리 |
| 장기 보존 | 가족 탈퇴·아이 삭제·계정 삭제 시 기록의 소유·보존·삭제 정책 |
| 데이터 내보내기 | 가족이 자신의 기록과 사진을 내려받을 수 있는 구조 |

**현재 성장기록의 운영 저장소는 기기의 IndexedDB입니다.** 서버 저장·사진 업로드·기기 기록 이전·수정 충돌 방지 코드는 1차 구현했지만 비활성 상태이며, 운영 서버 이전을 완료한 것은 아닙니다.

활동 관리용 별도 데이터, 대량 기록 페이지 조회, 장기 집계·검색은 추가 설계가 필요합니다.

## 4. 현재 기술 및 배포 현황

| 항목 | 현재 상태 |
|---|---|
| 프런트엔드 | HTML·CSS·JavaScript 기반 웹/PWA |
| 웹 운영 | GitHub Pages, 서비스워커를 통한 앱 셸 캐시·버전 갱신 |
| Firestore | 아이 정보, 가족 연결, 구성원, 일정, 할일 등 운영 사용 |
| Authentication | 이메일·비밀번호 로그인, 계정·가족 연결 구조 사용 |
| Storage | 프로젝트에 사진 저장용 버킷이 아직 없으며 도입 준비 중 |
| 과금 | 최근 확인 시 과금 비활성. Blaze 전환을검토·진행하려는 단계 |
| OCR | 기기 내 Tesseract 기반 글자 인식과 규칙 기반 일정 파싱 구현 |
| 음성 | 지원 브라우저의 음성 인식과 키보드 받아쓰기 대체 흐름 구현 |
| AI 파싱 | 인터페이스만 있으며 외부 AI 호출은 비활성 |
| FCM | 운영 푸시 구현 전 |
| Functions·Cloud Run | 도입 후보. 현재 핵심 처리의 상당 부분은 클라이언트에서 실행 |
| iOS | Capacitor 프로젝트와 웹 자산 복사본 존재. 스토어 출시 완료 상태는 아님 |
| Android | 출시 계획 단계 |

사진/OCR 일정 입력과 성장기록 사진 보관은 목적을 구분하려고 합니다. **일정 추출에 사용한 사진을 모두 장기 보관해야 하는 것은 아니며**, 성장기록 첨부로 선택한 사진과 별도 정책을 적용할 계획입니다.

OCR·AI가 불확실한 날짜·시간을 임의로 확정하지 않고, 사용자가 일정 후보를 확인한 후 등록하는 원칙을 유지합니다.

## 5. 현재 DB 구조와 전환 준비 상태

현재 운영 DB에는 이전 이름과 역할이 혼재되어 있습니다.

| 현재 운영 경로 | 현재 역할 | 준비 중인 이름 |
|---|---|---|
| `families/{아이코드}` | 아이 프로필·기존 상태 데이터 | `children/{아이코드}` |
| `households/{가족ID}` | 가족 공유 단위 | `families/{가족ID}` |
| 가족 하위 `children` | 가족과 아이 연결 | `childLinks` |
| `householdCodes` | 가족 초대코드 조회 | `familyInviteCodes` |
| `placeStats` | 장소 이용 집계 | `placeUsageStats` |
| `accounts` | 인증 UID와 서비스 계정 연결 | 유지 |

새 경로에 복사본을 만들고 변경분을 비교·검증했지만, **운영 앱의 경로 전환과 구 데이터 정리는 아직 완료하지 않았습니다.** 구·신 컬렉션이 계속 자동 동기화되는 구조도 아닙니다.

계정 비밀번호는 서비스 DB에 저장하지 않고 Firebase Auth에서 관리합니다. `accounts`에는 이메일과 서비스 계정·가족 연결 정보를 저장합니다.

다음 사항을 검토받고 싶습니다.

- 가족·아이·구성원·활동·기록의 관계가 적절한지
- 여러 가족에 연결된 아이 또는 보호자까지 고려해야 하는지
- 컬렉션 이름 변경과 기능 확장을 동시에 진행해도 되는지
- 구버전 앱·오프라인 대기열을 포함한 안전한 전환 절차
- 데이터를 언제까지 복제 상태로 유지하고 어떻게 정리할지

## 6. 최종 플랫폼 방향과 Firebase 의존 범위

최종적으로 동일한 가족 데이터를 다음 플랫폼에서 사용하려고 합니다.

- 웹/PWA
- iOS 앱 — App Store
- Android 앱 — Google Play

현재는 웹을 먼저 검증하고 iOS·Android로 확장하는 방향입니다. 웹 코드를 활용하는 Capacitor 방식과 별도 모바일 프런트엔드 방식 중 어느 쪽이 적절한지도 검토받고 싶습니다. Capacitor는 웹·iOS·Android를 지원하는 기반이지만, 실제 카메라·음성·푸시·인증 동작은 플랫폼별 검증이 필요합니다. [Capacitor 공식 문서](https://capacitorjs.com/docs)

현재 생각하는 백엔드 구성은 다음과 같습니다.

- Firestore: 가족·아이·일정·할일·성장기록 메타데이터
- Storage: 보관하기로 선택한 사진·이미지
- Auth: 로그인과 인증
- FCM: 기기별 푸시 전달
- Functions 또는 Cloud Run: 권한이 필요한 처리, 알림 예약, 향후 AI 파싱·집계

Firebase SDK를 화면 코드에 직접 결합하기보다 다음처럼 분리하려고 합니다.

**화면 → 서비스 규칙 → 데이터 접근 인터페이스 → Firebase 어댑터**

현재 일부 규칙 모듈과 동기화 모듈은 분리되어 있지만, 화면 코드의 직접 Firebase 호출도 남아 있습니다. 아직 완전히 분리된 구조는 아닙니다.

백엔드 이전을 고려할 때 다음까지 어느 정도 분리해야 하는지 의견을 요청드립니다.

- 서비스 내부 ID와 인증 제공자 UID의 연결
- 날짜·시간·서버 타임스탬프 표현
- 사진 경로와 다운로드 방식
- 조회·페이지네이션·실시간 구독
- 오프라인 저장·충돌·재시도
- 푸시 토큰과 알림 발송 구조
- 사용자 데이터·파일 내보내기

Firebase와 Supabase를 비교할 때 단순 저장 비용뿐 아니라 관계형 조회·통계·오프라인·실시간 공유·운영 인력·이전 비용을 함께 평가하고 싶습니다. Supabase를 선택하면 PostgreSQL과 RLS 기반 권한 설계를 검토해야 한다는 점도 인지하고 있습니다. [Supabase DB 문서](https://supabase.com/docs/guides/database/overview)

## 7. 출시 전 보안 및 개인정보 검토

가족 캘린더에는 아이 정보·생년월일·거주 지역·학교 및 학원 일정·사진·선생님 메시지가 포함될 수 있습니다.

현재 일정·할일에는 로그인한 가족 구성원 기준 권한을 적용했지만, **일부 기존 아이 프로필·가족 메타데이터 경로에는 코드나 ID를 아는 사용자에게 읽기를 허용하는 규칙이 남아 있습니다.** 외부 테스터 배포 전 우선 점검하려고 합니다.

검토를 요청하는 항목은 다음과 같습니다.

- 초대코드와 실제 데이터 접근 권한의 분리
- 초대 수락·만료·재발급·가입 시도 제한
- 보호자 공동 편집과 아이 본인 기록 편집 범위
- 아이 계정과 아이 프로필의 안전한 연결
- 가족 탈퇴·역할 변경 시 접근 해제
- 다른 가족·형제 기록에 대한 권한 테스트
- 사진·메시지의 보관 목적과 동의 범위
- 해외 저장 지역 선택 시 필요한 안내와 처리
- 로그·OCR·AI 요청에 개인정보가 남지 않도록 하는 구조
- 운영·개발·테스트 환경 분리와 백업·복구

교육 통계에 가족 기록을 활용하는 경우에는 **가족 공유용 데이터와 통계 제공 동의를 분리**하고, 최소 표본·재식별 위험·집계 방식도 검토하려고 합니다.

## 8. 초기 테스트와 비용 관리

초기에는 약 20명의 학부모에게 테스트 버전을 제공할 계획입니다.

현재 검토 중인 제한은 가족당 사진 누적 100장, 월 신규 사진 30장, 압축본·썸네일 저장입니다. 이 제한은 아직 적용하지 않았습니다.

Firebase Storage는 Blaze가 필요하며, 무료 한도 적용 지역과 국내 저장 여부를 먼저 결정해야 합니다. 무료 사용량 안에서 운영하는 것과 비용을 절대 발생시키지 않는 것은 구분하고 있습니다. [Firebase Storage 안내](https://firebase.google.com/docs/storage/web/start)

다음 비용 관리 방향이 적절한지 확인받고 싶습니다.

- 기기에서 사진 압축·썸네일 생성
- 목록은 썸네일, 큰 사진은 선택 시 다운로드
- 최근 기록부터 페이지 조회
- 캘린더는 필요한 기간만 조회
- 실시간 구독 범위 제한
- 가족 공유 파일을 계정마다 복제하지 않기
- 가족별 저장량·등록량 제한과 서버 검증
- 실패한 업로드·교체된 파일 정리
- AI는 필요한 경우에만 사용하고 요청량 제한
- 예산 알림과 실제 사용량 감시

장기적으로 사용자 수뿐 아니라 **가족당 누적 사진 수, 보존 기간, 앱·웹의 조회 횟수, AI 처리량**을 기준으로 비용 모델을 검토하고 싶습니다.

## 9. 최종적으로 받고 싶은 의견

다음 형식으로 의견을 부탁드립니다.

| 검토 항목 | 요청 내용 |
|---|---|
| 백엔드 선택 | Firebase 유지 / Supabase 전환 / 일부 기능 분리 중 권장안과 이유 |
| 모바일 확장 | 현재 웹 코드 활용 방식과 별도 앱 개발 방식의 장단점 |
| 성장기록 구조 | 장기 활동 이력·사진 누적에 적합한 데이터·파일 구조 |
| 출시 전 필수 작업 | 20명 테스트 전에 반드시 해결할 사항 |
| 추후 확장 작업 | 사용자 증가 후 진행해도 되는 사항 |
| 비용 전망 | 20가족·100가족·1,000가족 기준 가정과 주요 비용 요인 |
| 이전 가능성 | 지금 분리할 인터페이스와 나중에 이전하기 어려운 영역 |
| 운영 체계 | 보안 검증, 배포, 모니터링, 백업·복구의 최소 구성 |

특히 **현재 Firebase를 사용한다는 이유로 계속 유지해야 한다거나, 성장기록이 많아진다는 이유만으로 즉시 백엔드를 교체해야 한다고 전제하지 않고**, 실제 출시·운영 부담과 향후 데이터 규모를 기준으로 검토 부탁드립니다.
