# D1 계정 설계 — 회원가입·로그인·가족 합류 (설계서, 구현 전)

기준: [D0 사용시나리오](한눈육아-D0-회원가입-사용시나리오.md) UC-1~8, Q1~Q7은 D0의 **기본 가정**을 그대로 쓴다. 이 문서는 코드·규칙을 바꾸지 않는다(계획만).
현황(읽은 사실): 앱에 Firebase Auth 없음(index.html은 `firebase-app-compat`·`firebase-firestore-compat`만). 가구는 기기 단위(`hannun_household_code`·`hannun_household_id`·미러·대기열). 아이는 6자리 가족코드(`families/{code}`: profile·completed·records). 구성원 `households/{hid}/members/{memberId}`는 라벨 문서(role: MOM·DAD·GRANDPARENT·CAREGIVER·OTHER, 가구 생성 시 엄마·아빠 시드). 규칙은 비인증·코드 기반(가구·구성원·일정 get/list 모두 `true`).

## 1. Auth 도입과 기존 모델 연결
- Firebase Auth **compat**(같은 10.14.1) `firebase-auth-compat.js` 추가, 이메일/비밀번호(Q1). 새 모듈 `js/auth-service.js`(가입·로그인·로그아웃·재설정 메일·상태 구독·오류 문구 매핑)는 **어댑터 주입형**이라 가짜 Auth로 테스트한다. 플래그 `FEATURES.accounts`(`hannun_feature_accounts==="1"`)가 켜졌을 때만 Auth를 읽는다(꺼지면 SDK 호출 0건, 기존 화면 그대로). accounts ON이면 가족 캘린더(household)도 함께 켠다(D0 §3: 계정 기능이 켜지면 가족 캘린더가 기본 구조).
- **연결 문서 `accounts/{uid}`** (1인 1문서): `{ v, displayName, role, institution, householdId, memberId, createdAt, updatedAt }`. 로그인하면 `accounts/{uid}` get 한 번으로 내 가구·구성원을 찾는다(쿼리·list 불필요).
- **구성원 재사용**: 가입자는 새 구성원을 늘리지 않고 같은 role의 **시드 구성원(엄마/아빠)을 '내 것으로 확보'**(members 문서에 선택 필드 `uid` 추가)하고, 이모님·자녀 등은 구성원 1개를 새로 만든다. "나" = `members` 중 `uid == auth.uid`. 기존의 기기 로컬 '이 기기를 쓰는 사람'(`hannun_active_member`)은 계정이 없는 체험 모드의 대체 수단으로 남기고, 계정이 있으면 uid가 우선한다. 일정의 담당자 기본값은 "나"의 memberId.
- 아이는 변경 없음: 가구 children 링크(familyCode)·`families/{code}` 그대로(`accounts`가 가구를, 가구가 아이를 가리킴). 임산부 가입은 현재 앱이 이미 지원하는 `stage: "pregnant"`(birthDate=출산예정일) 프로필로 만든다.

## 2. 보안 규칙 변경 범위 (하위호환 우선)
- 추가만 한다(기존 줄 수정 없음): ① `match /accounts/{uid}` — `request.auth != null && request.auth.uid == uid`일 때만 get/create/update, 키 `hasOnly`, delete 금지 ② members 허용 키에 `uid` 추가(값은 자기 uid만: `!('uid' in d) || d.uid == request.auth.uid`)와 role에 `'CHILD'` 추가.
- **비인증 기존 사용자 호환**: 가구·아이·일정·완료의 기존 규칙(비인증 get/list/write)은 이번 트랙에서 **그대로 둔다**. 계정을 쓰지 않는 기기는 지금처럼 동작한다. "구성원만 읽기" 같은 강화는 후속(Q8, 결정 필요 아님·기본=후속) — 기존 사용자가 깨지기 때문.
- **규칙 배포 전에도 앱이 깨지지 않는 방식**: D1(Auth만)은 규칙이 필요 없다(Auth는 Firestore 규칙과 별개). D2부터 `accounts` 쓰기가 필요하므로, 가입 중 `accounts` 쓰기가 `permission-denied`이면 "계정 서버 설정이 아직 준비되지 않았어요" 안내 후 방금 만든 Auth 사용자를 삭제(`user.delete()`)하고 가입 전 상태로 돌아간다(가구는 만들지 않음). 순서: Auth 생성 → accounts 쓰기 시도 → 성공해야 가구 생성/합류 진행. role `CHILD`는 규칙 배포 전에는 `OTHER`로 저장하고 라벨로 구분한다.
- 사용자 몫: 콘솔 Auth 사용 설정(이메일/비밀번호)·승인된 도메인 확인·규칙 배포·수동 규칙 검증 페이지(autoRef와 같은 방식, 신규 `test/firestore-accounts-manual-test.html`)·테스트 계정/문서 정리.

## 3. 가입 화면과 임산부(아이 없는 상태)
- 필드(D0 UC-2 순서, 한 화면 스크롤 또는 2단계): ① 이메일·비밀번호(8자 이상) ② 지금 상황(임산부/아이가 있어요) ③ 가입하는 사람(엄마/아빠/자녀/이모님) + 표시 이름 ④ 아이 돌봄 기관(어린이집/유치원/초등학교/해당 없음 — 아이 프로필 `care`로 저장, 허용 필드라 규칙 변경 없음) ⑤ 가족 캘린더 코드(비움=신규, 입력=합류) ⑥ 아이 이름·출생일·성별 또는 출산예정일.
- 코드 입력 시(합류): ②·④·⑥은 숨긴다(가구의 아이 사용). 잘못된 코드는 가입 진행 전에 `joinHousehold` 사전 확인으로 막고 "코드를 찾을 수 없어요"(신규로 몰래 만들지 않음, UC-3-3). 코드가 맞아도 `accounts` 쓰기 실패 시 2번의 롤백.
- 임산부: 출산예정일 필수, 아이 프로필은 pregnant 단계(체크리스트·캘린더는 기존 임신 항목). **아이가 아예 없는 상태**(합류했는데 가구에 아이 없음, 또는 임산부가 예정일 미입력으로 건너뜀)는 허용하지 않고 예정일/아이 입력을 필수로 한다 — 단 합류자는 예외: 가구에 아이가 없으면 홈·체크리스트에 빈 상태 카드 "아이를 등록하면 자동 일정이 나와요" + [아이 등록하기]를 보인다.

## 4. 기존 기기 데이터 가져오기 (D4)
- 원칙: **로컬을 먼저 지우지 않는다.** 아이 데이터는 이미 `families/{code}`에 있어 "복사"가 아니라 **계정/가구에 연결**만 한다.
- 가입(신규 가족) 시 기기에 기존 아이가 있으면 "이 기기의 아이를 내 가족 캘린더로 가져올까요?" → 예: 새 가구를 만들고 그 아이를 `addChild`로 연결(N·B 연결 로직 재사용, 중복 링크 검사). 기기에 이미 가구(hid)가 있으면 그 가구를 계정에 귀속(`accounts.householdId`=기존 hid, 내 구성원 확보).
- 로그인 시 계정에 가구가 있는데 기기에도 로컬 아이가 있으면: 기본은 계정 가구를 열고, 기기 아이는 "이 기기의 아이도 가족 캘린더에 연결할까요?"로 선택(거절하면 로컬은 그대로 체험 데이터로 남음). 충돌이 아니라 선택으로 처리한다.

## 5. 로그아웃의 로컬 정리 범위
- D1(최소·안전): Auth 로그아웃 + 가구 로컬 키 정리(`HouseholdSync.leaveLocal`: 코드·id·미러·대기열) + 이 기기 사용자 키. **아이·완료·기록 캐시(profile·completed·children·familyCode)는 지우지 않는다**(체험 모드 데이터 보존, 서버 데이터는 그대로).
- D4(마이그레이션 이후 확정): 계정에서 가져온 아이 캐시를 지울지는 "서버에 이미 있는 데이터만 기기에서 제거, 대기열(보내지 못한 변경 N건)이 있으면 경고 후 선택"으로 N6 패턴 재사용. 기본은 UC-4 문구(가족 데이터 캐시 삭제)를 따르되 보내지 못한 변경이 있으면 막지 않고 경고한다.

## 6. 캘린더 '나' 기본 선택과 구성원 칩
- 현재 필터 칩은 MOM/DAD **역할 기반**이다. 계정 모드에서는 칩 id를 구성원 단위(`MEMBER:<memberId>`)로 일반화하고(MOM/DAD 호환 유지, 담당자 태그에 `MEMBER:<id>` 추가, 색은 role 색·그 외는 가족색 파스텔), 라벨은 나=`나(엄마)`·그 외 구성원 라벨·아이 이름. 기본 선택은 내 구성원 칩 하나(세션마다 초기화, 저장하지 않음).
- 합류 시 칩 자동 추가: 구성원 문서가 들어오면 이미 있는 리스너(`startListening` → `usRefreshCalendar`)가 칩 목록을 다시 그린다(새로고침 불필요).

## 7. 화면·메뉴
- 하단 5개·캘린더 UI 유지. 랜딩에 로고+회원가입/로그인(플래그 ON), 그 아래에 기존 입력 화면을 "계정 없이 시작하기"(체험 유지, Q5)로 둔다. `+` 메뉴(`showAddMenuSheet`)에 '아이 등록하기'(기존 `beginNewChildEntry`) · '가족 초대하기'(코드+복사+안내, 온보딩 코드 단계 재사용) 추가. 내 정보(프로필 시트)에 이름·역할·코드(복사)·구성원·로그아웃(현재의 '이 기기에서 나가기'는 계정 모드에서 로그아웃으로 대체).

## 8. 단계 분할
| 단계 | 내용 | 주요 파일 | 위험도 | 서버/콘솔 필요 |
|---|---|---|---|---|
| D1 | Auth(compat 스크립트·auth-service)·가입/로그인/로그아웃/재설정 화면·플래그 accounts·로그아웃 최소 정리. 계정 서버 데이터 없음(Auth 사용자만) | js/auth-service.js, js/account-view.js(순수), js/app.js, js/feature-flags.js, index.html, css, sw.js | T2 | 콘솔: Auth 이메일/비밀번호 사용 설정·승인 도메인(검증은 가짜 Auth로 가능) |
| D2 | accounts/{uid}·가구 생성/합류·구성원 확보(uid)·가입 필드 ②~⑥·로그인 시 가구 복원·롤백 | js/account-sync.js, js/household-sync.js, firestore.rules(추가만), 가입 화면 확장 | T2~T3(규칙·데이터 모델) | **규칙 배포 + 수동 검증 페이지** |
| D3 | `+` 메뉴 2항목·내 정보·캘린더 '나' 기본 선택·구성원 칩 일반화·빈 상태 | js/user-schedule-view.js, calendar-model.js, app.js | T2 | 없음(D2 규칙 이후) |
| D4 | 기기 데이터 가져오기·로그아웃 정리 확정·충돌 선택 | app.js, account-sync.js | T2 | 없음 |
- 서버/실제 Auth 없이 검증 가능: auth-service(가짜 어댑터)·가입 검증·역할 매핑·계정 문서 생성 순서/롤백(가짜 Firestore)·화면 마크업·플래그 OFF 불변·필터 칩 일반화 로직·규칙 로직 테스트(파서). 사용자 콘솔이 필요한 것: Auth 사용 설정, 규칙 배포, 수동 규칙 검증, 실제 가입/로그인 실기기 확인(플래그 켜기).

## 결정 필요 (막히는 것만)
1. (D2 착수 전) `accounts` 규칙을 지금 단계에서 "비인증 호환 유지(권장)"로 가도 되는지 — 보안 강화(구성원 전용 읽기)는 후속으로 미룸에 동의 필요.
2. 이메일 중복·비밀번호 재설정 문구 등 새 화면 문구는 구현 시 목록으로 승인 요청(결정 아님).
나머지(Q1~Q7)는 D0 기본 가정 사용.
