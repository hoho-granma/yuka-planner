# 한눈육아 C0 — AUTO·USER·FAMILY 결합 계약 (설계 초안, 코드 없음)

작성: hn-main · 2026-10-01 · 상태: **결정 확정(2026-10-01, 사용자 '추천대로') — Q1~Q6 모두 추천안으로 확정**. 기준 문서: `한눈육아-확장설계-2단계-상세.md` §1(동결 계약)·§3·§4·§7·§9·§10·§11, A6 설계검토 §14.

> 갱신 메모(2026-10-01): C1-a(필드 단위 갱신)는 구현·커밋됐다(7ec0392, 서버 검증 대기). §7의 `updateCompleted` 통째 교체 서술은 구현 이전 기준이다. §12의 첫 항목은 이후 확인됨: `families` 규칙은 최상위 키(`completed`)만 판정하므로 `completed` 안의 필드 단위 쓰기는 규칙상 허용되나, 실제 서버 동작은 서버 검증으로 확정한다. `records.scheduleRef`는 설계상 허용(§1-4)이지만 코드·규칙에는 아직 쓰이지 않는다(C2 대상).

## 1. 목적과 범위
- 목적: 이미 구현된 AUTO(엔진)와 USER/FAMILY(가구·일정, B1~B5)를 **의미 있게 연결**하는 규칙을 먼저 확정한다. 최종 화면: 한 달력에서 앞으로 챙길 일정·실제 예약·기관 일정·가족 일정·완료·현재 상황을 본다.
- 이번 문서가 하는 일: 연결 모델, 중복 표시, 완료 규칙, 기록 통합, 완료 상태 공유의 선행 조건, 코드·권한 체계, 불변식, 단계 계획.
- 하지 않는 일: 코드 변경, 담당자(B6)·알림(B7)·OCR·음성·외부 연동 설계, 새 화면 디자인(문구·배치는 구현 단계의 UX 승인).

## 2. 현재 기준선(변경 금지 — 동결)
| 구분 | 현재 사실 |
|---|---|
| AUTO | 엔진이 계산(저장 안 함). 완료만 `families/{코드}.completed` 맵(키 `todo_id__occurrenceKey`)에 저장. 월령 0~72(예비초등 포함), 기간형 AUTO·월령 칸·window 항목이 혼재. `displayDate`는 화면 배치값(저장·실날짜화 금지) |
| USER | `households/{hid}/schedules/{sid}`. FIXED/PERIOD, 반복·예외(주간·격주), 소프트 삭제. 완료는 문서 `status`(`completed` 맵과 키 공간 분리) |
| FAMILY | 가구 생성·참여·코드 재발급·아이 링크(B3). 플래그 `FEATURES.household` 기본 OFF |
| 분리 | AUTO·USER는 한 배열에 섞지 않고 `CalendarModel`에서만 합친다. T4 메타모픽 테스트가 "USER 변경이 AUTO 결과를 바꾸지 않음"을 잠근다 |
| 허용 추가(§1-4) | `records.scheduleRef`, `profile.care/academy/enrollmentYearOverride`, 새 컬렉션·새 localStorage 키만. 기존 문서에 그 외 필드 금지 |

## 3. 결합의 세 층
1. **표시 결합** — 이미 구현(CalendarModel). 날짜 칸·기간 목록·선택일 패널에서 AUTO와 USER를 한 화면에 보여준다.
2. **의미 결합(신규)** — "이 USER 일정은 저 AUTO 항목의 실제 예약이다"라는 **연결(Link)**.
3. **완료 결합** — 연결된 두 쪽의 완료를 어떻게 다룰지.

## 4. 연결(Link) 계약
- **방향: USER → AUTO 단방향으로만 저장한다.** AUTO 문서·`completed`는 연결 정보를 갖지 않는다(동결 유지). AUTO→USER 조회는 런타임에 `autoRef` 색인으로 계산한다.
- **새 필드(제안):** `schedules` 문서의 선택 필드 `autoRef: "<todo_id>__<occurrenceKey>"`(AUTO 완료 키와 동일 형식, 최대 80자). `schedules`는 새 컬렉션이라 동결 계약 위반이 아니지만, ① 스키마 `v:1` 허용 키 목록 ② `user-schedule.js` 검증 ③ Firestore 규칙 허용 키에 **추가가 필요**하다 — 규칙은 사용자가 배포한다.
- **불변식:** `autoRef`가 있으면 `scope=CHILD`이고 `childKeys`는 **정확히 1개**(AUTO 항목은 아이별이므로). `sourceType`은 `MANUAL`이든 OCR이든 무관. 한 AUTO 항목에 연결된 USER 일정이 여럿일 수 있다(재예약) — 취소·삭제되지 않은 것 중 가장 이른 미완료를 "현재 예약"으로 본다.
- **생성 경로:** AUTO 항목 상세의 "예약 일정 만들기" → 일정 편집기를 제목·분류(MEDICAL)·아이·`autoRef`로 미리 채워 열고, 사용자가 날짜·시각을 입력(I9: 날짜를 만들어 넣지 않는다). 기존 `normalizeFromCandidate`의 입력에 `autoRef`만 추가하는 형태.
- **후보 범위(1차):** 예방접종(VX)·영유아검진(HC)·치과 등 `MEDICAL` 성격의 AUTO. 나머지 AUTO는 이번 연결 대상이 아니다.
- **연결이 끊기는 경우:** USER 일정 삭제·취소 → AUTO는 연결 없는 일반 상태. AUTO 항목이 데이터 수정으로 사라지거나 ID가 바뀌면 `autoRef`는 "알 수 없는 항목"으로 취급하고 일반 USER 일정으로만 표시한다(깨지지 않는다).

## 5. 표시 규칙 (중복 방지)
| 화면 | 규칙 |
|---|---|
| 캘린더 날짜 칸 | 연결된 AUTO 항목의 **추천일(planned) 표식은 숨기고** USER 예약만 표시. `autoEvents`·`displayDate` Map은 **그대로**(숨김은 `CalendarModel` 안에서 필터, 바이트 동일 불변식 유지) |
| 선택일 패널 | USER 예약 카드에 "○○ 접종 연결" 배지. 추천 묶음에서는 해당 항목 제외 |
| 체크리스트·홈(AUTO 전용) | 항목은 그대로 보이고 **"예약됨 10/14"** 보조 표시만. 이를 위해 `linksByAutoId` 읽기 전용 맵을 보조 입력으로 전달(항목 자체는 바꾸지 않음) |
| 기간형 AUTO(`#auto-period-slot`)·월령 칸 | 연결 시 같은 보조 표시. 기간 카드를 숨기지는 않는다(예약만 하고 미완료일 수 있으므로) |
| 연결 없는 AUTO·USER | 기존 그대로 |

## 6. 완료 규칙
- **원칙: 두 쪽 완료는 서로 자동으로 쓰지 않는다. 제안만 한다.** AUTO 완료는 `families` 문서의 공유 상태이고 진행률·기록에 쓰이므로, 다른 쪽 조작이 몰래 바꾸면 오염·오체크 위험이 크다.
- USER 일정을 DONE으로 → "‘○○’도 완료로 기록할까요?" **예/아니오**. 예이면 기존 AUTO 완료 경로(`completed`)로 기록하고 완료일은 일정 날짜. 아니오면 USER만 DONE.
- AUTO를 먼저 완료 → 연결된 미완료 USER 예약이 있으면 "예약 일정은 그대로 둘까요? / 완료 처리할까요?" 안내(자동 변경 없음).
- AUTO 완료 취소·USER 상태 변경은 서로 영향 없음. `completed` 키 공간과 USER `status`는 그대로 분리.

## 7. 기록 통합과 완료 상태 공유
- **기록:** USER 완료 → 기록 추가 프롬프트(설계서 §10-4, `records.scheduleRef` 이미 허용). 연결된 쌍이 둘 다 완료면 기록 목록에 **한 줄**(AUTO 파생 기록에 "예약 일정 연결" 표시)로 합쳐 중복을 막는다. 구현 상세는 C2에서.
- **완료 상태 공유(C1, 선행 조건):** 현재 `sync.js updateCompleted`는 `completed` 맵을 **통째로 교체**한다. 가족 두 명이 동시에 체크하면 한쪽이 유실될 수 있고, 연결 기능이 AUTO 완료 작성 경로를 늘리므로 **C2 전에** 필드 단위 갱신(`completed.<키>` 갱신/삭제)으로 안전화한다. 확인할 것: 기존 규칙이 필드 단위 쓰기를 허용하는지, 옛 클라이언트(통째 교체)와의 혼용 기간 동작, 오프라인 유실 방지(§11-2 방식). 이 단계는 **기존 구조 변경**이라 골든 문서 T1 호환 검증이 필수다.

## 8. 코드·권한·범위 경계
- **코드 체계:** 아이 코드(6자리, `families`)와 가구 코드(8자리, `householdCodes`)를 **분리 유지**한다. 합치면 아이 코드만 아는 사람(조부모·돌보미)이 가구 전체에 접근하는 권한 상승이 생긴다(설계서 R1). 사용자 화면 문구에서 두 코드의 용도를 구분해 안내한다(구현 단계).
- **권한:** v1은 "코드를 아는 사람이 전권"이다(담당자 라벨은 인증이 아님). 병원·검진 일정이 들어오므로 `memo/location`은 민감 정보일 수 있음을 UX 문구로 알리고, OCR/외부 연동 전에 App Check 재검토를 선행한다(설계서 §11-3). 담당자(B6)·알림(B7)은 이 문서 범위 밖.
- **학년 경계:** AUTO는 72개월(예비초등)까지. 초등 이후 학교·돌봄 일정은 USER 일정으로 입력하며 `autoRef` 대상이 없다(연결 없는 일반 USER 일정). `profile.care/academy/enrollmentYearOverride` 입력 UI(어린이집·유치원 프로필)는 별도 단계(C3).

## 10. 불변식·테스트 계획 (구현 단계에서)
- T4 확장: 연결 추가·삭제·완료 어떤 연산 열에도 `autoEvents`·`displayDate` Map이 바이트 동일(숨김은 CalendarModel 내부).
- `completed` 키 공간과 USER `status` 분리 유지, USER 완료가 `completed`에 자동으로 들어가지 않음.
- 플래그 OFF·가구 없음에서 기존 동작과 동일(T1: 한 바이트도 다르게 쓰지 않음, 골든 가족 문서).
- `autoRef` 검증: 대상 없는 ID·childKeys≠1·잘못된 형식은 저장 거부 또는 일반 일정으로 안전 처리.
- 규칙 논리 테스트에 `autoRef` 허용 키·길이 추가.

## 12. 이번 검토에서 확인하지 못한 것
- 기존 `families` Firestore 규칙이 `completed.<키>` 필드 단위 쓰기를 허용하는지(C1에서 확인).
- 옛 클라이언트가 아직 쓰이는지, 혼용 기간의 실제 위험.
- `autoRef` 색인 계산의 성능(아이 N명·일정 수백 건), 실측 없음.
- 홈·체크리스트에 보조 입력을 전달할 때 `app.js`의 변경 크기.
