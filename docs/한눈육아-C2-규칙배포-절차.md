# C2 autoRef 규칙 배포·검증·플래그 켜기 절차

대상: 한눈육아 Firebase 프로젝트 `yuka-planner` (Firestore). 사용자가 직접 실행합니다(이 문서의 명령은 Claude 세션이 대신 실행하지 않습니다).
목적: 가족 캘린더 일정에 AUTO 항목 연결(`autoRef`)을 허용하는 새 보안 규칙을 올리고, 확인이 끝난 뒤에만 `autoLink` 기능을 켭니다.

> 한 줄 요약: **백업 → 배포 → 서버 PASS 확인 → 테스트 문서 정리 → 플래그 켜기.** 문제가 있으면 백업 규칙을 다시 올리고 플래그를 끕니다.
> 규칙은 운영 데이터 전체(가족 코드 `families`, 가구 `households`)에 적용됩니다. 4번에서 전부 PASS가 아니면 플래그를 켜지 마세요.

## 0. 준비
- 터미널에서 `cd ~/Documents/10-workspaces/14-육아지기/04-자체서비스/한눈육아`
- Firebase CLI 로그인 상태 확인: `firebase login:list` (없으면 `firebase login`)
- 프로젝트 확인: `.firebaserc`의 default = `yuka-planner`, `firebase.json`의 규칙 파일 = `firestore.rules`
- 작업본 확인: `git status`에서 `firestore.rules`가 수정 상태가 아니고, 올릴 커밋(autoRef 규칙 포함: 84286f3 C2-a 이후)인지 봅니다.

## 1. 현재 배포된 규칙 백업 (가장 중요)
1. 브라우저에서 Firebase 콘솔 → 프로젝트 `yuka-planner` → Firestore Database → **규칙** 탭을 엽니다.
2. 편집기의 내용 전체를 복사해 `~/Documents/firestore.rules.backup-YYYYMMDD` 같은 파일로 저장합니다(날짜는 오늘로). repo의 `firestore.rules`가 아니라 **콘솔에 지금 게시된 규칙**을 백업해야 롤백이 정확합니다.
3. 백업 파일이 비어 있지 않은지 열어서 확인합니다.

## 2. 배포 전 로컬 확인 (30초)
- `node test/firestore-rules.logic.test.js` 와 `node test/c2a-autoref.test.js` 가 통과하는지 확인합니다(서버 호출 없는 로컬 테스트).

## 3. 규칙 배포
- `firebase deploy --only firestore:rules --project yuka-planner`
- `Deploy complete!` 가 보이면 성공. 에러가 나면 4번으로 가지 말고 메시지를 복사해 전달하세요(규칙은 바뀌지 않은 상태입니다).
- 배포 직후 기존 기능 스폿 확인: 앱에서 가족 코드로 불러오기/완료 체크가 평소처럼 되는지 한 번 봅니다.

## 4. 서버 검증 페이지 실행 — 전부 PASS여야 함
1. 같은 폴더에서 `python3 -m http.server 8765` 실행(그대로 둡니다).
2. 브라우저로 `http://127.0.0.1:8765/test/firestore-autoref-manual-test.html` 을 엽니다(`file://`로 열지 마세요).
3. 확인란에 체크 → **[실행]**. 이 페이지는 운영 Firestore에 일회용 가구(`zz-autoref-…`) 아래 일정 문서를 실제로 만듭니다(기존 문서에는 쓰지 않음).
4. 요약이 **FAIL 0 · ERROR 0, 전부 PASS** 인지 확인합니다. 복사용 JSON을 그대로 복사해 전달해 주세요.
5. 하나라도 FAIL/ERROR → **7번 롤백**으로 가고, 5·6번은 하지 않습니다.
6. 확인이 끝나면 서버(터미널)는 `Ctrl+C`로 종료합니다.

## 5. 콘솔의 테스트 문서 정리 (사용자가 직접)
보안 규칙상 문서 삭제는 앱/페이지에서 불가하므로 콘솔에서만 지웁니다.
1. Firebase 콘솔 → Firestore Database → 데이터 탭.
2. 4번 화면 맨 아래에 표시된 경로 `households/zz-autoref-…/schedules` 아래 문서들을 삭제합니다(부모 가구 문서는 없고 기울임체로 보일 수 있음).
3. 이전 검증에서 만든 `zz-c1test-…` 등 `zz-`로 시작하는 테스트 문서가 남아 있으면 같은 방식으로 정리합니다(진짜 가구/가족 문서는 `zz-`로 시작하지 않으니, 이름을 확인하고 지우세요).

## 6. autoLink 플래그 켜기 (이 기기에서만)
플래그는 서버가 아니라 **각 기기 브라우저의 localStorage**에 둡니다. 켜는 기기에서만 동작합니다.
1. 앱을 연 브라우저(또는 홈 화면 웹앱)의 개발자 도구 콘솔에서:
   - `localStorage.setItem("hannun_feature_household", "1")`
   - `localStorage.setItem("hannun_feature_autolink", "1")`
   - 새로고침. (autoLink는 가족 캘린더(household) 플래그가 켜진 상태에서만 읽힙니다.)
2. 동작 확인: 프로필 시트에서 가족 캘린더가 있는 상태 → 체크리스트의 접종·검진 항목 상세에 **'예약 일정 만들기'**가 보이는지, 만들면 항목에 '예약됨 M/D'가 붙는지 확인합니다.
3. 플래그 상태 확인: `localStorage.getItem("hannun_feature_autolink")` → `"1"`이면 켜짐.
   (개발자 도구를 쓰기 어려운 기기는 별도 방법이 필요 — 추가검증 필요: iOS 홈 화면 앱에서 localStorage 플래그를 켜는 현실적인 방법.)

## 7. 롤백 (문제가 생겼을 때)
1. **플래그부터 끕니다**: `localStorage.removeItem("hannun_feature_autolink")` (필요하면 `hannun_feature_household`도) → 새로고침. 앱은 연결 기능 없이 기존 동작으로 돌아갑니다(앱 코드는 규칙과 독립).
2. **규칙 되돌리기**: 1번에서 만든 백업 내용을 콘솔 규칙 탭에 붙여넣고 **게시**하거나, 백업을 `firestore.rules`로 복사해 `firebase deploy --only firestore:rules --project yuka-planner` 를 다시 실행합니다(덮어쓰기 전에 repo의 파일은 `git stash`/복사로 보관).
3. 콘솔 규칙 탭에 이전 게시 버전 기록(복원) 기능이 있으면 그것도 쓸 수 있습니다 — 추가검증 필요(사용 가능 여부는 콘솔에서 확인).
4. 롤백 후 4번 페이지를 다시 돌리면 autoRef 시나리오는 FAIL이 정상입니다(옛 규칙이므로). 일반 기능(완료·가족 코드·일정)이 평소대로인지 확인합니다.

## 참고
- 이 규칙이 하는 일: 일정의 `autoRef` 형식(`^[A-Za-z0-9-]+__[A-Za-z0-9-]+$`)·80자 이하·`scope=CHILD`·`childKeys` 1개·반복 일정 아님·생성 후 불변.
- 이미 쓴 연결 데이터는 규칙을 되돌려도 삭제되지 않습니다(조회만 안 보이거나 수정이 막힐 수 있음).
- push(깃 원격 반영)와 규칙 배포는 별개입니다. 규칙은 `firebase deploy`로만 반영됩니다.
