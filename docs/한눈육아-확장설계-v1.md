## 0. 먼저 알아야 할 것 5가지 (분석 결과 요약)

1. **`displayDate`라는 이름은 코드에 없다.** 실제 이름은 `calDisplayDays`(`app.js:987`) / `assignDisplayDays()`(`hn-logic.js:88`), 화면 문구는 **"추천일"**. 저장되지 않고, 랜덤이 아니라 결정적 알고리즘이다(§2).
2. **엔진(`todo-engine.js`)에는 36개월 상한이 없다.** 그러나 **`app.js`에는 36 하드코딩이 4곳** 있고(§19), 엔진의 "1개월 = 30일" 근사는 6세·12세 쪽으로 갈수록 한 달 안팎 어긋난다(§19). 이전 대화에서 "데이터 문제일 뿐"이라고 한 말은 부정확했다 — 정정한다.
3. **다자녀는 "로컬 목록"일 뿐 서버에 없다.** 아이 1명 = 가족코드 1개 = Firestore 문서 1개이고, `hannun_children`은 이 기기의 localStorage 목록이다. 다른 기기는 형제 코드를 따로 입력해야 한다(§9).
4. **기존 v2 스키마 설계(`Firestore-스키마-설계.md`)는 그대로 채택할 수 없다.** 그 이후 앱에 생긴 `records`·`__na`·`memo`·사진·`stage`·`birthOrder`를 담지 못하고, 배포된 규칙이 이것들을 막는다(§13, 충돌 C3).
5. **새 일정(USER)을 지금 구조에 그냥 섞으면 앱이 깨진다.** `CATEGORY_META[e.category].color`(`app.js:1292`)가 6개 카테고리만 가정하고, `assignDisplayDays`가 사용자 기간형 일정에 "추천일"을 붙여 버린다(§14).

## 1. 현재 구조 (실제 코드 기준)

### 1-1. 데이터 흐름

```text
[입력] 온보딩: 이름·생년월일·몇째·시도·시군구·stage(born|pregnant)
   │  profile  ── localStorage "yukjigi_profile"  ── Firestore families/{코드}.profile
   ▼
[정적 데이터] data/todos/*.json (9개 카테고리) + data/subsidies/national-todos.json  → dataset.todoDefinitions
              data/subsidies/{national|시도|시군구}.json (지역 파일 규칙)              → dataset.subsidy
   ▼
[엔진] TodoEngine.calculateTodoInstances({today, child, region, familyDeclaredAttributes:{}, completions, todoDefinitions})
        → TodoInstance[]  (windowStart/windowEnd/status — "기간"만 계산, 확정 예정일은 없음)
   ▼
[schedule.js] buildSchedule() = buildTodoEngineEvents() + buildSubsidyEvents()
        → events[]  (공통 이벤트 모양, 아래 1-2)
   ▼
[app.js] visibleSchedule() : 카테고리 필터 + "생후 36개월 이하" + 미해당(__na) 제외
   ├─ 홈        (home.js → HNLogic.classifyHomeItems / todayItems)
   ├─ 캘린더    (renderCalendar → assignDisplayDays → 추천일 점)
   ├─ 체크리스트 (renderChecklistTab, 대표 월령 displayMonth별 아코디언)
   ├─ 혜택      (subsidy-view.js → HNLogic.subsidyBuckets)
   └─ 기록      (records-view.js → deriveAutoRecords(completed) + HNRecords 직접 기록)
```

- 엔진 입력의 `familyDeclaredAttributes`는 **항상 `{}`**(`schedule.js` `buildTodoEngineEvents`). 엔진은 `eligibilityCondition`/`variants`를 이미 지원하지만 앱은 아직 값을 넘기지 않는다 → 그 자리가 "현재 다니는 곳" 조건값의 자연스러운 통로다(§12).
- 이 서비스는 "계산은 클라이언트, 저장은 최소"다. TodoInstance·일정·추천일은 **어디에도 저장하지 않고** 매 렌더마다 계산한다.

### 1-2. 이벤트 공통 모양 — 이미 "Schedule 공통 계층"이 사실상 존재한다

`schedule.js`가 만드는 `events[]` 원소(엔진 일정·지원금 공통):

| 필드 | 의미 |
|---|---|
| `id` | 엔진: `${todo_id}__${occurrenceKey}` / 지역 혜택: `SEOUL-001` 등 |
| `category` | **6그룹 고정 문자열**: 발달관찰·예방접종·영유아검진·생활·수유·안전·돌봄·행정·지원금 |
| `scheduleKind` | **`fixed` \| `window` \| `monthly`** — 이미 있는 3유형 enum |
| `fixedDate` / `windowStart` / `windowEnd` | 실제 날짜 / 권장 기간(엔진 계산) |
| `date` | 정렬용 앵커(= windowStart 또는 지원금 시작일). **표시 날짜가 아니다** |
| `isEngineEvent`, `engineStatus`, `detail.instance/definition` | 엔진 일정 표식 |
| `isLegacySubsidy`, `entryDate`, `deadlineDate`, … | 지역 혜택 전용 |

→ **결론(Q1의 핵심)**: 새 "Schedule 공통 계층"을 만들 필요가 없다. 사용자 일정을 **같은 모양의 이벤트로 변환해 `buildSchedule()` 결과에 합치면** 된다. 기존 Todo를 Schedule로 변환하는 일은 없다.

### 1-3. 일정 유형 — 이미 있는 enum 재사용

| 제안(지침) | 현재 코드 | 조건 |
|---|---|---|
| AUTO_FIXED | `scheduleKind: "fixed"` | 혜택(지원금) 신청 시작일. 엔진은 확정 예정일을 만들지 않음 |
| AUTO_PERIOD | `scheduleKind: "window"` | 엔진 기간 폭 ≤ 60일(`DATE_SPECIFIC_MAX_WIDTH_DAYS`) |
| AUTO_AGE | `scheduleKind: "monthly"` | 기간이 넓거나 열림, 마일스톤 대기 |
| USER | (없음) | **신규** |

→ **새 enum을 만들지 않는다.** `scheduleKind`는 그대로 두고, 직교하는 **`origin: "AUTO" | "USER"`** 한 축만 추가한다(§7). `AUTO_FIXED` 같은 합성 이름은 저장하지 않는다.

### 1-4. 캘린더 흐름

`renderCalendar()`(`app.js:1015`) → `computeCalendarDays()`(`:988`)가 `calendarSchedule()` 전체로 `assignDisplayDays()` 실행 → 날짜별 `calendarDayItems(date)` = **`fixed`(지원금 신청 시작일) + `planned`(추천일이 그날인 항목)** → 점(최대 3개 + `+N`), 완료는 연회색 ✓ → 날짜 클릭 시 `renderSelectedDayPanel()`(`:1068`)이 카드 목록. `calendarMonthProgress()`가 "N월에 확인할 항목 N개 중 M개 확인" 계산.
`window`의 "띠" 표시는 UX 개편 초기 설계에 있었으나 현재 UI에는 없다(추천일 점으로 대체됨).

### 1-5. 체크리스트 흐름

`visibleSchedule(false)`(카테고리 필터 적용) → `renderChecklistTab()`: 대표 월령(`displayMonth`, `monthKeysOf`)별 아코디언. 0~12개월은 월별, 13~36개월은 `LATE_BUCKETS` 3구간(`app.js:1315`). 완료 상태 필터, 홈에서 넘어온 범위 보기(`checklistScope`).

### 1-6. 완료·기록 흐름

- **완료**: `completed[eventId] = {done, todo_id, occurrenceKey, recordType:"TODO_COMPLETED", recordedAt: <완료한 순간의 ISO>}`(`toggleComplete`, `app.js:1555`). 마일스톤형은 `${id}__milestone` 키 추가, 미해당은 `${id}__na`(`recordType:"NOT_APPLICABLE"`). 완료일 수정은 `setCompletionDate`(`:1636`)가 `recordedAt`만 바꾼다. **`completed` 맵 전체를 `FamilySync.updateCompleted`가 통째로 교체**한다.
- **엔진 입력**: `completionsForEngine()`이 `todo_id`가 있는 항목만 엔진에 넘긴다(접종 간격 등 `RELATIVE_TO_EVENT`가 `recordedAt` 기준).
- **기록**: ① 자동 기록 = `deriveAutoRecords(events, completed)`가 렌더 때 파생(저장 안 함) ② 직접 기록 = `HNRecords`(localStorage `hannun_records:<코드>` + `families/{코드}.records.<id>` **필드 단위** 동기화, `updatedAt` 큰 쪽이 이김, 소프트 삭제).
  `deriveAutoRecords`는 `events`에서 찾을 수 없는 완료 키를 **orphan으로 세어** 화면에 알린다(`hn-logic.js:403`) — 사용자 일정 완료 키를 `completed`에 넣으면 여기서 오염된다(§14).

### 1-7. Firebase 흐름 (요약 — 상세는 §13)

`families/{6자리코드}` 문서 1개 = `{profile, completed, records, updatedAt}`. `onSnapshot`은 이 문서 하나. 서브컬렉션·`familyCodes`·v2 코드(`sync-v2.js`)는 **앱이 로드하지 않는다**(`index.html`은 `sync.js`만, `sw.js` SHELL_ASSETS에도 `sync-v2.js` 없음).

### 1-8. PWA / iOS

- PWA: `sw.js`는 앱 셸 "네트워크 우선 → 실패 시 캐시", `data/*.json`은 캐시하지 않음, 버전은 `js/version.js` 한 곳(캐시명 `hannun-shell-v${APP_VERSION}`). 새 JS 파일은 **`SHELL_ASSETS`에 등록해야** 오프라인 캐시에 들어간다.
- iOS: Capacitor 8.5.2, `webDir: "www"`, appId `com.hoho.hannun`. `www/`는 루트 파일의 **복사본**(현재 `js/`와 동일, `diff` 결과 차이 없음)이고 `ios/`·`www/`·`node_modules/`는 git 미추적. 이 폴더에 `package.json`이 없어 **복사(`cap sync`) 절차가 어디에 정의돼 있는지 확인하지 못했다.**
- **알림 기반은 없다**: `node_modules/@capacitor/`에 `cli`·`core`·`ios`뿐, 로컬/푸시 알림 플러그인 없음. 앱 코드에도 알림 로직 없음.

## 2. 현재 `displayDate` 구조 (요청 §4 ①~⑥ 답)

> 지침의 `displayDate` = 코드의 **"추천일"(`calDisplayDays`)**. 앞으로 이 문서에서는 **`displayDay`**라고 부른다(이유: 코드가 날짜 하나가 아니라 `Map<eventId, Date[]>`이고, "Date"가 붙으면 저장 필드로 오해되기 쉬움).

| 질문 | 답 (근거) |
|---|---|
| **① 어디서 생성?** | `HNLogic.assignDisplayDays(events, {birthDate, monthKeysOf})`(`hn-logic.js:88`) **한 곳뿐.** 호출은 `computeCalendarDays()`(`app.js:988`) — `renderCalendar()` 매번, 그리고 `renderSelectedDayPanel()`에서 비었을 때 지연 호출. `todo-engine.js`·`schedule.js`는 만들지 않는다. |
| **② 어디에 저장?** | **어디에도 저장하지 않는다.** 원본 Todo JSON에도, localStorage에도, Firebase에도 없음. 모듈 변수 `calDisplayDays`(메모리 Map)뿐이고 화면을 그릴 때마다 재계산. |
| **③ 랜덤인가?** | **아니다. 결정적 탐욕 배치.** ⒜ 배치 대상: `window`(자기 기간)·`monthly`(대표 월령 한 달 = `birth + k개월 ~ k+1개월-1일`) 항목, 지원금(`행정·지원금`) 제외 ⒝ 같은 시기 접종은 한날로 묶음(`gkey`) ⒞ 좁은 기간부터, 동률은 `id` 정렬로 순서 고정 ⒟ 기간 안의 각 날을 점수화: `그날 항목수×100 + 이웃 ±1일×8 + ±2일×3`, 접종·검진이 주말이면 +50 ⒠ **최저 점수, 동점이면 가장 이른 날**(`score < bestScore`, 엄격 부등호) 선택. 탐색은 기간 시작부터 최대 120일. |
| **④ 언제 재계산?** | 렌더 때마다. 입력이 같으면 항상 같은 결과. **입력 집합이 바뀌면 바뀔 수 있다**: 생년월일·지역 수정, 미해당 처리(이벤트가 집합에서 빠짐), 접종 완료로 다음 회차의 `windowStart`가 계산되어 이벤트가 새로 나타나는 경우. 완료 여부 자체는 입력이 아니다(주석 "완료 처리해도 위치 안 바뀜"과 일치). |
| **⑤ 완료와의 관계** | **독립.** 완료 시 저장되는 날짜는 `recordedAt` = 누른 순간 또는 사용자가 고른 완료일(`setCompletionDate`). `displayDay`는 저장되지 않으므로 완료일과 같아질 방법이 없다. 엔진은 `recordedAt`만 본다. |
| **⑥ 캘린더 사용처** | 날짜 칸의 점(`calendarDayItems`), 선택일 패널 목록, 월 진행률(`calendarMonthProgress`). 체크리스트·홈·혜택은 **쓰지 않는다**(홈은 기간 기반 `classifyHomeItems`). |
| **⑦ 실제 날짜로 오해될 위험** | **중간.** 완화 장치: 캘린더 아래 안내 "혜택은 신청 시작일 · 그 외는 추천일(정해진 예정일이 아니에요)"(`index.html:175`), 카드 안에는 날짜가 아니라 기간("9월 1일 ~ 9월 30일" / 접종·검진 "2026년 9월 중")을 표기. 남는 위험: 선택일 패널 제목이 "11월 12일 (목)"이라 그 밑의 "영유아 건강검진"이 그날인 것처럼 읽힌다. 안내 문구가 그리드 아래 작은 글씨다. |

**실측(고정 테스트 프로필 은찬·2026-06-20·구로구, 이 실험은 읽기 전용)**: 이벤트 82개 중 71개 배치, 두 번 실행해 결과 동일(결정적). 기간 시작일에 정확히 놓인 것은 17개뿐 — 나머지는 분산됨(예: `HC-02` 기간 10/17~12/16 → 10/29). 임의의 이벤트 1개를 뺐을 때 다른 이벤트 이동 0건(표본 1회, 전수 검증은 아님).

**설계 규칙으로 못박을 것**
1. `displayDay`는 **화면 배치 전용 파생값.** 저장·동기화·기록·알림·완료일에 절대 쓰지 않는다.
2. **AUTO 항목에만** 적용. USER 항목은 이 함수에 넣지 않는다(§5·§6, `origin === "USER"` 가드).
3. 이 함수 시그니처·알고리즘은 이번 확장에서 **건드리지 않는다**(기존 0~36개월 캘린더 보존, 31개 테스트가 고정).
4. 오해 위험 완화는 별도 소규모 작업으로 분리(§11: 선택일 패널을 "내 일정 / 혜택 시작 / 추천 항목(정해진 날 아님)" 3묶음으로 나누어 제목·문구 분리).

```text
  아이 기본정보 ─────────▶ 규칙 엔진 ───▶ AUTO events ─┐
  (+ 현재 다니는 곳·학원 여부, 조건값일 뿐)               ├─▶ 한눈 캘린더 (전체·아이별·가족 · 월/주)
  가족 일정 저장소 ──▶ 전개(반복·예외) ──▶ USER events ─┘      └─▶ 체크리스트는 AUTO 전용 유지
     ▲ 직접입력 · 사진/OCR · 음성 · 외부연동  (모두 같은 Schedule 문서로)
```

원칙: **합치는 지점은 `buildSchedule()` 뒤 한 곳.** 엔진·Todo JSON·완료(`completed`)·기록은 그대로.

## 4. 데이터 모델 — 관계

```text
Household(가족)  ◀─ 새로 추가 (가족코드 = 사용자에게 보이는 유일한 코드, §9)
 ├─ Child[]  = 기존 families/{아이코드} 문서 그대로 (profile · completed · records) ─ 변경 없음
 │     ├─ Todo      : 정적 JSON (아이 문서에 저장 안 함, 계산만)
 │     ├─ Completed : 기존 completed 맵 (AUTO 항목 완료. USER 완료는 여기 넣지 않음)
 │     ├─ Record    : 기존 records 맵  + (선택) scheduleRef
 │     └─ Benefit   : 정적 JSON + completed(__na 포함)  ─ 변경 없음
 └─ Schedule[] = households/{hid}/schedules/{sid}  ◀─ 새로 추가 (USER 일정만 저장)
       childKeys[] 로 특정 아이에 연결, 비어 있으면 가족 전체
```

- **AUTO 일정은 저장하지 않는다** — 지금처럼 엔진이 계산. Schedule 컬렉션에는 **USER만** 들어간다(그래서 `origin`이 저장 필드가 아니라 런타임 필드이고 저장 문서에는 `sourceType`만 있다).
- 기존 `Todo → Schedule 강제 변환`은 하지 않는다(지침 §6).

## 5. Schedule 모델

### 5-1. 저장 문서 `households/{hid}/schedules/{sid}` (USER 일정)

명명 규칙은 기존 코드에 맞춘다: 필드 camelCase, 날짜는 `"YYYY-MM-DD"` 문자열(`records.date`와 동일), 시각 `updatedAt/createdAt/deletedAt`은 epoch ms 숫자(`records.js`와 동일), enum은 대문자(`TODO_COMPLETED`·`AGE_WINDOW` 관례).

| `deletedAt` | number(ms)\|없음 | | 소프트 삭제 | | `records.js`와 동일 |

### 5-2. 날짜 필드 6종의 의미 — 명확한 구분

| 이름 | 어디 있나 | 의미 | 실제 일정 날짜인가 | 저장? |
|---|---|---|---|---|
| `eventDate` | USER 저장 문서 | 사용자가 확인한 그날 | ✅ 실제 | ✅ |
| `startTime`/`endTime` | USER 저장 문서 | 그날의 시각 | ✅ 실제 | ✅ |
| `startAt`/`endAt` | **채택 안 함** | (제안 명칭) 타임스탬프 | — | — |
| `periodStart`/`periodEnd` | USER(PERIOD) 저장 문서 | 원본이 말한 기간("10월 중") | ❌ 기간일 뿐 | ✅ |
| `windowStart`/`windowEnd` | AUTO 런타임(엔진 계산) | 권장 기간 | ❌ 기간 | ❌(계산) |
| `displayDay` | AUTO 런타임(캘린더 배치) | 캘린더 위치용 "추천일" | ❌ **절대 아님** | ❌(계산) |

`startAt/endAt`을 쓰지 않는 이유(충돌 C1의 부수 결정): 이 프로젝트에서 이미 한 번 데이터 손상 버그가 있었다 — `birthDate.toISOString().slice(0,10)`이 UTC 기준이라 KST에서 하루 당겨졌다(기억 메모 2026-09-28 버그 #5). 사용자 일정의 "16:00 피아노"를 UTC 타임스탬프로 저장하면 같은 종류의 오류가 반복 일정·예외일 비교에서 더 크게 난다. **날짜 `YYYY-MM-DD` + 시각 `HH:mm` 로컬 문자열**로 저장하고 타임존 변환을 하지 않는다(Asia/Seoul 전제).

### 5-3. 런타임 이벤트에 추가되는 (모두 선택) 필드 — AUTO 이벤트는 값이 없어도 동작

`origin`("AUTO"|"USER", 없으면 AUTO로 취급), `sourceType`, `scheduleId`, `occurrenceDate`(반복 전개된 날), `startTime`, `endTime`, `assignee`, `childKey`, `isRecurring`. 이벤트 `id`는 `u:${sid}` (비반복) / `u:${sid}@${YYYY-MM-DD}` (반복 회차) — **`completed`의 키 공간(`todoId__occ`, `SEOUL-…`)과 절대 겹치지 않는다.**

## 6. 날짜 처리 규칙

| 유형 | 저장되는 날짜 | 캘린더 표시 | `displayDay` | 원본에 없는 날짜 생성 |
|---|---|---|---|---|
| **AUTO_FIXED** (`fixed`, 혜택) | `fixedDate` = 신청 시작일(실제 규정 기반 계산) | 그날 원 | 미사용 | 금지 |
| **AUTO_PERIOD** (`window`) | `windowStart/End` 계산 | **추천일 점**(기간 안) | **사용** | 표시용 추천일만 허용, 저장·완료·알림 금지 |
| **AUTO_AGE** (`monthly`) | 없음(대표 월령의 한 달) | 추천일 점(대표 월령 한 달 안) | **사용** | 위와 동일 |
| **USER · FIXED** | `eventDate`(+시각) — 사용자가 확인한 값만 | 그날 표시(시각 있으면 시각순) | **미사용** | **금지** |
| **USER · PERIOD**(날짜 미확정) | `periodStart/End`만, `eventDate: null` | **점이 아니라 기간 표시**(월 화면: "이 달 기간 일정" 목록 / 주 화면: 기간 띠). §11 | **미사용(가드 필수)** | **금지** |
| **OCR/VOICE 후보** | 원문에 있는 값만 후보로. 연도·요일이 원문에 없으면 필드를 **비워 두고 확인 화면에서 사용자가 채움** | 확인 전 저장·표시 안 함 | 미사용 | **금지**(§7) |

- "10월 중 부모 상담" → `dateKind: PERIOD, periodStart: 2026-10-01, periodEnd: 2026-10-31, eventDate: null` (정상). `eventDate: 2026-10-15`는 금지.
- 상대 표현("다음 주 화요일")은 **오늘 날짜 기준으로 확정 가능한 경우에만** 후보 날짜로 제안하고, 화면에 "2026-10-06(화)로 이해했어요"를 보여 준 뒤 사용자가 확인해야 저장한다(확인 없이 저장 금지).
- **구현 가드(필수)**: `assignDisplayDays`·`classifyHomeItems`·`calendarMonthProgress`·`todayItems`·`deriveAutoRecords` 앞단에서 `e.origin === "USER"`를 제외(또는 별도 처리). 이 가드가 없으면 USER 기간형이 "추천일"을 얻어 실제 날짜처럼 보인다.

## 7. 출처(origin / sourceType) 구조

```text
origin      : AUTO | USER                    ← 런타임 이벤트에만 존재(저장 문서는 항상 USER)
sourceType  : MANUAL | OCR | VOICE | IMPORT  ← USER 저장 문서 필드. AUTO는 없음(= 엔진)
```
- 지침의 `ENGINE`은 `origin: AUTO`로 표현(엔진 일정은 저장하지 않으므로 값이 필요 없음).
- 이름 충돌 없음: 기존 코드의 `source`는 "출처 기관"(`"국민건강보험공단"`, `event.source`)이라 **`source`를 재사용하지 않고 `sourceType`으로 분리**했다.
- OCR/VOICE/IMPORT는 **같은 Schedule 문서**로 들어간다(원칙 4). 차이는 `sourceType`·`provenance`뿐이고 저장 전에 반드시 "확인 화면"을 거친다. 입력 방식별 별도 구조 없음.

## 8. 반복 일정

### 8-1. 저장 구조 (RRULE 축소판 — 외부 라이브러리 없음)

```jsonc
"recurrence": {
  "freq": "WEEKLY",            // v1은 WEEKLY만. 이후 MONTHLY 추가 여지
  "interval": 1,               // 매 N주
  "byDay": ["TU", "TH"],       // 요일
  "startDate": "2026-10-06",   // 첫 적용일(확정값만)
  "until": "2027-02-28"        // 종료일. null 허용(무기한) — 전개는 항상 화면 범위로 자른다
},
"startTime": "16:00", "endTime": "16:50",
"exceptions": {
  "2026-10-08": { "status": "CANCELLED", "note": "휴강" },
  "2026-10-13": { "status": "RESCHEDULED", "movedTo": {"date":"2026-10-14","startTime":"17:00","endTime":"17:50"} },
  "2026-10-15": { "status": "DONE" },
  "2026-10-20": { "assignee": {"role":"DAD"} }      // 그 회차만 담당자 변경
}
```

### 8-2. 원칙
- **회차는 저장하지 않는다.** 화면에 필요한 범위(월/주)만 순수 함수 `expandOccurrences(schedule, rangeStart, rangeEnd)`로 전개 → 이벤트 배열. AUTO가 "계산만, 저장 최소"인 것과 같은 철학이라 이 코드베이스에 자연스럽다.
- 저장량은 **예외 개수에 비례**(회차 수와 무관) → 주 2회 × 1년(≈100회)도 문서 크기 변화 없음. **반복 일정의 완료를 `completed` 맵에 넣지 않는 이유**: 넣으면 회차마다 키가 쌓이고, `completed`는 통째 교체(§13)라 충돌·1MB 압박이 가장 커진다.
- 반복 일정의 "완료"는 대부분 의미가 없다(수업이 끝났다고 체크하지 않는다). 필요할 때만 `exceptions[date].status: "DONE"`.
- 날짜 계산은 **로컬 날짜 산술**(`new Date(y, m, d + n)`, `hn-logic.js`의 `addDaysD`와 동일한 방식) — UTC 변환 금지.
- 공휴일 자동 휴강은 **넣지 않는다**(사용자가 예외로 입력. 공휴일 데이터는 외부 연동 트랙).
- 편집 범위 UX: "이 날만 / 이후 모두"는 v1에서 **"이 날만(예외)" + "전체 수정"** 2가지로 시작. "이후 모두"는 문서 분할(`until` 지정 + 새 문서)로 구현 가능하나 후순위.

### 8-3. 기존 코드에 미치는 영향
없음(신규 순수 함수 `js/user-schedule.js`). 단, 전개 결과가 캘린더 렌더에 들어오므로 `calendarDayItems`·`renderSelectedDayPanel` 수정이 필요(§11).

## 9. 다자녀

### 9-1. 현재 (문제)
- 아이 1명 = 코드 1개 = `families/{코드}` 1문서. "가족" 개념 없음. `hannun_children`(localStorage)은 **이 기기에서 본 코드 목록**일 뿐(`app.js:2183`).
- 결과: ⒜ 다른 기기에서는 형제 코드를 별도로 입력해야 함 ⒝ "가족 전체" 일정을 둘 자리가 없음 ⒞ "전체/첫째/둘째" 뷰는 아이별 문서를 각각 받아야 함.

### 9-2. 선택지 (충돌 C7 — 결정 필요)

| 안 | 내용 | 기존 영향 | 장점 | 단점 |
|---|---|---|---|---|
| **A** | 새 개념 없이 각 아이 문서 아래 `schedules` 서브컬렉션. 가족 공통 일정은 "대표 아이" 문서에 저장 | 아이 문서에 서브컬렉션 추가(규칙 추가) | 가장 작은 변경 | 가족 일정의 집이 임의(대표 아이). 형제 크로스 기기 공유 미해결. **나중에 옮기려면 마이그레이션** |
| **B (추천)** | **`households/{hid}` 새 문서 = 가족.** `children: [{code,name,order}]` 목록 + `schedules` 서브컬렉션. 아이 문서(`families/{코드}`)는 **완전히 그대로** | 기존 문서·`completed`·`records` 무변경. 아이 문서 `profile`에 `householdCode`(선택) 한 필드만 추가 | 서버에서 형제 공유 해결, 가족 일정 집이 명확, 기존 데이터 0 마이그레이션, 지연 생성(쓰는 사람만 생성) | 코드가 2종(가구·아이) — UI에서는 가구 코드 하나만 노출 |
| **C** | 기존 v2 스키마(`families/{familyId}/children/{childId}/completions`)로 전면 이관 | 전부 변경 | 이상적 최종형(엔티티별 문서) | 현재 앱 기능(records·na·memo·사진·stage)을 못 담음(§13), 사용자 코드가 바뀜, 프로덕션 미검증, 이번 목표(작은 변경)와 반대 |

**추천: B.** 이유: (1) 기존 데이터·엔진·기록·완료 코드가 무변경이라 회귀 위험이 가장 작고 (2) 지금 필요한 세 가지(가족 일정의 집·형제 서버 공유·전체/아이별 필터)를 한 번에 해결하며 (3) v2의 핵심 원리("엔티티별 문서, 코드는 간접 참조")를 채택하되 이관을 강요하지 않는다. C는 "나중에 아이 데이터를 옮길 이유가 생기면" 별도 결정.

### 9-3. B안 동작
- **지연 생성**: 사용자가 (a) 형제를 추가하거나 (b) 첫 사용자 일정을 만들 때 household를 만든다. 기존 단일 아이 사용자는 아무 변화 없이 계속 쓴다. 이때 기존 아이 코드를 `children[0]`으로 연결하고 아이 문서 `profile.householdCode`에 기록.
- **새 기기**: 가구 코드 1개 입력 → 아이 목록 로드 → 각 아이 코드로 기존 `fetchFamily` 경로 재사용.
- **기존 코드 입력**(아이 코드)만 알던 사용자도 그대로 동작 — `profile.householdCode`가 있으면 가족 전체를 안내.
- **활성 아이**: 기존 `switchToChild`(아이 전환) 유지. **"전체"는 활성 아이 전환 없이 모든 아이의 AUTO 이벤트를 각자 계산해 합쳐 보여 주는 읽기 뷰**(엔진이 순수 함수라 N번 호출로 충분, 각 아이 완료 상태는 그 아이 문서의 `completed`).
- 이벤트 `id`는 아이 간 충돌하므로 전체 뷰에서는 `childKey`를 함께 들고 가서 `${childKey}|${id}`로 구분(표시·완료 토글 시 해당 아이 문서로 라우팅). **이 부분은 `app.js`의 `completed`가 "활성 아이 1명" 전역이라는 가정과 충돌**하므로 "전체" 뷰는 **1차에서는 USER 일정 + 활성 아이 AUTO**만 합치고, 형제 AUTO까지 한 화면에 섞는 것은 §H 단계 3의 후반으로 둔다(충돌 C7-b).

### 9-4. 다자녀가 증가시키는 것
아이 N명 → `families/{코드}` N개(각자 1MB 여유), `onSnapshot` N개(4명 이내 권장, 상한 두기). 사진(base64 240px)은 아이 문서 안에 있어 아이 수만큼 분산되므로 1MB 압박 없음.

## 10. 담당자

- 저장: `assignee: { role: "MOM"|"DAD"|"GRANDPARENT"|"CAREGIVER"|"OTHER", label?: string }` — 지침의 `MOM/DAD/GRANDPARENT/OTHER`에 **`CAREGIVER`(이모님·돌보미) 추가를 제안**(조부모 돌봄과 다른 실제 케이스가 많음. 결정은 사용자에게).
- **역할 라벨은 계정이 아니라 표시**다. 이 서비스는 로그인이 없고 코드 하나를 여러 기기가 공유하므로 "누가 담당"을 인증할 수 없다 — 그래서 사람 ID가 아니라 **역할(role)+표시명(label)**. 가구 문서에 `assigneeLabels: {MOM:"엄마", OTHER:"이모님"}`을 두어 가족마다 이름을 바꿔 쓴다.
- 회차별 변경은 `exceptions[date].assignee`로 덮어쓴다(§8).
- 기존 `HNRecords.authorLabel()`(기기별 작성자 표시명, `hannun_author_label`)과 **다른 개념**임을 UI에서 분리("이 기기 사용자" vs "담당자").
- **충돌·공백 감지에 필요한 데이터(구현은 다음 단계)**: 시각이 있는 일정(`startTime`) + `assignee` 유무 → "담당 미정". 돌봄 공백은 **학교·기관의 휴업일/재량휴업일 데이터**가 필요한데 지금 그런 데이터도 스키마도 없다 → 사용자가 입력하는 `category: INSTITUTION` 일정(예: "재량휴업일")과 "돌봄 있음" 표시를 조합하는 수동 방식이 1차, 기관 API는 후순위. **이번에는 필드만 예약**(`assignee`, `startTime`, `endTime`, `category`)하고 로직은 만들지 않는다.

## 11. 캘린더 UX

### 11-1. 원칙
- **월 화면은 지금 그대로 유지**하고 그 위에 얹는다. 주간은 신규.
- 상단: `[월][주]` 토글 + 필터 칩 `전체 · 아이별(이름) · 가족` + 토글 `자동 일정 함께 보기`(기본 ON).
- 필터 상태는 **캘린더 화면 로컬 상태**(체크리스트의 카테고리 필터 `activeCats`와 분리 — 기존 규칙 "달력은 체크리스트 필터와 무관하게 전체"를 유지).

### 11-2. 표시 규칙 (Q9: AUTO와 USER를 어떻게 구분하나)

| | AUTO | USER |
|---|---|---|
| 날짜 칸 표식 | 원(카테고리색), 완료 시 ✓ | **다른 모양**(예: 짧은 가로 막대) + 아이색/가족색. 시각 있으면 텍스트 |
| 문구 | "추천일"·"신청 시작"(기존 안내) | "내 일정" 뱃지 + `16:00` |
| 완료 | 체크(엔진) | 비반복만 체크, 반복은 예외로만 |
| 선택일 패널 | **"추천 항목 — 정해진 날이 아니에요"**로 묶음 제목 분리 | **"내 일정"**(시간순)이 맨 위 |

선택일 패널을 **3묶음**(내 일정 / 혜택 신청 시작 / 추천 항목)으로 나누는 것은 §2 ⑦의 오해 위험도 함께 줄인다(패널 제목 "11월 12일"은 그대로여도 "추천 항목" 소제목이 붙음).

### 11-3. USER 기간형(날짜 미확정) 표시 — 현재 UI에 없는 부분 (충돌 C5)
현재 캘린더에는 기간 띠가 없고(추천일 점으로 대체됨), 점 표시는 "그날"로 읽힌다. **USER 기간형에 점을 찍으면 원칙 C 위반**이다.
- 선택지: ⒜ 월 화면 그리드 아래 **"이 달 기간 일정" 목록**(예전 `remaining-grid`와 같은 방식) ⒝ 날짜 칸에 연한 띠 ⒞ 표시하지 않음.
- **추천: ⒜.** 기존 그리드 로직을 안 건드리고 그리드 아래 섹션 하나만 추가. 주간 화면에서는 주 상단에 기간 띠. (띠는 칸이 좁아 3개월짜리가 모든 칸을 덮는 소음 문제가 있다.)

### 11-4. 홈·체크리스트와의 관계
- **"이번 달 챙길 것"(홈)은 그대로**(AUTO 기간 기반). USER는 여기에 섞지 않고 **"오늘·이번 주 일정" 카드를 별도로** 추가(6~8단계, 알림·충돌 감지와 함께). `classifyHomeItems`에 USER를 넣지 않는다.
- 단계적 진행: 월 화면에 USER 표시 → 주간 화면 → 홈 카드.

## 12. 온보딩 UX — "현재 다니는 곳 / 학원 여부"

### 12-1. 위치·방식
현재 폼: 이름 → 생년월일 → 몇째 → 지역 → 제출. **지역 아래에 칩 2개 필드**를 추가(기존 칩 UI `order-chips`/`region-chips` 재사용):

```text
현재 다니는 곳   ( ) 가정양육  ( ) 어린이집  ( ) 유치원  ( ) 초등학교  ( ) 아직 몰라요(=건너뜀)
학원·수업        ( ) 없어요    ( ) 있어요                            ( ) 아직 몰라요
```
- **선택 사항, 건너뛰기 가능**, 기본은 "아직 몰라요"(미설정). 이유: ⒜ 가입 장벽을 늘리지 않음 ⒝ **나이로 자동 추정해 값을 채우면 "데이터에 없는 것을 만들지 않는다" 원칙 위반** — 만 3세 아이가 어린이집에 다니는지는 서비스가 모른다. 나이 기반으로는 **"이 아이는 어린이집·유치원 시기예요, 다니는 곳을 알려주세요"라는 제안 배너**까지만.
- 상세(기관명·반·선생님·시간표·담당자)는 **묻지 않는다** — 가입 후 "일정 추가" 흐름에서만.
- 값은 **바뀌는 정보**(어린이집→유치원→초등)라서 프로필 수정(연필 아이콘 시트, `showProfileSheet`)에서 바꿀 수 있어야 한다. 임신 중(`stage: pregnant`)에는 두 필드를 숨김.

### 12-2. 저장 — 기존 구조 재사용
- `profile`에 `care`(`HOME`|`DAYCARE`|`KINDERGARTEN`|`ELEMENTARY`|null)·`academy`(true|false|null) 추가. `profileToPlain`/`profileFromPlain`의 필드 목록에 2줄 추가(**`stage`와 섞지 않는다** — `stage`는 born/pregnant 전용).
- Firestore는 `profile` 맵 내부 키를 규칙이 제한하지 않는다(규칙은 문서 **최상위 키**만 allow-list) → **규칙 변경 없이 저장 가능**.
- 옛 데이터(값 없음) = `null` = 현재와 동일 동작. **마이그레이션 불필요.**

### 12-3. 조건값으로 쓰기 — 엔진이 이미 지원
`familyDeclaredAttributes: {}`(현재 빈 값)에 `{care, academy}`를 채우면, Todo 데이터의 `eligibilityCondition: {attribute:"care", requiredValue:"KINDERGARTEN"}`로 항목을 걸러낼 수 있다(값 없으면 `UNKNOWN` → `schedule.js`가 status null이라 숨김).
**한계(정직하게)**: `requiredValue`는 **단일 값 동등 비교**(`attrValue !== requiredValue`)라 "어린이집 또는 유치원"을 표현할 수 없다. 대안: ⒜ Todo를 두 개로 복제 ⒝ 엔진에 `requiredValues: []` 소규모 확장(낮음). 새 Todo 데이터를 만드는 것은 이번 범위 밖(공식 출처 조사 트랙).
※ 기존 어린이집 항목 `CR-01~04`는 지금 모든 아이에게 6개월부터 노출된다(변경하지 않음).

- 이 규칙 파일은 배포 시 v2 컬렉션 규칙(`familyCodes`, `children`, `completions`)도 함께 켜 놓는다 — 쓰는 코드는 없다.

### 13-2. 기존 v2 설계 대 현재 코드 — 충돌 C3 (보고 형식)

- **현재 구조**: 설계 문서 v2는 `families/{familyId}/children/{childId}/completions/{todo__occ__recordType}`, `familyCodes/{code}`, 코드 재발급. 작성일 2026-09-28. 이후 앱은 v1 구조 위에서 계속 진화했다.
- **문제**
  1. v2 `children` 규칙은 `birthDate, gender, childDeclaredAttributes, updatedAt`만 허용 → 현재 프로필의 `name, birthOrder, stage, province, district, photoDataUrl`을 저장할 수 없다.
  2. v2 `completions`는 `recordType in [MILESTONE_REPORTED, TODO_COMPLETED]`만 생성 허용, 수정은 `recordedAt/createdAt`만 → 현재 앱의 `NOT_APPLICABLE`(`__na`), `memo`를 저장할 수 없다.
  3. `records`(직접 기록) 저장소가 v2에 없다. 사진(프로필)도 없다.
  4. 마이그레이션 계획의 "레거시 일정 ID ↔ `todo_id` 매핑 미해결" 문제는 **지금은 해소**됐다(현재 `completed` 키가 `todoId__occurrenceKey`라 그대로 대응) — 그러나 지역 혜택 ID(`SEOUL-001`)와 `__na`/`__milestone` 접미 키는 별도 처리가 필요.
  5. 마이그레이션은 **가족코드를 새로 발급**한다(v1 코드 → 새 코드). 이미 공유된 코드가 있는 사용자에게 큰 변화이며, 함수는 실행·검증된 적이 없다(`sync-v2.js` 헤더·마이그레이션 계획 문서가 명시).
  6. v2가 풀려는 문제 중 **동시 수정(마지막 쓰기 우선)**은 진짜로 남은 위험이라 방향은 옳다.
- **선택지**: ① v2를 현재 앱에 맞게 고쳐(스키마·규칙·마이그레이션) 전면 채택 ② v2 폐기, v1 유지 + 필요한 곳만 서브컬렉션 추가 ③ **v2의 원리만 채택**(엔티티별 문서, 코드 간접 참조)하고 새 데이터(가구·일정)부터 그 방식으로, 기존 아이 문서는 그대로.
- **추천: ③.** 새 기능(household·schedules)은 문서 단위 쓰기로 처음부터 안전하게, 기존 `families/{코드}`는 무변경. `completed` 통째 교체 문제는 **별도 개선 과제**(예: `completed.<id>` 필드 단위 갱신 — `records`가 이미 쓰는 방식)로 분리해 다루고 이번 확장의 필수조건으로 묶지 않는다.
- **기존 기능에 미치는 영향**: 없음(추가만). `sync-v2.js`·`migrate…`는 계속 미사용 — **폐기할지 유지할지는 별도 결정**(문서 "미사용 코드 정리" 항목으로 제안).

| 구분 | 항목 |

| **지금(기반)** | ① 배포된 규칙 실제 내용 확인 ② `households`·`schedules` 규칙 설계(추가만) + 규칙 테스트(`test/firestore-rules.logic.test.js` 확장) ③ 문서 크기 실측 스크립트(가장 큰 가족 문서) ④ 새 데이터는 필드/문서 단위 쓰기 + 실패 시 화면 표시 원칙 확정 |

### 13-4. 새 규칙(안) 개요 — 구현 아님, 설계만
```text
households/{hid}                : get 허용, list 금지, create/update 는 허용 키 allow-list(children, assigneeLabels, updatedAt)
households/{hid}/schedules/{sid}: get/list(이미 hid를 아는 경로) 허용, create/update 는 허용 키 allow-list + v==1 + sourceType∈enum,
                                  delete 금지(소프트 삭제 deletedAt)
families/{code}.profile         : 변경 없음(내부 키 미제한). householdCode/care/academy 그냥 저장됨
```
`update` allow-list는 기존 규칙처럼 `affectedKeys().hasOnly([...])`로. **잘못된 규칙 하나가 전체 동기화를 막을 수 있으므로**(규칙은 문서 단위가 아니라 프로젝트 단위 배포) 에뮬레이터 없이 배포하지 않는다 — 이 환경엔 Firebase CLI 인증이 없어 사용자 쪽에서 배포해야 한다.

### 13-5. 마이그레이션 방법
| 데이터 | 필요? | 방법 |
|---|---|---|
| 기존 `families/{코드}` (profile/completed/records) | **불필요** | 무변경. 옛 클라이언트(캐시된 PWA·iOS)와 새 클라이언트가 같은 문서를 계속 안전하게 공유 |
| `profile.care/academy/householdCode` | 불필요 | 없으면 `null`(기존 동작) |
| localStorage | 불필요 | 키 **추가만**(`hannun_household_code`, `hannun_user_schedules:<hid>` 캐시). 기존 키(`yukjigi_*`, `hannun_*`) 불변 |
| household 생성 | 지연(첫 사용 시) | 사용자 동의 화면 후 생성. 실패해도 기존 기능 영향 없음 |

**구버전 클라이언트 공존**: 새 최상위 필드를 아이 문서에 추가하지 않으므로(`profile` 내부만), 옛 클라이언트의 `updateProfile`(merge)·`updateCompleted`(update) 동작에 영향 없음. 단 옛 클라이언트의 `profileToPlain`은 `care/academy/householdCode`를 모르므로 **`updateProfile`이 `set({profile: {...}}, {merge:true})`(중첩 맵 병합)라 기존 필드를 지우지 않는지는 실제 확인 필요**(Firestore merge는 맵 필드를 병합하므로 지우지 않을 것으로 보이나, 실기기 확인을 1단계 체크리스트에 넣는다).

**C1. 지침의 `displayDate`가 코드와 다르다**

**C2. "엔진 하드코딩 없음" 이전 답변 정정 + 월 산술**
- 현재: `todo-engine.js`에 연령 상한 없음. 그러나 `app.js:764`(`ageInMonths(...) <= 36` 필터), `:1315-1324`(`LATE_BUCKETS` 끝 36), `:1412`(`Math.min(36,…)`, `endMonth==null → 36`), 표시 문구(0~36개월) 4곳. Todo 데이터 최대 월령은 이미 72(혜택 SB-08 등)라 필터 때문에 숨겨질 뿐이다. 그리고 `todo-engine.js:24` `MONTH_DAYS = 30`: 월령 N개월의 창이 `출생일 + N×30일`로 계산되어 **N이 클수록 어긋난다**(36개월≈16일, 72개월≈32일, 144개월≈64일 일찍). 지금 0~36개월 데이터의 소수 월령(0.47 = 14/30)이 이 근사에 맞춰 역산돼 있어 그대로 두는 게 맞다.

```text
profile(생년월일·지역·몇째·stage) ─▶ 정적 Todo JSON(9카테고리)+혜택 JSON
   ─▶ TodoEngine(순수함수, 기간 계산) ─▶ buildSchedule() = events[] (fixed|window|monthly, 6그룹 카테고리)
   ─▶ visibleSchedule()(36개월 이하 필터)
        ├ 홈 · 체크리스트(월령 아코디언) · 혜택 · 기록(완료에서 파생 + 직접기록)
        └ 캘린더: assignDisplayDays()로 "추천일"을 화면마다 계산(저장 안 함)
저장: families/{코드} 통짜 문서 {profile, completed(통째 교체), records(필드 단위)}, 아이 1명 = 코드 1개
```

## B. 목표 구조

```text
Household ─ Child[](= 기존 families/{코드} 무변경) ─▶ 엔진 ─▶ AUTO events ┐
   └ schedules/{sid}(USER 일정만 저장; 반복=규칙+예외)  ─▶ 전개 ─▶ USER events ┴▶ 한눈 캘린더(월/주, 전체·아이별·가족)
프로필 조건값(care·academy)은 엔진의 eligibilityCondition으로 재사용. 체크리스트·기록·혜택은 AUTO 그대로.
```

## C. 유지할 것
1. 엔진·Todo JSON 전체와 `completed`/`records` 구조, 완료 처리
2. `scheduleKind`(fixed/window/monthly) enum, `assignDisplayDays`(추천일) 알고리즘과 그 안내 문구
3. 체크리스트(AUTO 전용), 혜택 탭, 홈 "이번 달 챙길 것", 기존 아이 전환·가족코드·PWA·iOS 구조

## D. 변경할 것
1. `origin`(AUTO/USER) 가드를 캘린더 진행률·추천일·홈·기록에 추가
2. 36 하드코딩 4곳을 설정값으로(§19)
3. 선택일 패널을 3묶음(내 일정/혜택 시작/추천 항목)으로 분리해 오해 위험 완화
4. 프로필에 `care`·`academy`·`householdCode` 저장, 온보딩·프로필 수정에 칩 2개

## E. 새로 추가할 것
1. **Schedule**: `households/{hid}/schedules/{sid}` + `js/user-schedule.js`(검증·전개·이벤트 변환, 순수 함수 + 테스트)
2. **다자녀**: `households/{hid}`(가족 코드, 아이 목록, 담당자 라벨), 지연 생성
3. **사용자 일정**: 직접 입력 화면(제목·아이·날짜/기간·시간·담당자)
4. **반복 일정**: WEEKLY + 예외 맵
5. **담당자**: `assignee` 역할+표시명
6. (후순위) 알림, 충돌·공백 감지, OCR, 음성, 외부연동

## G. 데이터 마이그레이션 필요 여부

- **불필요**(이번 확장 범위). 기존 `families/{코드}`·`completed`·`records`·localStorage 키는 변경하지 않는다. 새 필드(`care`/`academy`/`householdCode`/`scheduleRef`)는 모두 선택이며 없으면 현재 동작.
- 새 컬렉션(`households`, `schedules`)은 **지연 생성**(사용한 가족만).
- v2 전면 이관은 별도 결정 사항(§13-2 ③은 이관 없이 원리만 채택).
- 확인 필요: 옛 클라이언트의 `updateProfile`(merge)이 새 `profile` 하위 필드를 지우지 않는지 실기기 확인.
