작성: 2026-10-04 · 상태: **계획 확정 대기(구현 없음)** · 기준: v1.12.80
근거 문서: `한눈육아-F0-최종-서비스-설계.md` §6(S7 사진으로 일정 등록), `js/user-schedule.js`(`normalizeFromCandidate`·I8·I9), `firestore.rules`(provenanceOk), `한눈육아-운영규칙.md`

## 1. 목표와 원칙

**목표** 직접 입력 폼은 다른 캘린더(구글·네이버)와 차별점이 없으므로, **음성·사진으로 일정 초안을 만들고 사용자는 확인만** 하게 한다.

```
음성  → STT ─────┐
사진  → OCR ─────┼→ 텍스트 → [공통] 일정 후보 파서 → 일정 초안 → [공통] 확인 화면 → 저장(기존 USER 일정 문서)
직접입력 ────────┘ (기존 폼, 변경 없음)
```

**불변 원칙**
1. **확인 없이 저장하지 않는다.** 서버 규칙(I8)이 `sourceType != MANUAL` 일정에 `provenance.confirmedByUser == true`를 요구하므로, UX 문구도 "자동 등록"이 아니라 "초안을 만들어 드려요 → 확인 후 저장"으로 쓴다.
2. **말하지(찍히지) 않은 값은 추측해서 채우지 않는다**(I9). 누락·모호 항목만 사용자에게 묻는다.
3. **입력 방식 때문에 새 일정 구조를 만들지 않는다.** 저장은 기존 `households/{hid}/schedules/{sid}` 문서 + `sourceType`(`VOICE`/`OCR`)뿐이다.
4. **STT·OCR 계층과 파싱·확인·저장 계층을 분리한다.** 웹으로 먼저 만들고 iOS/Android 네이티브로 교체해도 STT 이후 로직은 한 줄도 안 바뀌어야 한다.
5. 사용자가 정해진 문장 형식을 외우게 만들지 않는다.
6. 원본 사진·음성 오디오는 저장하지 않는다(기존 원칙). 인식 원문 텍스트 저장 여부는 §10 결정 3.

## 3. 모듈 구조

모두 순수 모듈(UMD, DOM·Firestore 비의존)과 얇은 화면 모듈로 나눈다.

```
js/capture/
  speech-input.js        SpeechInputAdapter 계약 + 어댑터 선택(createSpeechInput)
  speech-web.js          WebSpeechAdapter (SpeechRecognition / webkitSpeechRecognition)
  speech-fallback.js     KeyboardFallback (입력칸 + "키보드 마이크로 말하기" 안내)
  speech-native.js       NativeAdapter 슬롯 (이번 범위: 계약·스텁·문서만. 구현은 앱 재배포 단계)
  text-recognition.js    TextRecognitionAdapter 계약(사진 쪽, §8)
js/capture/parse/
  datetime-ko.js         한국어 날짜·시간 규칙 파서 (순수, today 주입)   ← 음성·사진 공통의 핵심
  candidate-parser.js    텍스트 → ScheduleCandidate[] (제목·분류·대상·반복·장소 포함)
  ai-parser.js           AI 보강 호출 인터페이스 (텍스트만 전송, §7)
js/capture/
  draft-view.js          일정 초안 확인 화면 (음성·사진 공용)
  capture-flow.js        입력 → 파서 → 초안 → 저장 흐름 연결, user-schedule.js 호출
```

### 3-1. SpeechInputAdapter 계약 (플랫폼 비의존)
```js
// 어댑터 인터페이스
{
  id: "web-speech" | "keyboard" | "native-ios" | "native-android",
  isAvailable(): Promise<{ ok: boolean, reason?: "unsupported"|"permission-denied"|"insecure-context"|"in-app-webview"|"no-network" }>,
  start({ lang: "ko-KR", onPartial(text), onFinal(result), onError(err) }): Promise<void>,
  stop(): void,
}
// STT 결과(어댑터가 무엇이든 이 형태로만 내보낸다)
SttResult = { text: string, lang: "ko-KR", isFinal: boolean, source: <adapter id>, alternatives?: string[] }
```
- 어댑터 선택은 `createSpeechInput()` 한 곳에서만 한다. 선택 순서: **native(있으면) → web-speech(가능하면) → keyboard 폴백.**
- 파서 이하는 `SttResult.text`만 본다. 어댑터 id를 분기 조건으로 쓰지 않는다.
- 음성 버튼은 **숨기지 않는다.** `isAvailable()`이 실패하면 사유별 안내(예: "이 환경에서는 음성 인식을 쓸 수 없어요. 키보드의 마이크 버튼으로 말해 보세요")와 함께 KeyboardFallback 입력칸을 연다. 폴백도 결과는 같은 `SttResult` → 같은 파서로 들어간다.

### 3-2. 일정 후보(ScheduleCandidate)
`normalizeFromCandidate`의 입력 필드(title·category·scope·childKeys·eventDate·periodStart/End·allDay·startTime·endTime·location·memo)에 **필드별 상태**를 덧붙인다.
```js
field = { value, state: "found" | "confirm" | "missing", evidence?: "원문 일부", by: "rule" | "ai" }
// found   : 원문에 있고 규칙이 확정 (예: "내일" → 오늘 기준 계산)
// confirm : 후보값은 있으나 모호 → 확인 화면에서 강조, 사용자가 선택해야 저장 가능
// missing : 원문에 없음 → 빈칸, 사용자가 채워야 저장 가능
```
- 저장 시 `provenance = { confirmedByUser: true, method: "rule"|"ai"|"mixed", kind: "voice"|"photo" }`만 남긴다. `evidence`·`state`는 화면용이고 저장하지 않는다. (`provenance`에 추가 키를 넣어도 규칙상 제한은 없어 보이나 **구현 시 규칙 시뮬레이션으로 확인** — dev.)
- `needsUserInput`(기존 계약)은 `state != found`인 필수 필드에서 파생한다. 새 검증기를 따로 만들지 않는다.

## 4. 공통 규칙 파서 (이 계획의 핵심)

`parseKoDateTime(text, today)` — **`today`("YYYY-MM-DD")를 인자로 받는 순수 함수.** `new Date()` 직접 호출 금지(테스트 가능성). 날짜 산술은 기존 규칙대로 로컬 Date만, `toISOString` 금지(I11). 주는 월요일 시작(기존 `mondayOf`와 동일).

### 4-1. 날짜
| 표현 | 결과 | state |
|---|---|---|
| 오늘·내일·모레·글피 | today 기준 계산 | found |
| 10월 23일 / 23일 / 10/23 | 연도 없으면 today 이후 가장 가까운 해당 날짜 | found (연도가 오늘 연도를 넘으면 confirm) |
| 2026년 10월 23일 / 2026-10-23 | 그대로 | found |
| 금요일 / 금요일에 (요일만) | today 이후 가장 가까운 그 요일(오늘이 그 요일이면 **오늘이 아니라 confirm**) | found / confirm |
| 이번 주 X요일 | 월요일 시작 주 기준. **이미 지난 날짜가 나오면** | confirm |
| 다음 주 X요일 | 월요일 시작 주 기준 다음 주. **today가 일요일이면** (구어체상 의미가 갈림) | confirm |
| 다음 달 5일, 이번 달 말 | 계산 | found / 말일은 confirm |
| N일 뒤·N주 뒤 | 계산 | found |
| 날짜 표현 없음 | 값 비움 | **missing** (오늘로 기본 채움 금지) |
| 지난 날짜가 나옴 | 값 유지 + 경고 | confirm ("이미 지난 날짜예요") |

### 4-2. 시간
| 표현 | 결과 | state |
|---|---|---|
| 오후 3시 / 3시 반 / 3시 30분 | 15:00 / 15:30 / 15:30 | found |
| 아침 9시 / 저녁 7시 / 밤 11시 | 09:00 / 19:00 / 23:00 | found |
| 15시 / 15:30 | 그대로 | found |
| **오전·오후 없는 "3시"** | 후보 15:00·03:00 제시 | **confirm** |
| 점심(때)·저녁·아침 (시각 없음) | 시각 비움, 힌트만 표시 | missing (12:00으로 채우지 않음) |
| 시간 표현 없음 | allDay 후보로 두고 | missing(종일 여부는 사용자 선택) |
| 3시부터 5시까지 | 시작·종료 | found |

### 4-3. 그 외 필드
- **대상(아이)**: 연결된 아이 이름·애칭과 매칭(조사 "이·가·는·랑" 제거). 둘 이상 매칭이면 복수 선택. 이름이 없으면 scope 기본값(앱 현재 컨텍스트)을 쓰되 `confirm`으로 표시.
- **분류**: 키워드 사전 → `LESSON·INSTITUTION·MEDICAL·FAMILY·ETC`. 사전 밖은 `missing`이 아니라 `ETC` + confirm.
- **제목**: 날짜·시간·이름·조사를 제거한 나머지 구. 비면 missing. 100자 제한(`LIMITS.titleMax`).
- **반복**: "매주 화·목", "격주 월요일" → 기존 WEEKLY 규칙(B5). 그 밖의 반복("매달")은 **지원하지 않음**(규칙이 WEEKLY만 허용) → 한 번짜리로 두고 안내.
- **장소**: "…에서" 패턴 및 사전(병원·학원 이름은 제목에 두고 장소는 추측하지 않음). 원문에 명시된 것만.
- **한 문장 여러 일정**("내일 소아과 모레 어린이집 상담")은 1차에서 **분리하지 않고 첫 일정 + 안내**로 처리(음성은 1건이 기본). 사진은 후보 여러 개가 정상이므로 분리 로직은 사진 단계에서 추가.

### 4-4. 규칙이 못 풀 때
`ScheduleCandidate`의 필수 필드(제목·날짜)가 `missing`이거나 파서가 구조를 못 잡은 경우에만 AI 보강 대상(§7). 규칙이 `found`로 확정한 필드는 AI가 덮어쓰지 못한다(AI 결과는 `missing`·`confirm` 필드의 제안으로만 반영).

## 5. 확인 화면 (음성·사진 공용 draft-view)

- 상단: **인식된 원문**(음성: STT 텍스트 / 사진: 인식 텍스트 요약)을 보여 주고 "다시 말하기/다시 찍기" 제공. STT 텍스트는 직접 고쳐서 **다시 파싱**할 수 있다(음성 오인식 대응).
- 본문: 후보 카드. 필드별로 `found`는 일반 표시, `confirm`은 강조 + 선택지 칩(예: 오전/오후, 날짜 후보 2개), `missing`은 빈칸 + 같은 톤의 "필요해요" 표시. 값 수정은 기존 `date-picker.js`·폼 컴포넌트 재사용.
- 저장 버튼은 `confirm`·`missing` 필수 항목이 모두 처리돼야 활성. **1회 탭 저장**(별도 2차 확인 팝업 없음 — 이 화면 자체가 확인).
- 음성은 후보 1개가 기본, 사진은 후보 목록(체크박스, 저장할 것만 선택). **같은 컴포넌트**이고 후보 수만 다르다.
- 지난 날짜·원문에 없는 값은 사용자가 눈으로 구분할 수 있게 표시(문구는 §10 결정 5에서 승인).
- 아이가 여러 명/가구 없음 등 기존 일정 폼의 전제 조건(`usActive()`)과 같은 가드를 쓴다.

**UX 문구(안, 승인 필요)**
- 음성 안내: "일정 내용을 말씀해 주세요. 날짜와 시간을 함께 말하면 자동으로 넣어드려요."
- 예시: "내일 오후 3시 민준이 소아과" (예시 아이 이름은 실제 연결된 아이 이름으로 바꿔 보여 주는 안 포함)
- 저장 전 고지: 확인 화면 자체가 "내용을 확인하고 저장해 주세요" 역할(별도 "자동 등록됩니다" 문구는 쓰지 않는다 — 실제 동작과 다름).

## 6. 음성 STT — 웹 우선 구현과 앱 확장

### 6-1. 웹에서의 선택 (검증 전 가설)
| 방식 | 판단 | 비고 |
|---|---|---|
| **Web Speech API**(`SpeechRecognition`/`webkitSpeechRecognition`) | **1차 기본 어댑터** | Chrome(데스크톱·안드로이드)·Safari 계열에서 제공되나 **환경별 편차가 큼.** 오디오가 브라우저 벤더 서버로 전송될 수 있어 안내 문구 필요 |
| 키보드 받아쓰기(KeyboardFallback) | **항상 있는 폴백** | 개발 부담 최소, 권한·지원 문제 없음. 마이크 버튼을 한 번 더 눌러야 하는 UX |
| 서버 STT(Whisper·Clova 등) | 이번 범위 밖 | 서버·비용·오디오 전송. 정확도 문제가 실측으로 확인되면 재검토 |

### 6-2. 환경별 제약 (모두 **추가검증 필요** — P0에서 실측)
- **Capacitor iOS 앱(현재 TestFlight 1.0)의 WKWebView**: Web Speech API가 노출되지 않을 가능성이 높다. 그렇다면 **현재 iOS 앱에서는 처음엔 KeyboardFallback만** 동작하고, 네이티브 어댑터는 재배포 때 붙인다.
- **iOS Safari / 홈 화면에 추가한 웹앱(standalone)**: 지원 여부·권한 동작이 다를 수 있음.
- **권한**: 마이크(웹은 브라우저 프롬프트, HTTPS 필수 / 네이티브는 Info.plist·AndroidManifest 사용 설명). 권한 거부 시 폴백으로 자연스럽게 전환(막다른 화면 금지).
- **개인정보 고지**: Web Speech의 서버 전송 가능성, 인식 텍스트는 저장하지 않는다는 점을 최초 사용 시 한 줄 고지(문구는 승인 필요).
- **네트워크 없음**: 웹 STT는 대개 온라인 필요 → 오프라인이면 폴백 안내.

### 6-3. 앱(iOS/Android) 확장 경로
- 네이티브 음성 인식 플러그인(Capacitor)을 `speech-native.js`에 어댑터로 연결한다. **STT 이후 코드는 변경 없음**이 합격 기준(어댑터 파일 + `createSpeechInput` 선택 순서만 수정).
- 네이티브는 **앱 재배포**가 필요(플러그인·권한 문구·Info.plist). 사진 OCR 네이티브 어댑터와 **같은 배포에 묶는다.**
- 이번 구현 범위에서 네이티브 어댑터는 **계약 + 스텁 + 연결 지점 문서**까지. 실제 플러그인 도입은 별도 트랙(§9 P5).

## 7. AI 보강 (텍스트 전용, 후순위)

- **음성은 AI 없이 1차 출시가 가능하다**(규칙 + 확인 화면). AI는 정확도 실측 후 붙인다 → 서버·요금 결정이 음성 출시를 막지 않는다.
- 호출 조건: 규칙 후 필수 필드가 `missing`이거나 구조 파싱 실패일 때만. **전송 대상은 텍스트뿐**(오디오·이미지 아님). 로그인 사용자만, 호출 횟수 제한.
- 서버 방식(Firebase Functions[Blaze] vs Cloudflare Workers)은 사진 AI·알림(B7)과 같은 결정으로 묶는다(§10 결정 1). 이 문서에서는 `ai-parser.js` 인터페이스(`parseWithAI(text, today, context) → ScheduleCandidate[]`)만 고정한다.
- 아이 이름 등 개인정보는 가능하면 서버로 보내기 전에 치환(예: "아이1")하고 돌려받은 뒤 복원 — 적용 여부는 §10 결정 4.

## 8. 사진 입력과의 정합 (기존 설계 §6 대비)

**충돌 없음(공통):** 확인 화면·저장·`sourceType:"OCR"`·I8/I9·원본 사진 미저장·규칙 변경 없음.

**수정이 필요한 부분 (먼저 보고)**
1. **"기기 안에서 먼저 글자 인식" 전제**: 설계서 §6 A안은 웹에서 품질이 낮다(오픈소스 OCR의 한글·표·손글씨). 웹에서 기기 내 OCR을 쓸 수 있는 마땅한 방법이 **현재 확인되지 않았다.** 따라서 사진도 음성처럼 **어댑터로 분리**한다:
   - `TextRecognitionAdapter` 계약: `recognize(imageBlob) → { text, lines?[], source }`
   - **앱(iOS/Android)**: 네이티브 글자 인식 어댑터(기기 안, 서버 전송 없음).
   - **웹**: 1차는 이미지를 AI 비전 서버로 보내 텍스트/후보를 받는 어댑터(서버 결정 §10-1 필요) 또는 후순위. → **웹 사진 입력은 서버 결정 이후**, 음성은 그 전에 출시 가능.
2. **하이브리드 순서**: 사진은 "OCR 텍스트 → 공통 규칙 파서 → (필요 시) AI". 웹에서 비전 AI가 이미지를 직접 처리하는 경우 이미지가 외부로 전송되므로 **동의 문구가 별도로 필요**(음성의 텍스트 전용 AI와 고지 수준이 다름).
3. **사진은 후보가 여러 개 나오는 입력**이라 문서 분리·표 해석(가정통신문·시간표)·대화 캡처 추론 규칙(근거·확신도 표시)이 추가로 필요 → 이 문서에서는 P4로 두고 별도 세부 설계.
4. **대화 캡처**(상대 날짜 "내일"을 대화의 날짜 구분선 기준으로 풀기)는 공통 파서의 `today`를 **"기준일" 인자**로 일반화하면 해결된다(`parseKoDateTime(text, baseDate)`). 사진 단계에서 구분선 날짜를 baseDate로 넘긴다. 이 일반화는 P1 설계에 이미 반영한다(인자명 `baseDate`).

## 9. 단계와 담당

운영 원칙(3-Agent): 조사/구현/테스트 분리, **조사 결과를 바로 구현하지 않고 hn-main이 판정**, 구현자 자체 테스트만으로 완료 처리 금지. 조사·검증은 건당 5분 제한(초과는 "추가검증 필요" 마킹).

| 단계 | 내용 | 담당 | 산출·합격 기준 |
|---|---|---|---|
| **P0 사전 검증** | ① 웹 STT 지원 실측: Capacitor iOS WKWebView · iOS Safari · 홈 화면 웹앱 · Chrome(안드로이드/데스크톱). ② 현재 iOS 프로젝트의 권한 설명(Info.plist 위치·카메라/마이크/음성 항목 유무). ③ 웹 배포 구조(HTTPS·호스팅·`www` 복사 절차). ④ 규칙 시뮬레이션: `provenance` 추가 키 허용 여부 | research (+ dev 일부) | 환경별 지원 표(가능/불가/조건), §6-2 가설 확정·정정 |
| **P1 공통 코어** | `datetime-ko.js`·`candidate-parser.js`·`draft-view.js`·`capture-flow.js`, + 메뉴 진입, **텍스트 직접 붙여넣기/KeyboardFallback으로 end-to-end 동작**(음성 없이도 초안→확인→저장) | dev | §12 샘플 세트 전부 통과, 확인 없이 저장 불가, 기존 일정 테스트 불변 |
| **P2 음성** | `speech-input.js` 계약·`WebSpeechAdapter`·권한/환경 안내·음성 버튼(플래그 `voiceInput`) | dev | P0에서 가능으로 확인된 환경에서 말하기→초안; 불가 환경은 안내+폴백, 막다른 화면 없음 |
| **P3 AI 보강** | `ai-parser.js` + 중계 서버(서버 결정 후) | dev | 규칙이 못 푼 샘플만 개선, `found` 필드 덮어쓰기 없음, 호출 횟수 제한 |
| **P4 사진** | 사진 선택·압축·`TextRecognitionAdapter`(웹=비전 서버, 앱=네이티브)·후보 분리·대화 캡처 규칙·동의 문구 | dev + research | 별도 세부 설계 후 착수 |
| **P5 네이티브 연결** | 앱 재배포: 네이티브 STT·OCR 어댑터, 권한 문구, TestFlight | dev | STT 이후 코드 무변경으로 동작 |
| **검증** | 각 단계 독립 테스트(§12), 실기기 확인 | test | 단계별 통과 후에만 다음 단계 |

권장 순서: **P0 → P1 → P2**(여기까지 서버·앱 재배포 없이 출시 가능) → P3 → P4 → P5. P0 결과로 iOS 앱에서 웹 STT가 안 되면 P2는 "웹·사파리용 음성 + 앱은 폴백"으로 나가고 앱 음성은 P5에서 개방된다.

## 12. 테스트 계획 (hn-test 독립 검증 기준)

기준일 고정: `baseDate = 2026-10-04 (일)`. 순수 파서 단위 테스트(node)로 자동화한다.

| 입력 | 기대 결과 |
|---|---|
| 내일 오후 3시 민준이 소아과 | 날짜 2026-10-05 found, 15:00 found, 대상 민준(연결 시), 제목 "소아과", 분류 MEDICAL(confirm 아님) |
| 모레 아침 9시 어린이집 상담 | 2026-10-06, 09:00, 제목 "어린이집 상담", 분류 INSTITUTION |
| 10월 23일 캠핑 | 2026-10-23, 시간 missing(종일 여부 선택) |
| 금요일 저녁 7시 가족 저녁식사 | 2026-10-09, 19:00 |
| 다음 주 화요일 3시 피아노 | 날짜 **confirm**(일요일 기준 모호: 10-06 / 10-13), 시간 **confirm**(오전/오후) |
| 이번 주 토요일 병원 | 10-03은 지난 날짜 → **confirm** |
| 소아과 예약 | 제목만 found, 날짜·시간 **missing**(오늘로 채우지 않음) |
| 점심에 보연이 만나기 | 시간 missing(12:00 채우지 않음), 날짜 missing |
| 매주 화목 4시 피아노 | recurrence WEEKLY byDay TU·TH, 16:00 |
| 3시 반 병원 | 15:30/03:30 confirm |
| 어제 3시 병원 | 지난 날짜 경고 confirm |
| (빈 문자열 / 의미 없는 말) | 후보 없음 + "다시 말해 주세요" |
| 2026년 12월 25일 | found (연도 명시) |
| 내일 소아과 모레 어린이집 상담 | 첫 일정만 + 분리 안내 |

공통 검증 항목
1. 어떤 입력에서도 **확인 전에는 저장 호출이 발생하지 않는다**(저장 함수 호출 스파이).
2. 저장 문서가 `UserSchedule.validate`를 통과하고 `sourceType`·`provenance.confirmedByUser`가 규칙(I8)과 일치한다. 규칙 에뮬레이터 테스트로 `VOICE` 문서 생성 허용·미확인 거부 확인.
3. 어댑터 교체 테스트: 가짜 어댑터(고정 `SttResult`)로 파서 이하를 구동해 **어댑터 id와 무관하게 결과 동일**.
4. `isAvailable()` 실패 사유별로 막다른 화면 없이 폴백이 열린다.
5. 플래그 OFF에서 + 메뉴·기존 일정 흐름이 이전과 **100% 동일**(기존 `test/*` 전부 통과).
6. 실기기: P0 표에서 "가능"인 환경 각각에서 말하기→초안→저장 확인(은찬·구로구 고정 테스트 계정).
