# 06. 큐레이션 엔진 설계 — "지금 꼭 할 것 3개"를 무엇으로 고르나 (판단 구조 초안)

> 작성 2026-10-05 · 배포 v1.12.97 기준 · 읽기 전용 분석(코드·데이터 수정 없음, 브라우저 실행 없음).
> 기준 문서: `docs/한눈육아-서비스방향설계서.md`(이하 설계서), `docs/한눈육아-메뉴별UX지침.md`(이하 지침), `docs/ux-review/00~05`.
> 이 문서는 UI 문서가 아니다. 화면 시안보다 먼저, **어떤 데이터로 무엇을 어떤 순서로 고르는지**를 정한다.
> 기존 0~36개월 엔진(`js/todo-engine.js`, `js/schedule.js`)은 다시 만들지 않는다. 엔진이 이미 계산하는 값을 **위에 얹어 쓰는 판단 층** 하나를 추가하는 설계다.
> 표기: 코드 위치는 `파일:행`. 코드로 확인했지만 화면에서 확인하지 않은 것은 **추가확인 필요**. 근거가 없는 값은 **제안값**으로 적었다.

## 0. 결론 먼저 (5줄)

1. 한눈육아는 지금 "개인화 필터"(나이·지역·검증 상태·36개월 허용 목록)까지는 잘 되어 있다. 하지만 필터를 통과한 항목 사이에서 **무엇이 더 급한지는 거의 판단하지 않는다.** 홈은 카테고리 순서로 나열하고(`js/home.js:82-93`), `priority`는 정렬 동점 처리에만 쓰인다(`js/hn-logic.js:247`).
2. 판단에 필요한 신호는 **데이터에 이미 대부분 있다.** 엔진 상태 7종(`js/todo-engine.js:209-220`), `catchUp`(놓치면 끝인가), `leadDays`(언제부터 "곧"인가), 신청 소급 기한(`js/todo-engine.js:277-290`), 지원금 마감·임박 판정(`js/hn-logic.js:343-437`)이 있다. 정작 "지금 할 일"을 고르는 함수 `todayItems`(`js/hn-logic.js:317-335`)는 만들어져 있는데 **화면 어디에서도 쓰지 않는다.**
3. 없는 신호는 네 가지다. ① 항목의 성격(행동형/관찰형/주의형) ② 같은 방문·같은 창구 묶음 ③ 조건형 자격에 대한 부모의 답 ④ 부모가 "봤다/확인했다"는 기록. ①②는 카테고리 코드로 거의 자동 생성할 수 있다. ③④는 저장 경로를 새로 만들어야 한다.
4. 제안: 점수 합산 대신 **규칙 계층(슬롯 배정)**을 쓴다. 후보를 먼저 "행동형/알아둘 것"으로 나누고, 행동형만 시급성 규칙으로 "지금 꼭 할 것(최대 3)"과 "곧 다가오는 것(최대 2)"에 넣는다. 알아둘 것은 대표 1개만 보여 준다. 비면 채우지 않는다. 이 순서는 36개월 전후 모두 같다.
5. 기존 계획(00 문서)의 단계 0 → 단계 1 순서는 유지해도 된다. 다만 단계 1 맨 앞에 **"1-0 판단 규칙 정의"**(유형 매핑 + 순수 함수 + 테스트, M)를 끼워 넣어야 한다. 그래야 홈·월령 정보·지원·자동 일정 개편이 같은 기준을 쓴다. 단계 0의 "36+ 날짜 필터 수정"은 지원금만의 문제가 아니라 **검진·접종도 기간이 열리는 날 사라지는 문제**라서, 범위를 넓혀 단계 0에서 먼저 처리해야 한다(§9).

### Q3. 중요도가 다른데 같은 무게로 보이는 곳

- 홈 카테고리 줄: "접종" 줄과 "생활" 줄이 같은 모양이다. 줄 안에서는 `priority`로만 정렬한다(`js/hn-logic.js:247`).
- 체크리스트 카드: 놓치면 다시 못 하는 VX-ROTA(`catchUp: NOT_ALLOWED`)와 언제 해도 되는 FD-11 컵 연습(`ALLOWED`, priority 3)이 같은 카드 모양이다(`js/app.js:2077-2125`).
- 지원 탭: 첫만남이용권 SB-01(무조건, NOT_ALLOWED)과 구로구 수유 코칭 GURO-P02(선택 서비스)가 같은 목록 높이에 있다.
- `priority` 값 자체도 섞여 있다. 안전 수칙 SF-02~05는 priority 1, 대부분의 접종은 priority 2다(데이터 집계: priority 1=24건, 2=56건, 3=23건). **priority는 "위험의 크기"에 가깝고 "시급성"이 아니다.** 그래서 priority 하나로 "지금 꼭 할 것"을 고르면 안전 수칙이 접종보다 앞에 온다.

### Q4. 정보·관찰·행동·일정·혜택이 어떤 기준으로 섞이나

현재는 **화면별로 기준이 다르다.**

| 화면 | 섞는 기준 | 위치 |
|---|---|---|
| 홈 0~35 | `categoryGroup`(6개) → 카테고리 줄. 지원금(행정·지원금)은 따로 혜택 섹션 | `js/hn-logic.js:212`, `js/home.js:121-142` |
| 체크리스트 | 월령 그룹 → 6카테고리 순서 | `js/app.js:2282-2286` |
| 상세 시트 | `categoryGroup`이 발달·생활·안전이면 관찰형 분기. 그래서 SC·CR(생활·수유로 묶임)에 '관찰 포인트' 라벨이 붙음 | `js/app.js:2601-2620` |
| 달력 칩 | `scheduleKind`(fixed/window/monthly). 창 폭 60일 이하면 날짜형 | `js/schedule.js:105-118, 170` |

즉 **"이 항목이 행동인지 정보인지"를 한 곳에서 정의하지 않는다.** 화면마다 categoryGroup·scheduleKind·접두사 목록을 따로 본다. 이것이 판단 층이 필요한 가장 큰 이유다.

### Q5. '지금 해야 할 것'과 '알아두면 좋은 것'을 구분하나

- **엔진은 구분한다.** 상태 `DUE`(지금 기간 안), `UPCOMING`(leadDays 안), `OVERDUE_CATCHUP`(지났지만 가능), `OVERDUE_FINAL`(지나서 끝)이 있다(`js/todo-engine.js:209-220`). 화면 문구 "지금 챙기세요/곧이에요/이 시기는 지났어요"도 있다(`js/schedule.js:40-48`).
- **화면은 거의 구분하지 않는다.** 홈은 엔진 상태를 쓰지 않고 "이번 달과 겹치는가"로 자체 분류한다(`js/hn-logic.js:206-250`). `exposureLevel`(MUST 84 / CONDITIONAL 17 / REFERENCE 2)은 엔진 결과에 실려 나오지만(`js/todo-engine.js:298`) 화면 어디에서도 읽지 않는다.
- `todayItems`(DUE·OVERDUE_CATCHUP 중 날짜형, 지난 것 먼저 → priority → 마감 순)는 정확히 "지금 해야 할 것" 후보를 만드는 함수다. 하지만 `js/hn-logic.js:600`에서 내보내기만 하고 호출하는 곳이 없다. `selectOverdue`(`js/todo-engine.js:484`)도 같다.
- 홈의 `cls.upcoming`(다음 달 이후)도 계산만 하고 쓰지 않는다(`UPCOMING_MAX` 미사용, `js/home.js:10`).

## 3. 산출물 A-1. 우선순위 기준 — 무엇을 쓰고 어떻게 계산하나

### 3-1. 기준별 채택 여부

### 3-2. 점수 합산 대신 규칙 계층을 쓰는 이유

1. **'왜 지금' 설명이 가능해야 한다**(지침 §3). 계층 규칙은 "마감이 10월 18일이에요"처럼 걸린 규칙 하나를 그대로 문장으로 쓸 수 있다. 가중 합산 점수는 이유를 설명하기 어렵다.
2. **데이터가 고르지 않다.** priority는 의미가 섞여 있고, 지역 지원금은 priority가 없다(기본 2, `hn-logic.js:310`). 점수에 넣으면 출처별로 왜곡된다.
3. **"모든 것을 중요하다고 하지 않기"를 보장한다.** 계층은 자격이 없는 항목(알아둘 것)이 상위 슬롯에 들어가는 것을 구조적으로 막는다. 점수 방식은 알아둘 것이 많이 쌓이면 점수가 올라 상위로 새어 나온다.

### 3-3. 계산식(규칙 계층 + 동점 처리)

```
입력: e (visibleSchedule(true) 이벤트), 오늘 T, 사용자 상태 S

[게이트] 아래 중 하나라도 해당하면 후보에서 제외
  G1 완료 / 미해당(__na) / autoExtended
  G2 연결 일정이 있고, 연결 날짜 > T + 7일   (home-reappear.json, 전 단계 공통)
  G3 OVERDUE_FINAL (→ "지난 것" 기록으로만, 홈 미노출)
  G4 지원금 status ≠ available·upcoming, 또는 deadlineType = unconfirmed 이고 행동 링크도 없음 → 알아둘 것으로만

[유형] actionType(e) = 정책 매핑(§5) — ACT(예약·신청·학교 행정) / CHECK(조건 확인) / KNOW(관찰·주의·해보기·정보)

[시급성 계층] ACT·CHECK만 계산
  L1 놓치면 끝   : catchUp = NOT_ALLOWED 이고 DUE, 그리고 기간 끝까지 ≤ 30일
  L2 마감 임박   : 마감(subsidyDeadline | applicationDeadline | windowEnd) − T ≤ 30일
  L3 늦었지만 가능: OVERDUE_CATCHUP 이고 exposureLevel = MUST
  L4 지금 기간 안 : DUE 이고 (창 폭 ≤ 60일 | priority = 1 & MUST | 신청 소급이 아직 가능(retroactiveEligible))
  L5 기간 안·여유 : 그 밖의 DUE / available (마감 > 30일 또는 상시)
  L6 곧 시작     : UPCOMING(leadDays 안) 또는 시작 − T ≤ 45일
  L7 나중        : 그 밖(SCHEDULED)

[슬롯]
  지금 꼭 할 것  = L1~L4 (ACT), 최대 3 행동 단위
  곧 다가오는 것 = L5~L6 (ACT·CHECK), 최대 2 행동 단위
  이 시기 알아두기 = KNOW 중 DUE, 대표 1 (+ 접힌 "N개 더")
  나중          = L7, 홈 미노출

[동점 처리 — 같은 계층 안]
  ① 남은 날 오름차순(마감 없음 = ∞)
  ② missable(catchUp NOT_ALLOWED) 먼저
  ③ exposureLevel MUST 먼저 (CONDITIONAL 뒤)
  ④ priority 오름차순
  ⑤ id
```

- 숫자 값(30일, 45일, 60일, 7일)은 모두 **제안값**이다. 30일은 기존 `isUrgent` 기본값, 60일은 기존 날짜형 판정(`schedule.js:105`), 7일은 기존 재등장 값과 맞췄다. 정책 파일 하나(`data/policy/curation.json`, 신설 제안)에 모아 값만 바꾸게 한다.
- L4의 "priority = 1 & MUST" 조항은 SB-01·02·04, PG-01·02, HC-03~09처럼 **창이 길어도 미루면 손해가 큰** 항목을 위한 것이다. 이 조항이 없으면 HC-04(18~24개월, 창 6개월)는 23개월이 될 때까지 "곧"에 머문다.
- 시급성 계산은 **이미 있는 함수 위에 얹는다**: 엔진 status(`todo-engine.js:209`), `subsidyStatus`·`subsidyDeadline`·`isUrgent`(`hn-logic.js:343-408`), `todayItems`의 정렬(`hn-logic.js:328-334`)을 재사용한다.

### 3-4. 데이터 한계 때문에 생기는 오판 예시(설계 시 반드시 표시)

- **NAT-011 배우자 출산휴가(출생 후 120일)**: `conditionLabel`이 없어서 "무조건 받는 것"으로 분류된다. 하지만 실제로는 근로자만 해당한다. 테스트 계정(2026-06-20생)은 마감이 10월 18일이라 L2(마감 임박)로 "지금 꼭 할 것" 1순위가 된다. → `conditionKey: employed` 같은 조건 키가 없으면 **잘못된 1순위**가 나온다. 조건 키 보강 전까지는 고용 관련 항목(NAT-009~013, PREG-008)을 CHECK로 매핑하는 예외 규칙이 필요하다.
- **SB-02 부모급여 / SB-04 아동수당**: 60일 소급 기한이 지난 뒤에도 미신청이면 `retroactiveEligible: false`가 된다. 이때는 L4가 아니라 "지금 신청해도 신청한 달부터 받는다"는 문장으로 L4에 남기는 편이 맞다. 제도 해석은 데이터 문구(`next-stage.json` TO_BORN detail)를 그대로 쓰고, 새 사실을 만들지 않는다.

## 4. 산출물 A-2. 우선순위 체계 — 4단계 정의

이름 제안: **지금 꼭 할 것 / 곧 다가오는 것 / 이 시기 알아두기 / 나중에**. 요청안의 "지금 알아둘 것"은 "꼭 할 것"과 '지금'이 겹쳐 무게가 같아 보인다. 그래서 "이 시기 알아두기"로 시기 범위만 말하게 했다. "나중에 알아도 되는 것"은 홈에 나오지 않으므로 사용자 문구가 필요 없다(월령 정보 탭의 "나중 시기 보기" 접힘으로 충분).

| 단계 | 정의 | 진입 조건 | 이탈 조건 | 최대 노출 | 근거 |
|---|---|---|---|---|---|
| **① 지금 꼭 할 것** | 이번에 하지 않으면 손해·놓침이 생기는 **행동** | ACT 유형 + L1~L4 | 완료 / 일정 연결(→ 가족 일정 카드로 이동, 날짜 7일 전 재등장) / 미해당 / 기간 끝(OVERDUE_FINAL) | **3 행동 단위** | 01 문서 H2와 같은 값. 실제 데이터에서 같은 시기에 L1~L4가 동시에 3개를 넘는 경우는 출생 직후(PG-01·SB-01·02·04 + 지역 마감)와 접종 회차가 겹칠 때뿐이다. 묶음 규칙을 적용하면 대부분 3 이하다(**추가확인 필요**: 단계별 실측) |
| **② 곧 다가오는 것** | 기간 안이지만 여유가 있거나, 곧 시작할 행동 | ACT·CHECK + L5~L6 | ①로 올라감 / 완료·연결 / 미해당 | **2** | "곧"은 준비 신호라 1~2개면 충분하다. 많이 보여 주면 ①과 경쟁한다. 다음 단계 배너가 따로 있다 |
| **③ 이 시기 알아두기** | 관찰·주의·해보기·정보 | KNOW + DUE(이번 달과 겹침) | 기간 끝 / '확인했어요'(주의형, 그 구간 동안 접힘) / `seenAt` 후 강등 | **대표 1** + "N개 더"(접힘) | 지침 §2 "대표 고민 우선". 알아둘 것은 개수가 많아도 급하지 않다 |
| **④ 나중에** | 시작이 45일보다 먼 것 | L7 | 시간이 지나 ②로 | 홈 0 | 지침 §3 "너무 일찍 과도하게 노출하지 않음" |

### 4-1. "행동 단위" 묶기 규칙(개수를 셀 때)

| 묶음 | 규칙 | 근거 데이터 |
|---|---|---|
| 같은 방문 접종 | 같은 창(시작·끝 같은 날)의 VX 회차는 1단위("4개월 접종 4가지") | `hn-logic.js:108` VX 묶음 키 재사용 |
| 접종 + 검진 같은 시기 | 같은 달 VX 묶음과 HC는 2단위로 둔다(기관이 다를 수 있음) | 제안 |
| 출생 직후 신고·신청 | PG-01 + SB-01·02·04 + 원스톱 대상 지역 장려금은 1단위("출생신고 때 한 번에") | 원스톱 범위는 **추가확인 필요**(03 문서). 확인 전에는 PG-01·SB-02·SB-04(next-stage TO_BORN이 이미 묶은 3개)만 묶는다 |

### 4-2. 넘칠 때 자르는 규칙

1. 계층 순서(L1 → L4)와 동점 처리 순서대로 3단위를 채운다.
2. 남은 ① 후보는 **②로 내리지 않는다.** "지금 꼭 할 것 N개 더 보기" 한 줄로 남긴다. 급한 것을 "곧"으로 보이게 하면 판단을 다시 부모에게 넘기게 된다.
3. 같은 유형이 3칸을 모두 차지하면(예: 지원금 3개) 3번째 칸은 다른 유형의 L1~L3이 있을 때만 그것으로 바꾼다. 같은 유형 3개만 있으면 그대로 둔다.
4. ③ 알아두기 대표 1개는 다음 순서로 고른다: 이번 달 **새로 시작**하는 항목(displayMonth = 현재 월령) → 이정표 시기 → 주의형 priority 1 → 관찰형. 이미 본(`seenAt`) 항목은 뒤로 보낸다.

| **연례·반복형** | 매년·매 6개월 | 다음 회차 후보만 | ② | VX-FLU(2번째 시즌 이후 정책 미확정, `todo-engine.js:388-421`), OR-04 |

**핵심 규칙**: 캘린더는 "날짜가 있는 것"만, 홈은 "판단 결과"만 보여 준다. 같은 항목이 둘 다에 나올 수 있다. 다만 **홈에서 일정에 넣으면 홈에서는 빠지고 캘린더(가족 일정 카드)로 옮겨 간다**(G2 규칙). 이렇게 하면 "한 번 판단한 것을 두 번 판단하지 않게" 된다.

36개월 이상도 같은 표를 쓴다. 다른 점은 후보가 `auto-after36.json`에 있는 34개로 제한된다는 것뿐이다. 이미 그 목록이 "필수·시기성"(설계서 §7-D) 기준으로 골라 둔 것이라, 36+ 후보는 대부분 ACT 유형이다.

## 7. 산출물 B. 큐레이션 엔진 초안 — 단계별 가능/추가 개발

### 7-1. 파이프라인 검토

요청안: 전체 후보 → 조건 필터 → 완료/중복 제거 → 시급성 → 연령 적합 → 지역 적합 → 행동 가능성 → 우선순위 → 상위 N

**실제 데이터 구조에 맞춘 수정안**

```
① 후보 생성  : buildSchedule → visibleSchedule(true)       [연령·지역·검증·출생순위·36+ 허용이 이미 여기서 끝남]
② 상태 제거  : 완료·미해당·연결(7일 밖)·OVERDUE_FINAL·autoExtended
③ 묶기      : 같은 방문(VX 묶음 키)·같은 창구·같은 제도(별칭)
④ 유형 분류  : actionType (ACT / CHECK / KNOW)               ← 신설
⑤ 시급성 계층: L1~L7 (엔진 status + 마감 + catchUp + 소급)
⑥ 슬롯 배정  : ①3 / ②2 / ③1 / ④0 + 넘침·빈칸 규칙
⑦ 이유 문장  : 걸린 규칙 → '왜 지금' 템플릿
⑧ 행동 붙이기: AutoSteps 모델(신청 → 일정 → 완료)
```

요청안과 다른 점은 세 가지다.

1. **연령·지역 적합을 뒤로 둘 필요가 없다.** 엔진과 `buildSubsidyEvents`가 이미 처음에 걸러 준다(`todo-engine.js:331-333`, `schedule.js:216-231`). 뒤에서 다시 하면 같은 판단이 두 번 생긴다.
2. **"상위 N"이 아니라 "유형별 슬롯"이다.** 전체를 한 줄로 세워 상위 N개를 자르면 알아둘 것이 행동 칸에 섞인다. 유형을 먼저 나누고(④), 행동형 안에서만 시급성을 비교한다.
3. **묶기(③)를 시급성보다 먼저 한다.** 묶지 않으면 2개월 접종 5건이 3칸을 다 차지한다.

## 8. 산출물 C. 홈 UX — '판단 결과'로서의 홈

### 8-1. 최종 정보 구조(모든 단계 공통)

| 순서 | 영역 | 보여 주는 판단 결과 | 왜 이 자리인가 |
|---|---|---|---|
| 0 | **머리 줄**: 이름 · 월령/나이/학년 · 지역 | "무엇을 기준으로 골랐는지" | 지침 §3 '왜 지금'의 전제. 36+에는 지금 없음(01 문서 H1) |
| 1 | **지금 꼭 할 것**(≤3) | L1~L4 행동, 행마다 '왜 지금' 한 줄 + 바로 버튼(신청 링크 / 일정 넣기 / 완료) | 설계서 §15 ①. 앱을 연 이유에 가장 먼저 답한다 |
| 2 | **우리 가족 일정**(7일) | USER + 연결된 AUTO 예약 + 신청 마감 | 설계서 §9. "한 번 판단해 일정이 된 것"이 여기로 온다. 지금은 AUTO를 뺀다(`app.js:4573`) |
| 3 | **곧 다가오는 것**(≤2) | L5~L6, 시작 날짜 | 설계서 §15 ④ |
| 4 | **이 시기 알아두기**(대표 1 + 접힘) | KNOW 중 대표 | 설계서 §15 ①의 '대표 고민' |
| 5 | **다음 단계**(배너 1) | `next-stage` pick | 설계서 §12 |
| 6 | **탐색 한 줄**(조건부) | 어디갈까(데이터 있는 지역만), 교육(초등만) | 설계서 §15 ⑥. 숫자를 지어내지 않는다 |

- **1과 2의 순서 규칙(36개월 전후 통일)**: ①이 비어 있지 않으면 ①이 맨 위, 비어 있으면 가족 일정이 맨 위. 지금처럼 "36+이면 가족 먼저, 계정 모드면 가족 먼저"(`home.js:67-70`) 같은 나이·모드 분기를 없앤다. 초등은 ①이 자주 비므로 자연스럽게 가족 일정이 위로 온다.
- **혜택 섹션은 따로 두지 않는다.** 마감 있는 지원금은 ①·②에 시급성대로 섞인다. 상시 혜택은 4번 아래 "받을 수 있는 혜택 N개 · 확인할 것 M개" 한 줄로 혜택 탭에 잇는다(36+는 탭이 숨겨져 있으므로 이 한 줄이 시트로 열리게 — 사용자 결정).
- 36+ 메모장 할 일은 6번 아래로 내리거나 가족 일정 카드에 합친다(01 문서 개선 UX).
- 00 문서 단계 1-2 "이번 달 한눈에(가족 일정 N·챙길 것 N·갈 만한 곳 N)" 요약은 **권하지 않는다.** 개수 요약은 "무엇부터?"를 다시 부모에게 묻는 형태다. 숫자는 각 영역의 "N개 더"에만 쓴다.

### 11-3. 사용자 결정이 필요한 것(이 문서에서 새로 생긴 것)

1. 슬롯 개수 3 / 2 / 1과 시급성 값(마감 30일, 곧 45일, 짧은 창 60일)을 제안값으로 승인할지
2. 고용 조건 항목(NAT-009~013, PREG-008)을 조건 키 보강 전까지 "확인형"으로 내릴지
3. 엔진 조건형 지원 4건(SB-06~09)을 숨김 대신 "해당되면" 확인형으로 보여 줄지(Q6, 실화면 확인 후)
4. 조건 답을 저장할지, 저장한다면 항목 단위("해당돼요/아니에요")로만 할지(소득 구간은 묻지 않는 안 권장)
5. `seenAt`(봤음)을 기기에만 저장할지, 가구로 동기화할지
6. 36+에서 혜택 탭을 계속 숨길지(숨긴다면 홈 한 줄 → 시트)
7. 00 문서 단계 1-2(이번 달 한눈에)를 보류할지

## 12. 10줄 요약

1. 한눈육아는 나이·지역·검증 필터까지는 자동이지만, 통과한 항목 중 무엇이 급한지는 판단하지 않는다. 홈은 카테고리 나열이고, `priority`는 동점 처리에만 쓴다(`hn-logic.js:247`).
2. 판단 신호는 대부분 이미 있다. 엔진 상태 7종, `catchUp`(놓치면 끝 8건), `leadDays`, 신청 소급 기한, 지원금 마감·임박이다. "지금 할 일" 함수 `todayItems`는 만들어져 있지만 쓰이지 않는다.
3. 없는 신호는 항목 성격(행동/관찰/주의), 같은 방문 묶음, 조건형에 대한 부모의 답, 봤음 기록이다. 앞의 둘은 코드 접두사로 자동 생성할 수 있다.
4. 새로 확인한 문제 둘: 36+ 홈이 `date(시작일) >= 오늘`로 걸러서 검진·접종도 기간이 열리는 날 빠진다(`app.js:1264`). 엔진 조건형 지원 SB-06~09는 입력이 비어 있어 항상 숨겨진다(`schedule.js:145`). 둘 다 실화면 확인이 필요하다.
5. 제안은 점수 합산이 아니라 규칙 계층이다. 게이트 → 묶기 → 유형(ACT/CHECK/KNOW) → 시급성 L1~L7 → 슬롯 순서로 고르고, 걸린 규칙을 그대로 '왜 지금' 문장으로 쓴다.
6. 슬롯은 지금 꼭 할 것 3(행동 단위) / 곧 다가오는 것 2 / 이 시기 알아두기 대표 1 / 나중에 0이다. 넘치면 "N개 더"로 남기고 아래 단계로 내리지 않는다. 비면 채우지 않는다.
7. 행동 연결 필수 유형(접종·검진·지원 신청·학교 행정·구강 예약)만 "지금 꼭" 후보가 된다. 관찰·주의·생활·학교 검진은 정보로 충분하다. 캘린더에는 날짜·마감이 있는 것만 넣는다.
8. 홈은 머리 줄 → 지금 꼭 → 가족 일정 → 곧 → 알아두기 → 다음 단계 → 탐색 순서다. ①이 비면 가족 일정이 맨 위로 온다. 이 하나의 규칙으로 36개월 전후를 통일한다.
9. ⑥ "우선순위 대행" 점수는 현재 홈 2, 월령 정보 1, 지원 2, 자동 일정 2, 다음 단계 3이다. 판단 층을 적용하면 4 / 3 / 4 / 4 / 4로 오를 것으로 본다. 교육 트렌드는 데이터 없이는 1~2에 머문다.
10. 00 문서 계획은 유지하되 단계 1 맨 앞에 "1-0 판단 규칙 정의(M)"를 넣는다. 단계 0의 36+ 날짜 필터는 범위를 넓혀 먼저 고친다. 중복 정리는 확인 후 1-0과 함께, 시트 라벨 수정은 매핑 표와 함께 한다. 초등 학년 전환은 단계 1로 옮기고, 1-2 개수 요약은 보류한다.
