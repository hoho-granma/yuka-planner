# 한눈육아 C1 — 완료 상태 공유 안전화 (필드 단위 갱신) 설계

작성: hn-main · 2026-10-01 · 상태: **C1-a 구현·커밋 완료(7ec0392). 실제 Firestore 서버 검증 전까지 릴리스·push·버전 변경 금지.** 아래 §1의 줄 번호와 현재형 서술은 **구현 이전(HEAD 5f97b75) 기준**이며, 구현 후에는 호출부가 `syncCompletedChanges(before)`로 바뀌었다(`js/app.js`, 4곳). `updateCompleted`는 폴백·기존 함수로만 남아 있다. 근거: C0 결합계약 §7·§11(C1은 C2 선행), hn-test 사실 확인(2026-10-01), hn-research Firebase 공식 문서 확인(2026-10-01).

## 1. 문제 (확인된 사실)
- `js/sync.js updateCompleted(code, completedData)`가 `ref.update({completed: 전체맵, updatedAt})`로 `completed` 필드를 **통째로 교체**한다. 호출부 4곳(js/app.js: 해당 없음 `:681`, 완료·취소 `:1575`, 완료일 수정 `:1644`, 기록 메모 `:3025`)은 모두 로컬 `completed` 객체 전체를 넘긴다.
- 읽는 쪽(`app.js:303-325` 리스너, `:3143-3173` 앱 시작, `:2062` 코드 불러오기, `:2217` 아이 전환)은 서버 값을 로컬에 **통째로 덮어쓴다**(병합·시점 비교 없음).
- 순수 JS 모사 결과: 두 기기가 서로 스냅샷을 받기 전에 각각 X·Y를 체크하면 서버 {Y}만 남고 X가 유실된다. 한 기기의 취소가 다른 기기의 늦은 전송으로 되살아날 수 있다. (실제 Firestore 호출 없음 — 모사)
- 규칙: `families` update는 최상위 키(`completed`, `updatedAt` 등)만 판정하므로 `completed` 안의 필드 단위 쓰기도 규칙상 허용된다. `completed` 값 검증 규칙은 없다.

## 2. 공식 문서 근거 (열람 2026-10-01)
- 중첩 필드를 도트 표기/FieldPath로 갱신하면 같은 맵의 다른 키를 덮어쓰지 않는다. 맵을 통째로 넣으면 맵 전체가 덮어쓰기된다(Add data).
- 필드 경로의 simple field name은 영문자·숫자·언더스코어만, 숫자로 시작 불가. 하이픈이 있는 키(`VX-DTAP__dose-5`)는 도트 문자열 방식이 안전하지 않고 **FieldPath 객체를 쓰라고 문서가 명시**한다(Quotas and limits).
- `update(field: string | FieldPath, value, ...)` 시그니처 지원(DocumentReference v8). 특정 필드 삭제는 `FieldValue.delete()`(Delete data). 문서가 없으면 `update`는 실패한다.
- 문서에서 확인되지 않은 것(실제 서버 테스트로 확정): 서로 다른 기기가 서로 다른 키를 동시에 쓸 때의 동작, `FieldPath("completed", 키)`+`FieldValue.delete()` 조합, 오프라인 큐·유실, `hasPendingWrites`.

## 3. 계약
1. **쓰기**: `completed` 맵 전체를 보내지 않는다. 키 하나를 `update(new firebase.firestore.FieldPath("completed", key), entry, "updatedAt", serverTimestamp)`(필요하면 FieldPath 인자 형태를 둘로 나눈 호출)로 쓴다. 취소는 같은 경로에 `firebase.firestore.FieldValue.delete()`. **키 문자열을 `"completed." + key`로 이어 붙이지 않는다.**
2. **새 sync.js 함수**(기존 `updateCompleted`는 삭제하지 않고 남긴다 — 옛 호출·테스트 호환): `setCompletedEntry(code, key, entry)`, `removeCompletedEntry(code, key)`, 그리고 **`updateCompletedEntries(code, {set:{key:entry,…}, remove:[key,…]})`**(한 번의 `update(fp1,v1, fp2,FieldValue.delete(), …, 'updatedAt', ts)`로 여러 필드를 원자적으로 전송). 앞의 둘은 뒤의 공용 헬퍼를 쓴다. 반환·오류 처리는 `updateRecord`(필드 단위, `sync.js:85-94`)와 같은 방식. (2026-10-01 hn-dev 반환으로 보강: 호출부가 한 번에 2~3키를 바꾸므로(해당 없음 설정=삭제1+설정1, 완료 토글=`__na` 삭제+완료/취소+`__milestone` 설정, 완료일 수정=id+`__milestone`) 키마다 별도 update를 보내면 중간 상태가 다른 기기에 보이고 일부 실패 시 불일치가 생긴다 → 호출부당 update 1회.)
3. **호출부 4곳**: 로컬 `completed` 객체를 바꾸고 `saveCompleted()` 한 뒤, 맵 전체 대신 **이 조작에서 실제로 바뀐 키 집합**(set·remove)을 `updateCompletedEntries` **한 번**으로 보낸다. 로컬 변경 로직(어떤 키를 지우고 쓰는지, 취소 시 `__milestone`을 남기는 현재 동작 포함)은 **그대로** 두고 전송 방식만 바꾼다.
4. **불변**: `completed`의 키 형식(`<todo_id>__<occurrenceKey>`, `__na`, `__milestone`)과 값 형태(`{done, todo_id, occurrenceKey, recordType, recordedAt, memo?}`), 로컬 저장(`yukjigi_completed`), 읽는 쪽(스냅샷 덮어쓰기)은 이번 단계에서 바꾸지 않는다. `createFamily`·`ensureFamilyCode`의 최초 일괄 업로드도 그대로.
5. **규칙 변경 없음, 배포 없음.** 옛 클라이언트(통째 교체)와 섞여도 지금과 같은 위험이 남을 뿐 나빠지지 않는다. 옛 코드가 통째로 쓰면 새 코드의 필드 단위 이점이 그 시점에는 무효가 된다.
6. 같은 키를 동시에 쓰면 마지막 쓰기가 이긴다(허용). 서로 다른 키는 서로 덮어쓰지 않는 것이 목표 — 서버 테스트로 확정.

## 4. 이번 단계에서 하지 않는 것 (C1-b, 나중)
오프라인 대기열·재시도·"이 기기에만 저장됨" 표시, 앱 시작 시 로컬 변경 보존 병합, 실패 알림(현재는 `console.error`), 스냅샷 병합 정책 변경. (오프라인 유실은 기존 단일 기기 한계이며 가족 공유의 동시성 문제와 구분)

## 5. 테스트 계획
- 로직 테스트(Firestore 대체물 주입): `setCompletedEntry`/`removeCompletedEntry`가 FieldPath 두 인자(`"completed"`, key)와 값/삭제 센티널, `updatedAt`를 올바르게 구성하는지, 키에 하이픈·`__`가 있어도 문자열 이어 붙임을 쓰지 않는지, 호출부 4곳이 맵 전체가 아닌 바뀐 키 하나를 넘기는지(스텁 기록 비교).
- 모사 테스트: 같은 시나리오(순차·동시·취소+타 기기 체크)를 필드 단위 의미로 돌려 두 키가 모두 남고 취소가 되살아나지 않음을 확인(Firestore 호출 금지, 의미 모사임을 주석으로 명시).
- 회귀: 기존 test/*.test.js 전체, 규칙 논리 테스트(변경 없음 확인), T1(가구 쓰기 없음)·골든 가족 문서 호환(완료 토글 외에는 쓰기 없음).
- **실제 서버 검증(자동화 불가)**: FieldPath+delete 조합, **한 update에 여러 FieldPath/값 쌍(삭제 센티널 혼합 포함)**, 서로 다른 키 동시 쓰기, 하이픈 키 — 일회용 테스트 가족 코드에서 두 브라우저(또는 수동 테스트 페이지)로 확인. 방법은 사용자 결정(수동 vs hn-test가 일회용 코드에서만 검증 후 사용자가 삭제).
